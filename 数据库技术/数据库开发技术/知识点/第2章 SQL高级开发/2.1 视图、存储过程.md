视图与存储过程是数据库端封装的两类核心对象：视图封装“查询形状”，存储过程封装“业务动作”。二者共同构成数据库的对外接口层，是应用层调用数据库的稳定契约。本节基于 MySQL 8.0（InnoDB），SQL 方言差异处单独标注。

## 视图（VIEW）

视图是一条命名查询的虚拟表，本身不存储数据（物化视图除外），每次访问时由 DBMS 重写为底层查询执行。

### 创建视图

```sql
-- MySQL 8.0 / InnoDB
-- 依赖表：employee(id, name, dept_id, salary, status)、department(id, dept_name)
CREATE OR REPLACE VIEW v_active_employee AS
SELECT e.id, e.name, e.salary, d.dept_name
FROM employee e
JOIN department d ON e.dept_id = d.id
WHERE e.status = 'ACTIVE';
```

### WITH CHECK OPTION

限制通过视图执行的 `INSERT/UPDATE` 必须满足视图的 `WHERE` 条件，防止“插入后从视图查不到”的异常。

```sql
CREATE OR REPLACE VIEW v_active_employee AS
SELECT id, name, salary, dept_id, status
FROM employee
WHERE status = 'ACTIVE'
WITH CHECK OPTION;

-- 以下语句会因违反 CHECK OPTION 而报错
-- INSERT INTO v_active_employee(id, name, salary, dept_id, status) VALUES (10, 'Tom', 8000, 1, 'INACTIVE');
```

### 视图作用

1. **简化查询**：把多表 JOIN 与复杂过滤封装为单表式访问。
2. **数据安全**：通过只暴露部分列与行实现行/列级权限控制。
3. **逻辑独立性**：底层表结构调整时，视图可屏蔽变化，应用层 SQL 不必修改。

### 视图更新限制

视图可更新（`INSERT/UPDATE/DELETE`）的前提是其定义能唯一对应到基表的一行。下列情况通常**不可更新**：

- 包含聚合函数（`SUM/COUNT/AVG`）
- 包含 `DISTINCT`、`GROUP BY`、`HAVING`、`UNION`
- 包含子查询引用基表
- 多表 JOIN 且非键保持表（key-preserved）

> [!warning] MySQL 不可更新视图的限制
> MySQL 对可更新视图的判定较严格，包含 `JOIN` 的视图通常只能更新键保持表的列。Oracle/SQL Server 的判定规则不同，迁移时需逐视图验证。

## 存储过程（PROCEDURE）

存储过程是预编译并存储在 DBMS 中的过程对象，可包含控制流、循环、异常处理与事务。

### 创建存储过程

```sql
-- MySQL 8.0
-- 依赖表：account(id, balance)、transfer_log(id, from_id, to_id, amount, created_at)
DELIMITER $$
CREATE PROCEDURE transfer(
    IN  p_from    BIGINT,
    IN  p_to      BIGINT,
    IN  p_amount  NUMERIC(15,2),
    OUT p_result  VARCHAR(32)
)
BEGIN
    DECLARE v_bal NUMERIC(15,2);

    -- 事务边界见 [[3.1 事务ACID特性]]
    START TRANSACTION;

    SELECT balance INTO v_bal FROM account WHERE id = p_from FOR UPDATE;
    IF v_bal IS NULL THEN
        ROLLBACK; SET p_result = 'FROM_NOT_FOUND';
    ELSEIF v_bal < p_amount THEN
        ROLLBACK; SET p_result = 'INSUFFICIENT_BALANCE';
    ELSE
        UPDATE account SET balance = balance - p_amount WHERE id = p_from;
        UPDATE account SET balance = balance + p_amount WHERE id = p_to;
        INSERT INTO transfer_log(from_id, to_id, amount, created_at)
            VALUES (p_from, p_to, p_amount, NOW());
        COMMIT; SET p_result = 'OK';
    END IF;
END$$
DELIMITER ;

-- 调用
CALL transfer(1, 2, 100.00, @r);
SELECT @r AS result;
```

### 参数模式

| 模式 | 方向 | 说明 |
| ---- | ---- | ---- |
| `IN` | 调用方 → 过程 | 默认模式，传入只读 |
| `OUT` | 过程 → 调用方 | 过程内赋值后返回 |
| `INOUT` | 双向 | 调用方传入初始值，过程可修改后返回 |

### 优缺点

| 优点 | 缺点 |
| ---- | ---- |
| 预编译，执行计划可复用 | 可移植性差，方言差异大 |
| 减少应用与 DB 之间的往返 | 调试困难（无统一断点机制） |
| 封装业务逻辑，统一权限控制 | 业务逻辑下沉数据库，扩展性受限 |
| 减少网络流量（仅传参数与结果） | DB 服务器 CPU 压力上升 |

> [!note] 业务逻辑放应用层还是数据库？
> 现代架构普遍倾向把业务逻辑放在应用层（更易测试、扩展、版本化），仅在以下场景使用存储过程：
> - 强一致性写多表且需减少往返；
> - DBA 需统一权限审计入口；
> - 历史系统兼容。

## 限制与易错点

- 视图嵌套层次过多会显著影响性能与可读性，建议不超过 3 层。
- 存储过程中默认不自动提交，必须显式 `COMMIT`/`ROLLBACK`（见 [[3.1 事务ACID特性]]）。
- MySQL 存储过程中 `DECLARE` 必须在 `BEGIN` 后最前面，顺序错误会编译失败。
- Oracle 的存储过程语法（`PL/SQL`、`PROCEDURE ... AS ... BEGIN ... END;`）与 MySQL 不同，迁移需逐过程重写。
