数据库开发生命周期（Database Development Life Cycle, DDLC）描述一个数据库应用从需求到运维所经历的全部阶段及其产出物。它不等于软件开发生命周期（SDLC），但与之对应：DDLC 聚焦数据建模与持久层，SDLC 聚焦功能交付。两者在实现阶段后合流。

## 各阶段产出物

| 阶段 | 核心问题 | 主要产出物 |
| ---- | ---- | ---- |
| 需求分析 | 系统要存储与处理什么数据 | 数据字典、数据流图、业务规则清单 |
| 概念设计 | 现实实体与关系是什么 | ER 图（实体、关系、基数、属性） |
| 逻辑设计 | 如何用关系模型表达 | 关系模式、主外键、范式化（3NF/BCNF） |
| 物理设计 | 在具体 DBMS 上如何落地 | 表结构、索引、分区、存储引擎选择 |
| 实现 | 用 DDL/DML 建库与初始数据 | `CREATE` 脚本、初始化数据脚本、视图/过程 |
| 测试 | 是否满足功能与性能要求 | 单元测试、集成测试、压力测试报告 |
| 部署 | 如何交付到生产 | 迁移脚本、回滚脚本、配置项 |
| 维护 | 长期如何保持可用 | 监控告警、备份策略、容量规划、调优记录 |

## 数据库设计与软件设计的对应

| 数据库设计 | 软件设计 | 关系 |
| ---- | ---- | ---- |
| 需求分析 | 需求分析 | 同源输入，数据需求是功能需求的子集 |
| 概念设计 | 领域建模 | ER 图对应领域模型，实体对应领域类 |
| 逻辑设计 | 详设（接口/类） | 关系模式对应持久层接口契约 |
| 物理设计 | 实现细节（数据结构） | 索引/分区对应内存数据结构与缓存策略 |
| 实现 | 编码 | DDL 脚本是数据库的“源代码” |
| 测试 | 测试 | 数据准备脚本服务于集成测试 |

> [!note] 区分概念模型、逻辑模型与物理模型
> - **概念模型**：与 DBMS 无关，描述“现实有什么”。产物是 ER 图。
> - **逻辑模型**：用关系模型表达，但仍与具体 DBMS 解耦。产物是关系模式。
> - **物理模型**：绑定具体 DBMS，确定类型、索引、存储参数。产物是 DDL。
> 这三层对应 [[数据库原理]] 中的三级模式：外模式、概念模式、内模式。

## 示例：电商订单的建模演进

```sql
-- MySQL 8.0
-- 概念设计产出：实体 Customer, Order, Product；关系 Place, Contain
-- 逻辑设计产出（已范式化到 3NF）：
CREATE TABLE customer (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    name        VARCHAR(64)  NOT NULL,
    email       VARCHAR(128) NOT NULL,
    created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_customer_email UNIQUE (email)
);

CREATE TABLE product (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    name        VARCHAR(128) NOT NULL,
    price       NUMERIC(15,2) NOT NULL CHECK (price >= 0),
    stock       INT          NOT NULL DEFAULT 0
);

CREATE TABLE orders (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    customer_id   BIGINT       NOT NULL,
    order_no      VARCHAR(32)  NOT NULL,
    total_amount  NUMERIC(15,2) NOT NULL,
    placed_at     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customer(id),
    CONSTRAINT uk_orders_no UNIQUE (order_no)
);

CREATE TABLE order_item (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id    BIGINT        NOT NULL,
    product_id  BIGINT        NOT NULL,
    quantity    INT           NOT NULL CHECK (quantity > 0),
    unit_price  NUMERIC(15,2) NOT NULL,
    CONSTRAINT fk_oi_order   FOREIGN KEY (order_id)   REFERENCES orders(id),
    CONSTRAINT fk_oi_product  FOREIGN KEY (product_id)  REFERENCES product(id)
);

-- 物理设计补充索引（应对高频查询路径）
CREATE INDEX idx_orders_customer ON orders(customer_id, placed_at);
CREATE INDEX idx_order_item_product ON order_item(product_id);
```

> [!tip] 设计阶段就要考虑索引
> 物理设计阶段依据高频查询模式决定索引；上线后再发现慢查询加索引属于维护阶段补救，代价更高。性能优化见第6章（待扩展）。

## 限制与易错点

- 跳过概念设计直接画表，会导致后期反复重构、范式化失败。
- 逻辑设计未做范式化，会引入插入/更新/删除异常（详见 [[数据库原理]] 范式章节）。
- 实现阶段写出 DDL 但没有迁移与回滚脚本，部署失败时无法快速回退。
