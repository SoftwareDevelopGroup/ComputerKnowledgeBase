索引是数据库性能优化的第一道防线：没有索引则查询退化为全表扫描。本节以 InnoDB 的 B+ 树为核心，说明索引结构、聚簇与二级索引的差异、复合索引的最左前缀原则，以及导致索引失效的典型写法。掌握这些原则才能在设计阶段就避免性能陷阱。本章以 MySQL 8.0 InnoDB 为例。

## 索引类型

| 类型 | 结构 | 适用 | InnoDB 支持 |
| ---- | ---- | ---- | ---- |
| B+ 树索引 | 平衡多叉树，叶子有序链表 | 等值、范围、排序、分组 | 默认 |
| 哈希索引 | 哈希表 | 等值查询 | 自适应哈希（内部） |
| 全文索引 | 倒排索引 | 文本检索 `MATCH ... AGAINST` | 支持 |
| 空间索引 | R 树 | 地理数据 | 支持 |

## B+ 树索引结构

B+ 树是 B 树的变体：非叶子节点只存索引键（不存数据），所有数据存于叶子节点，且叶子节点按主键顺序用双向链表相连。这种结构使范围查询只需遍历链表。

```mermaid

    N1 --> L2[叶子: 15,20]

    N3 --> L4[叶子: 35,40]

    L2 <-.双向链表.-> L3
    L3 <-.双向链表.-> L4
```

> [!note] 为什么用 B+ 树而非二叉树
> - 树高低：磁盘 IO 以页（16KB）为单位，B+ 树每个节点可存上千个键，3 层即可覆盖千万级数据，IO 次数少。
> - 范围查询快：叶子链表顺序遍历即可，B 树需中序回溯。

## 聚簇索引 vs 非聚簇索引

| 维度 | 聚簇索引 | 二级索引（非聚簇） |
| ---- | ---- | ---- |
| 数据存储 | 叶子节点存整行数据 | 叶子节点存主键值 |
| 每表数量 | 仅 1 个 | 可多个 |
| InnoDB 主键 | 默认主键即聚簇索引 | 需通过主键“回表”取整行 |
| 查询效率 | 直接取到数据 | 非覆盖索引需回表 |

> [!warning] 回表与覆盖索引
> 通过二级索引查到主键后，再到聚簇索引查整行，称为**回表**，产生两次 IO。若查询的列已全部包含在二级索引中，则无需回表，称为**覆盖索引**（`EXPLAIN` 的 Extra 显示 `Using index`）。

```sql
-- 建表与索引
CREATE TABLE employee (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,
    dept_id BIGINT NOT NULL,
    age INT,
    INDEX idx_name(name),
    INDEX idx_dept_age(dept_id, age)
) ENGINE=InnoDB;

-- 走 idx_name，但需回表取 age（非覆盖索引）
EXPLAIN SELECT id, name, age FROM employee WHERE name = '张三';

-- 走 idx_dept_age，且 dept_id+age 已覆盖查询列（覆盖索引）
EXPLAIN SELECT dept_id, age FROM employee WHERE dept_id = 1;
-- Extra: Using index
```

## 复合索引与最左前缀原则

复合索引 `(a, b, c)` 在 B+ 树中按 a、b、c 顺序排序。能利用索引的前提是查询条件从最左列开始连续使用。

| 查询条件 | 是否使用 idx(a,b,c) | 说明 |
| ---- | ---- | ---- |
| `WHERE a=?` | 使用 | 最左前缀 |
| `WHERE a=? AND b=?` | 使用 | 连续 |
| `WHERE a=? AND b=? AND c=?` | 使用 | 全部命中 |
| `WHERE b=?` | 不使用 | 缺最左列 a |
| `WHERE a=? AND c=?` | 部分使用（仅 a） | b 缺失，c 无法用索引 |
| `WHERE a>? AND b=?` | a 用范围，b 无法用索引 | 范围之后的列失效 |

```sql
-- 反例：违反最左前缀，索引失效
SELECT * FROM employee WHERE age = 25;  -- idx_dept_age 无法使用

-- 正例：按最左前缀设计查询
SELECT * FROM employee WHERE dept_id = 1 AND age = 25;  -- 完整命中 idx_dept_age
SELECT * FROM employee WHERE dept_id = 1;               -- 命中前缀 dept_id
```

## 索引设计原则

- **选择性高优先**：区分度 `count(distinct col)/count(*)` 接近 1 的列适合建索引；性别等低选择性列单独建索引意义不大。
- **避免过度索引**：每个索引都有写入与存储成本，单表索引建议不超过 5~6 个。
- **覆盖索引**：高频查询的列尽量放入复合索引，避免回表。
- **前缀索引**：长字符串列可用 `INDEX(col(20))` 只索引前缀，节省空间。
- **主键尽量短**：二级索引存主键值，主键越长，二级索引越大。

## 索引失效场景

```sql
-- 1. 函数操作：对索引列使用函数 → 失效
WHERE YEAR(created_at) = 2024          -- 失效
WHERE created_at >= '2024-01-01'       -- 改为范围查询，走索引

-- 2. 隐式类型转换：字符串列传入数字 → 失效
WHERE phone = 13800138000              -- phone 是 VARCHAR，失效
WHERE phone = '13800138000'            -- 正确，走索引

-- 3. LIKE 前缀通配 → 失效
WHERE name LIKE '%张'                  -- 失效（前导 %）
WHERE name LIKE '张%'                  -- 走索引

-- 4. OR 条件中一侧无索引 → 整体失效
WHERE dept_id = 1 OR salary > 10000    -- 若 salary 无索引，整体退化为全表

-- 5. 不等于（!= / <>）、NOT IN 通常失效
WHERE status != 1                      -- 通常全表扫描

-- 6. 计算 → 失效
WHERE age + 1 = 18                     -- 失效
WHERE age = 17                         -- 改写后走索引
```

> [!tip] 判断索引是否生效的唯一方法
> 永远用 `EXPLAIN` 验证。`key` 字段显示实际使用的索引，`type` 为 `ALL` 表示全表扫描，`rows` 是预估扫描行数。

## EXPLAIN 关键字段

| 字段 | 含义 | 优化目标 |
| ---- | ---- | ---- |
| `type` | 访问类型 | `const` > `eq_ref` > `ref` > `range` > `index` > `ALL` |
| `key` | 实际使用的索引 | 非 NULL 且符合预期 |
| `rows` | 预估扫描行数 | 越小越好 |
| `Extra` | 附加信息 | `Using index`（覆盖索引）为佳；`Using filesort`/`Using temporary` 需警惕 |
| `possible_keys` | 可能选用的索引 | 为空说明无可用索引 |
| `ref` | 索引比较的常量或列 | — |

```sql
EXPLAIN SELECT * FROM employee WHERE dept_id = 1 AND age > 20 ORDER BY age;
-- 期望: type=range, key=idx_dept_age, Extra 不应出现 Using filesort
```

## 限制与易错点

- 索引不是越多越好：写多读少的表，索引过多会拖慢 INSERT/UPDATE/DELETE。
- `EXPLAIN` 的 `rows` 是基于统计信息的估算，可能与实际行数有偏差，可用 `EXPLAIN ANALYZE`（MySQL 8.0）查看实际执行。
- 加索引在大表上可能锁表较久，线上应使用 `ALGORITHM=INPLACE, LOCK=NONE` 或 `pt-online-schema-change`。
