参数化查询用占位符替代 SQL 拼接，同时解决安全（SQL 注入）与性能（执行计划复用）两个问题。这是应用层数据访问的第一安全防线。本节基于 JDBC，原理同样适用于 ADO.NET、Python DB-API、Node.js 驱动。

## SQL 注入风险

字符串拼接 SQL 时，用户输入若包含 SQL 元字符，会被解释为 SQL 的一部分，导致越权访问。

### 反模式示例

```java
// 危险：拼接 SQL
String name = request.getParameter("name");  // 用户输入："'; DROP TABLE product; --"
String sql = "SELECT * FROM product WHERE name = '" + name + "'";
// 拼接结果：SELECT * FROM product WHERE name = ''; DROP TABLE product; --'
// 后果：先查询空结果，再删除表
Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery(sql);
```

> [!danger] 不要依赖输入过滤防注入
> 黑名单/正则过滤难以覆盖所有注入向量（编码、注释、二次注入）。正确做法是**永远使用参数化查询**，让 DBMS 负责参数与 SQL 文本的边界。

## PreparedStatement

`PreparedStatement` 是 JDBC 提供的预编译语句对象，SQL 文本与参数分离，参数通过 `setXxx` 绑定。

```java
// 安全：参数化查询
String name = request.getParameter("name");  // 任意输入都不会被解释为 SQL
String sql = "SELECT id, name, price FROM product WHERE name = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, name);  // 参数值整体作为字面量绑定
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            // 处理结果
        }
    }
}
```

> [!note] 为什么参数化查询能防注入
> - SQL 文本与参数分别发送给 DBMS。
> - DBMS 先解析 SQL 模板并生成执行计划，`?` 处被标记为“参数占位”。
> - 绑定的参数值只作为**字面量**（数据）处理，永远不被解析为 SQL 语法。
> - 因此参数值中包含 `'`、`;`、`--` 等元字符也不会改变 SQL 结构。

## PreparedStatement vs Statement

| 维度 | Statement | PreparedStatement |
| ---- | ---- | ---- |
| SQL 构造 | 字符串拼接 | 占位符 + 绑定 |
| SQL 注入 | 易受攻击 | 防注入 |
| 执行计划 | 每次重新解析 | 模板可复用 |
| 可读性 | 差（引号转义复杂） | 好 |
| 适用 | DDL、无用户输入的固定语句 | 所有带用户输入或重复执行的语句 |

## 参数化查询的性能优势

DBMS 对 SQL 文本计算 hash 并缓存执行计划。相同模板的 SQL 第二次执行时可直接复用计划，省去解析与优化开销。

```java
// 服务端预编译：useServerPrepStmts=true&cachePrepStmts=true
// JDBC URL: jdbc:mysql://.../demo?useServerPrepStmts=true&cachePrepStmts=true&prepStmtCacheSize=64

// 第一次执行：DBMS 解析、优化、缓存执行计划
try (PreparedStatement ps1 = conn.prepareStatement("SELECT id FROM product WHERE category_id = ?")) {
    ps1.setLong(1, 1L);
    ps1.executeQuery();
}

// 第二次执行（同模板）：复用执行计划，仅绑定新参数
try (PreparedStatement ps2 = conn.prepareStatement("SELECT id FROM product WHERE category_id = ?")) {
    ps2.setLong(1, 2L);
    ps2.executeQuery();
}
```

> [!warning] 性能优势的前提
> - 必须开启服务端预编译（`useServerPrepStmts=true`），否则驱动只在客户端做参数转义。
> - 模板必须完全相同（含空格），动态拼接表名/列名会破坏计划复用。
> - 计划缓存有大小上限，热点 SQL 才能稳定命中。

## Statement vs PreparedStatement 对比示例

```java
// 同一业务：按部门 ID 查员工
// === Statement（拼接，不安全） ===
String deptId = request.getParameter("deptId");
String sqlBad = "SELECT id, name FROM employee WHERE dept_id = " + deptId;
try (Statement stmt = conn.createStatement();
     ResultSet rs = stmt.executeQuery(sqlBad)) {
    // deptId="1 OR 1=1" → 全表泄露
}

// === PreparedStatement（参数化，安全） ===
try (PreparedStatement ps = conn.prepareStatement(
        "SELECT id, name FROM employee WHERE dept_id = ?")) {
    ps.setLong(1, Long.parseLong(request.getParameter("deptId")));
    try (ResultSet rs = ps.executeQuery()) {
        // 输入 "1 OR 1=1" 会被 Long.parseLong 拒绝；
        // 即使绕过校验，也只会作为字面量比较，无注入
    }
}
```

## 不能参数化的部分

占位符**只能用于值**，不能用于标识符（表名、列名）或 SQL 关键字。下列用法非法：

```sql
-- 非法：占位符不能替换表名
SELECT * FROM ? WHERE id = ?;

-- 非法：占位符不能替换列名
SELECT ? FROM product;
```

处理动态表名/列名时，必须用白名单校验后拼接，例如：

```java
// 白名单：只允许预定义的列名
Set<String> allowed = Set.of("name", "price", "created_at");
String orderBy = request.getParameter("orderBy");
if (!allowed.contains(orderBy)) {
    throw new IllegalArgumentException("invalid order column");
}
String sql = "SELECT id, name FROM product ORDER BY " + orderBy + " LIMIT ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setInt(1, 10);
    // ...
}
```

> [!tip] 排序/分页列名用白名单
> 动态 `ORDER BY` 列不能参数化，必须用枚举或白名单校验后拼接。这是常见的注入点。

## 限制与易错点

- `IN` 子句的参数列表需逐个占位符或使用 `find_in_set`、临时表等技巧，JDBC 不支持单个 `?` 绑定数组。
- 参数化不防“业务逻辑漏洞”（如 IDOR 越权访问），仍需业务层鉴权。
- 不同 DBMS 的预编译行为不同：MySQL 默认客户端预编译，需显式启用服务端预编译才能获得计划复用。
- 批量插入使用 `addBatch` + `executeBatch` 比循环单条 `executeUpdate` 高效得多。
