用户权限管理解决“谁能连接、能对哪些对象做什么操作”的问题。它既是安全的第二道防线（即使应用被注入，账户权限也限制了破坏范围），也是多团队协作时的隔离手段。本节以 MySQL 8.0 为例，介绍用户管理、权限类型、授权与回收、角色与权限层级，并强调最小权限原则。

## 用户管理

```sql
-- 创建用户（同时指定密码与登录限制）
-- MySQL 8.0 推荐用 CREATE USER 而非 GRANT 隐式创建
CREATE USER 'app_user'@'10.0.%.%' IDENTIFIED BY 'StrongPass!2024';
-- '主机' 部分: '%' 任意主机、'10.0.%.%' 内网段、'localhost' 仅本机、'%' 不安全

-- 修改密码
ALTER USER 'app_user'@'10.0.%.%' IDENTIFIED BY 'NewPass!2024';

-- 锁定/解锁账户（临时禁用）
ALTER USER 'app_user'@'10.0.%.%' ACCOUNT LOCK;
ALTER USER 'app_user'@'10.0.%.%' ACCOUNT UNLOCK;

-- 删除用户
DROP USER 'app_user'@'10.0.%.%';

-- 查看现有用户
SELECT user, host, account_locked FROM mysql.user;
```

> [!tip] 账户命名 = 用户名 + 主机
> MySQL 账户由 `用户名@主机` 唯一标识。`'app'@'localhost'` 与 `'app'@'%'` 是两个不同账户，可拥有不同权限。生产环境应限定主机段，避免 `'%'` 全网开放。

## 权限类型

| 类别 | 权限 | 说明 |
| ---- | ---- | ---- |
| 数据 | `SELECT` `INSERT` `UPDATE` `DELETE` | 表行级 CRUD |
| 结构 | `CREATE` `ALTER` `DROP` `INDEX` | 表结构变更 |
| 管理 | `CREATE USER` `GRANT OPTION` `RELOAD` `PROCESS` | 账户与服务器管理 |
| 全部 | `ALL PRIVILEGES` / `ALL` | 所有权限（慎用） |

## 权限授予与回收

```sql
-- 授予表级权限
GRANT SELECT, INSERT, UPDATE ON shopdb.order TO 'app_user'@'10.0.%.%';

-- 授予列级权限（仅允许读取敏感列）
GRANT SELECT (id, name), UPDATE (name) ON shopdb.user TO 'app_user'@'10.0.%.%';

-- 授予库级权限（该库所有表）
GRANT SELECT ON shopdb.* TO 'report_user'@'10.0.%.%';

-- 授予全局权限
GRANT SELECT ON *.* TO 'readonly_user'@'10.0.%.%';

-- 回收权限
REVOKE UPDATE, DELETE ON shopdb.order FROM 'app_user'@'10.0.%.%';

-- 查看用户权限
SHOW GRANTS FOR 'app_user'@'10.0.%.%';
```

> [!warning] GRANT OPTION 的风险
> `GRANT OPTION` 允许被授权者把自身权限再授予他人，等于扩散权限。生产环境应严格控制，普通应用账户不应拥有。

## 角色管理

MySQL 8.0 原生支持角色（Role），把一组权限打包，再授予用户，便于批量管理与审计。

```sql
-- 创建角色
CREATE ROLE 'role_app', 'role_readonly', 'role_dba';

-- 给角色授权
GRANT SELECT, INSERT, UPDATE ON shopdb.* TO 'role_app';
GRANT SELECT ON shopdb.* TO 'role_readonly';

-- 把角色授予用户
GRANT 'role_app' TO 'app_user'@'10.0.%.%';
GRANT 'role_readonly' TO 'report_user'@'10.0.%.%';

-- 设置用户默认激活的角色（登录后自动生效）
ALTER USER 'app_user'@'10.0.%.%' DEFAULT ROLE 'role_app';

-- 查看用户被授予的角色
SHOW GRANTS FOR 'app_user'@'10.0.%.%' USING 'role_app';

-- 回收角色
REVOKE 'role_app' FROM 'app_user'@'10.0.%.%';
```

| 层级 | 语法 | 适用 |
| ---- | ---- | ---- |
| 全局级 | `*.*` | DBA、监控账户 |
| 数据库级 | `db.*` | 应用账户绑定单库 |
| 表级 | `db.table` | 细粒度业务隔离 |
| 列级 | `db.table(col1, col2)` | 敏感列保护 |

## 最小权限原则

> [!def] 最小权限原则（Principle of Least Privilege）
> 账户只授予完成其职责所必需的最小权限，且仅授予必需时长。权限越少，账户被盗或被注入后的破坏范围越小。

落地要点：

1. **应用账户与 DBA 账户分离**：应用日常只用业务库的 CRUD 账户，DDL 用独立 DBA 账户经审计执行。
2. **读写分离账户**：读副本连接的账户只授 `SELECT`，不授写权限。
3. **限定主机**：`'app'@'10.0.0.5'` 比 `'app'@'%'` 安全得多。
4. **定期审计**：`SELECT user, host FROM mysql.user;` 与 `SHOW GRANTS` 检查冗余权限并回收。
5. **不用 root 连应用**：root 拥有 `ALL`，被注入等于数据库沦陷。

## 限制与易错点

- MySQL 权限是“并集”：一个用户被多次授权，最终权限是所有授权的并集，回收需逐条 `REVOKE`。
- 修改权限后立即生效（MySQL 8.0 默认），旧版本可能需 `FLUSH PRIVILEGES`（仅直接改 mysql 表时需要）。
- 列级权限会让某些 `SELECT *` 失败，应用需显式列出有权限的列。
- 角色未设为 `DEFAULT ROLE` 时，用户登录后需手动 `SET ROLE role_name;` 才激活。
