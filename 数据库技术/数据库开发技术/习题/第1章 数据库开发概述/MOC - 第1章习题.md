<details>
<summary>分析题答案</summary>

**1.** 原两层 C/S 架构客户端直连 Oracle，业务逻辑在客户端，需安装升级、暴露面大、不支持异地办公。改造为三层 B/S 后：浏览器↔应用服务器↔数据库服务器，业务逻辑集中到应用服务器，DB 仅对应用服务器开放，安全边界清晰；浏览器零部署，升级集中在服务端，支持异地办公。

**2.** 表示层直接拼接 SQL → SQL 注入风险高、难以测试、层职责混乱；数据访问层写业务规则 → 迁移困难、层职责混乱。正确划分：表示层仅处理 UI 与输入校验；业务逻辑层封装领域规则与事务边界；数据访问层封装 SQL 与连接管理。业务层跨多个数据访问操作须包事务，否则数据不一致。

**3.** ①实体与关系 → 概念设计（产出 ER 图）；②关系模式与主外键 → 逻辑设计（范式化到 3NF）；③补充索引 → 物理设计。物理设计需考虑索引的原因：依据高频查询路径决定索引，上线后再发现慢查询加索引属于维护阶段补救，代价更高；设计阶段就考虑索引能预防性能陷阱。

**4.** Oracle 特有语法（`ROWNUM`、`DUAL`、`SEQUENCE.NEXTVAL`）非通用 SQL，迁移到 MySQL 需逐条重写（如 `ROWNUM`→`LIMIT`/窗口函数，`DUAL`可省略，`SEQUENCE`→`AUTO_INCREMENT`）。Driver Manager 架构只能切换驱动与连接字符串、统一 API，**不能**解决 SQL 方言差异——方言由驱动透传，应用层需自行适配。

</details>

<details>
<summary>综合题答案</summary>

**1.**
- **(1)** 选三层 B/S 架构。理由：需支持 Web 端与未来移动端，异地访问；B/S 浏览器零部署，升级集中；DB 仅对应用服务器开放，安全边界清晰；百万级订单量适合应用服务器连接池复用。
- **(2)** 关键产出物：需求分析（数据字典、业务规则清单）→概念设计（ER 图：Customer/Order/Product/OrderItem）→逻辑设计（关系模式、主外键、3NF）→物理设计（表结构、索引如 `idx_orders_customer`、存储引擎 InnoDB）→实现（DDL 脚本、初始化数据）→测试（集成/压力测试）→部署（迁移与回滚脚本）→维护（监控告警、备份策略）。
- **(3)** 推荐 MySQL 8.0 + JDBC。选型依据：Web 应用首选 OLTP，InnoDB 支持事务与行锁；Java 生态 JDBC 标准接口成熟，由厂商提供实现，配合连接池与 PreparedStatement。百万级数据量 MySQL 完全胜任。

**2.** 建议：现代架构普遍倾向把业务逻辑放在应用层（更易测试、扩展、版本化、迁移）。理由：两层 C/S 把业务下沉客户端导致部署升级困难；存储过程虽减少网络流量、封装业务、统一权限审计，但逻辑下沉数据库导致可移植性差、调试困难、扩展性受限、DB 服务器 CPU 压力上升。适合使用存储过程的场景：①强一致性写多表且需减少往返（如转账）；②DBA 需统一权限审计入口；③历史系统兼容。结论：默认业务逻辑放应用层，仅在上述明确场景使用存储过程。

</details>
