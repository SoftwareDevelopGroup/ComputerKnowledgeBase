# 6.3 索引、序列、同义词、视图

本节解决的核心问题是：**5类Oracle索引（B树/位图/函数/反向键/域）各自适用什么场景？如何创建与维护索引？序列的CYCLE/CACHE/ORDER参数如何配置？同义词PUBLIC/PRIVATE有什么区别？视图WITH CHECK OPTION和READ ONLY如何保证数据安全？** 索引与视图是SQL优化与权限控制的核心工具；序列是主键自动生成的基础设施。

## 6.3.1 索引五大家族与适用场景

> [!definition] 索引（Index）
> 索引是建立在表的列/多列组合上的**辅助访问结构**，类似图书的目录，通过减少全表扫描（Full Table Scan）需要访问的数据块数量，大幅加速WHERE条件过滤、JOIN连接、ORDER BY排序等操作。Oracle索引按组织方式分5大类：**B树索引（默认）、位图索引、函数基索引、反向键索引、域索引**。

```mermaid
graph TD
    A[Oracle索引家族] --> B[B树索引 B-Tree Index]
    A --> C[位图索引 Bitmap Index]
    A --> D[函数基索引 Function-Based Index]
    A --> E[反向键索引 Reverse Key Index]
    A --> F[域索引 Domain Index]

    B --> B1[普通B树（默认）：主键/唯一键/高基数列]
    B --> B2[唯一索引 UNIQUE INDEX：PRIMARY KEY/UNIQUE约束自动建]
    B --> B3[复合/组合索引 Composite：(col1, col2, col3...)多列一起]
    B --> B4[压缩索引 COMPRESS 1：复合索引前缀压缩，省空间]
    B --> B5[降序索引 DESC：某列DESC的范围查询]

    C --> C1[低基数列（性别/状态/省份<100个值）]
    C --> C2[数据仓库/报表：AND/OR/COUNT类复杂查询]
    C --> C3[DML极低（几乎不修改）的分析型系统]

    D --> D1[WHERE对列用函数：UPPER(name)='A' / TRUNC(dt)=DATE'...']
    D --> D2[表达式索引：TO_CHAR(id)||'-'||code]

    E --> E1[RAC集群：递增序列做主键，防止索引热块争用]
    E --> E2[键值连续递增导致B树右半边热块冲突场景]

    F --> F1[全文检索 Oracle Text（CONTAINS搜索）]
    F --> F2[Spatial空间数据（经纬度距离计算）]
    F --> F3[图像/XML/JSON自定义检索]
```

### 1. B树索引（默认，★★★OLTP最常用）

#### (1) B树结构与原理

B树（Balance Tree，平衡多路查找树）的每个叶子块用双向链表连接，支持等值/范围扫描；每个分支块存下级键值范围；所有叶子块到根块的深度相等（平衡，保证任意键查询路径长度一致）。

```mermaid
graph TD
    Root[根块 <br/> (键范围边界)] --> L1[分支块1<br/> 1~500]
    Root --> L2[分支块2<br/> 501~1000]
    L1 --> Leaf1[叶子块1<br/> 1~50行的ROWID]
    L1 --> Leaf2[叶子块2<br/> 51~100行的ROWID]
    L2 --> Leaf3[叶子块3<br/> 501~550行的ROWID]
    L2 --> Leaf4[叶子块4<br/> 551~600行的ROWID]
    Leaf1 <--> Leaf2
    Leaf2 <--> Leaf3
    Leaf3 <--> Leaf4
    style Leaf1 fill:#9f9
    style Leaf2 fill:#9f9
    style Leaf3 fill:#9f9
    style Leaf4 fill:#9f9
```

> [!note] Oracle B树索引不存NULL值！
> 单列B树索引中，列值为NULL的行**不会进入索引叶子块**。因此`WHERE col IS NULL`条件用不到普通B树索引，只能全表扫描；需要IS NULL查询可以用**函数基索引NVL(col, 'X')** 或**位图索引（位图索引存NULL）**解决。

#### (2) B树索引创建SQL（Oracle 19c）

```sql
-- ========== 普通单列B树索引 ==========
CREATE INDEX hr.emp_dept_id_idx
  ON hr.employees (department_id)
  TABLESPACE hr_indx
  PCTFREE 10                          -- 叶子块预留10%空闲（后续UPDATE导致分裂）
  INITRANS 2                          -- 高并发DML表的索引设2~4
  STORAGE (INITIAL 64K NEXT 64K MINEXTENTS 1 MAXEXTENTS UNLIMITED PCTINCREASE 0)
  NOLOGGING                           -- 创建索引时少写REDO（大索引创建加速）
  COMPUTE STATISTICS;                 -- 创建后立即收集统计信息，不用再GATHER

-- ========== 唯一索引（UNIQUE约束自动建，也可以手动建唯一索引）==========
CREATE UNIQUE INDEX hr.emp_email_uk_idx
  ON hr.employees (email)
  TABLESPACE hr_indx;

-- ========== 复合（组合）索引（A+B+C列组合）==========
-- ★★★ 索引列顺序原则：最常用在WHERE条件的等高数列在前，等数列/范围列在后
CREATE INDEX hr.ord_user_status_dt_idx
  ON hr.orders (user_id, status, create_date)   -- user_id等值过滤最多+status等值+create_date范围
  TABLESPACE hr_indx
  COMPRESS 2;                         -- 前缀压缩（压缩前2列的重复前缀，省大量空间）

-- ========== 在线创建索引（11g+ ONLINE关键字）==========
-- ★生产大表创建索引：必须加ONLINE！不加ONLINE会对整个表加DML表级锁，期间禁止INSERT/UPDATE/DELETE
CREATE INDEX hr.big_ord_user_idx
  ON hr.big_orders (user_id)
  TABLESPACE hr_indx
  ONLINE                              -- 允许DML并发（内部用临时日志表记录期间的DML，最后合并）
  PARALLEL 8                          -- 并行8个进程扫描大表建索引（OLAP用，OLTP不要太高并行）
  NOLOGGING;

-- ========== 反向键索引（RAC用，防止递增主键热块冲突）==========
CREATE INDEX hr.ord_id_rev_idx
  ON hr.orders (order_id)
  REVERSE                             -- 对键值的字节反转：123456 → 654321，把连续键值打散到不同叶子块
  TABLESPACE hr_indx ONLINE;
```

#### (3) B树索引维护SQL

```sql
-- ========== 索引重建（REBUILD）==========
-- 什么时候要REBUILD？DBA_INDEXES中：
--   BLEVEL > 3（B树深度>3层，路径长）
--   PCT_USED < 50%（叶子块使用率<50%，大量DELETE导致空块碎片）
--   删除了表大量行后，索引体积不缩
ALTER INDEX hr.emp_dept_id_idx REBUILD
  TABLESPACE hr_indx ONLINE           -- ★加ONLINE，DML不中断
  NOLOGGING PARALLEL 4 COMPUTE STATISTICS;

-- ========== 索引合并（COALESCE）==========
-- 轻度碎片：把相邻半满叶子块合并，不重建整个段（比REBUILD更轻量，不需要双倍空间）
ALTER INDEX hr.emp_dept_id_idx COALESCE;

-- ========== 索引重命名/不可见/删除 ==========
ALTER INDEX hr.emp_dept_id_idx RENAME TO hr.emp_dept_id_idx_v2;
ALTER INDEX hr.emp_dept_id_idx INVISIBLE;   -- 11g+：索引不可见，优化器忽略（不用DROP先验证性能影响，后悔了再VISIBLE）
ALTER INDEX hr.emp_dept_id_idx VISIBLE;
DROP INDEX hr.emp_dept_id_idx;              -- 删除索引（删主键索引要加DROP CONSTRAINT ... CASCADE，或直接ALTER TABLE DROP CONSTRAINT 主键名）

-- ========== 索引使用率统计（11g+ V$OBJECT_USAGE / 12c+ DBA_INDEX_USAGE）==========
-- 开启索引监控：
ALTER INDEX hr.emp_dept_id_idx MONITORING USAGE;
-- 观察1~3个月后：
SELECT index_name, table_name, used, start_monitoring, end_monitoring
  FROM v$object_usage WHERE index_name = 'EMP_DEPT_ID_IDX';
-- USED=NO的索引基本可以判定是无效索引，删除减少INSERT/UPDATE维护开销
```

### 2. 位图索引（Bitmap Index，★数据仓库OLAP专用）

#### (1) 适用场景 vs 不适用场景

| B树索引适用（OLTP） | 位图索引适用（OLAP/DW） | 位图索引绝对不能用的场景 |
| ---- | ---- | ---- |
| 列基数高（>1000+个不同值，如用户ID/订单ID） | **列基数极低（<100个不同值，甚至只有2~10个）**：性别M/F、订单状态NEW/PAID/CANCEL、省份1~34 | **高并发OLTP，频繁DML**：位图索引修改一行键值会锁整个位图段（上千行），必然导致严重死锁和DML阻塞 |
| OLTP：高并发INSERT/UPDATE/DELETE | **数据仓库/报表**：几乎不修改，大量只读复杂AND/OR查询 | 表的该列值经常被UPDATE（如订单状态频繁从NEW→PAID→SHIP） |
| 等值/范围查询 | AND/OR条件组合查询：WHERE status='CANCEL' AND dept_id=10 AND region='华东' | |
| COUNT(*)无位图优化 | `SELECT COUNT(*) FROM t WHERE dept_id=10 AND gender='F';` 位图直接位与，极快 | |

```sql
-- 创建位图索引（报表库订单状态列）
CREATE BITMAP INDEX dw.ord_status_bm_idx
  ON dw.orders (status)
  TABLESPACE dw_indx
  NOLOGGING PARALLEL 4;

-- 多列复合位图索引也常用（但B树复合索引更常用）
CREATE BITMAP INDEX dw.cust_gender_region_bm_idx
  ON dw.customer (gender, region_id)
  TABLESPACE dw_indx;
```

> [!warning] OLTP建位图索引的经典坑
> 某开发同学在订单status列（10个值）建了位图索引想加速查询，结果每天促销大量用户修改订单时，Oracle报大量`enq: TX - contention`死锁——位图索引段级锁导致两个改不同订单的会话互相抢位图段锁——**生产事故**。立即删除位图索引，改B树索引（虽然区分度不高，但至少行级锁不冲突）。

### 3. 函数基索引（Function-Based Index）

> [!definition] 函数基索引
> 对列做函数运算或表达式运算后的结果建B树索引。**解决WHERE中对列用函数导致索引失效的问题**（如WHERE UPPER(name)='A'、WHERE TRUNC(create_date)=DATE'2024-01-01'）。

```sql
-- 场景1：用户名大小写不敏感查询
CREATE INDEX hr.emp_upper_name_idx
  ON hr.employees (UPPER(last_name))   -- 对last_name转大写后的结果建索引
  TABLESPACE hr_indx ONLINE;
-- 查询时写WHERE UPPER(last_name) = 'KING' 就能走索引！不写函数的话B树(last_name)不能用

-- 场景2：按天查询订单（TRUNC日期）
CREATE INDEX hr.ord_trunc_crt_dt_idx
  ON hr.orders (TRUNC(create_date))    -- 对日期去时分秒后建索引
  TABLESPACE hr_indx ONLINE;
-- 查询WHERE TRUNC(create_date) BETWEEN DATE'...' AND DATE'...' 完美走索引范围扫描

-- 场景3：手机号尾号查询（对列做SUBSTR表达式）
CREATE INDEX hr.cust_substr_mobile_idx
  ON hr.customer (SUBSTR(mobile, 8, 4))
  TABLESPACE hr_indx ONLINE;

-- 场景4：虚拟列11g+替代函数基索引（更清晰）
ALTER TABLE hr.orders ADD (create_date_trunc AS (TRUNC(create_date)) VIRTUAL);
CREATE INDEX hr.ord_vc_dt_idx ON hr.orders (create_date_trunc) ONLINE;
-- 用虚拟列代替函数，执行计划更稳定
```

### 4. B树vs位图索引终极对比表

| 维度 | B树索引（默认，99%场景用） | 位图索引（只适合极少数场景）|
| ---- | ---- | ---- |
| **存储结构** | 键值+ROWID，叶子块双向链表 | 每个键值对应位图串（1bit=1行是否是该值） |
| **索引列基数** | **高基数列**（不同值>=1000）：主键、唯一键、订单ID、用户ID | **极低基数列**（不同值<=100最好<50）：性别、状态、省份 |
| **适用系统** | **OLTP高并发**：大量DML增删改 | **OLAP数据仓库**：极少DML，大量查询 |
| **锁粒度** | 行级锁（只锁修改的那行，高并发友好）| **段级锁**（修改一个键值对应位图串时锁上千行，高并发OLTP必挂）|
| **存储空间** | 大（存ROWID+键值） | 小（位图压缩，极省空间）|
| **NULL处理** | 单列普通B树不存NULL行 | 位图索引存NULL行，IS NULL查询能用到 |
| **AND/OR逻辑优化** | 无（需分别读索引再合并） | 位图直接位运算与/或/异或，极快 |
| **创建SQL** | CREATE INDEX ... | CREATE BITMAP INDEX ... |

> [!tip] OLTP+低基数列：不要位图，怎么办？
> 订单status列10个不同值，但WHERE status='NEW'查询很常用，OLTP不能建位图。**可以建普通B树索引**！即使区分度低，如果status='NEW'只占总行数<20%，B树索引还是比FTS快（INDEX RANGE SCAN跳转到对应叶子块，不用扫全表）。区分度低不是B树的问题，OLTP安全第一。

## 6.3.2 序列（Sequence）：自增主键生成器

> [!definition] 序列（Sequence）
> Oracle中独立的数据库对象，用于生成**连续不重复（默认）的整数序列**，是OLTP系统中自动生成主键ID的标准方式（12c+新增IDENTITY列其实是序列的语法糖）。序列和表是独立对象，一个序列可被多表多用户共用，也可以1表1序列。

### 1. CREATE SEQUENCE语法 + 生产参数

```sql
CREATE SEQUENCE hr.order_id_seq
  START WITH 1000000              -- 起始值（默认1，建议从一个大值开始方便历史数据导入）
  INCREMENT BY 1                  -- 步进值（默认1，正数递增，负数递减）
  MINVALUE 1                      -- 最小值（默认NOMINVALUE=1递增/-10^26递减）
  MAXVALUE 999999999999           -- 最大值（NOMAXVALUE递增默认10^27）
  NOCYCLE                         -- ★★★默认NOCYCLE：达到MAXVALUE后NEXTVAL报错ORA-08004（主键不允许重复！选NOCYCLE）
  -- CYCLE                        -- 达到MAXVALUE循环回MINVALUE重新发（仅适用于流水号用完允许重复的场景，绝不能做主键！）
  CACHE 20                        -- ★缓存20个序列值到SGA内存，分配极快（默认20，生产高并发建议CACHE 100~1000）
  -- NOCACHE                      -- 不缓存，每次NEXTVAL更新数据字典行（极慢，高并发下SEQ$锁竞争严重），生产严禁NOCACHE
  ORDER                          -- ★RAC集群想要严格按提交顺序发号（ORDER保证顺序，代价略大），单实例NOORDER默认即可
  ;
```

> [!warning] CACHE与RAC的注意事项
> - **CACHE值小（如默认20）+高并发**：会产生大量`enq: SQ - contention`锁争用（序列缓存耗尽要去字典表SEQ$再取20个，期间锁）。生产高并发每秒100+请求的序列建议CACHE=1000，1000个内存缓存基本不会锁冲突。
> - **RAC集群默认NOORDER**：每个节点独立缓存各自一段范围的序列（节点1 1~100，节点2 101~200），所以ID不是严格按用户提交时间顺序。如果业务要求严格按时间序（如金融订单号），加ORDER参数（代价是每次取序列号要全局同步，性能略低）。

### 2. 序列使用SQL

```sql
-- ========== 取序列值（伪列NEXTVAL / CURRVAL）==========
-- NEXTVAL：取下一个值（唯一不重复，每次调用序列+1）
SELECT hr.order_id_seq.NEXTVAL FROM DUAL;
-- CURRVAL：取当前会话最近一次NEXTVAL的值（不推进序列，不会重复取）
SELECT hr.order_id_seq.CURRVAL FROM DUAL;
-- 注意：新会话必须先NEXTVAL一次才能用CURRVAL，否则ORA-08002

-- ========== 作为主键插入（最常用场景）==========
INSERT INTO hr.orders (order_id, user_id, amount, create_date)
VALUES (hr.order_id_seq.NEXTVAL, 12345, 99.99, SYSDATE);

-- ========== 12c+ IDENTITY列（语法糖，不用单独建序列）==========
CREATE TABLE hr.products (
  product_id NUMBER(10)
    GENERATED ALWAYS AS IDENTITY (START WITH 1 INCREMENT BY 1 NOCACHE NOCYCLE),
  product_name VARCHAR2(100) NOT NULL
);
-- 内部Oracle自动创建一个关联序列，插入不用写product_id，自动填：
INSERT INTO hr.products (product_name) VALUES ('iPhone 15');   -- product_id自动填1,2,3...

-- ========== 序列维护 ==========
-- 改序列参数（不能改START WITH，想要改只能DROP重建）
ALTER SEQUENCE hr.order_id_seq
  MAXVALUE 99999999999999
  CACHE 1000
  CYCLE;   -- 不建议主键CYCLE！
-- 序列当前值设到100000（NEXTVAL直接跳到100000）
ALTER SEQUENCE hr.order_id_seq INCREMENT BY 900000;  -- 假设当前100000，要跳到1000000：先INCREMENT BY差值
SELECT hr.order_id_seq.NEXTVAL FROM DUAL;            -- 取一次值：跳到1000000
ALTER SEQUENCE hr.order_id_seq INCREMENT BY 1;        -- 再改回INCREMENT 1

-- 删除序列
DROP SEQUENCE hr.order_id_seq;
```

### 3. 查询序列字典

```sql
-- DBA_SEQUENCES：所有序列定义
SELECT sequence_owner, sequence_name, min_value, max_value, increment_by,
       cycle_flag, order_flag, cache_size, last_number
  FROM dba_sequences
 WHERE sequence_owner = 'HR';
-- LAST_NUMBER = 磁盘SEQ$数据字典中存的下一个CACHE边界值（不是当前最后分配的值）
-- 有CACHE时LAST_NUMBER通常比实际用掉的最后值大CACHE大小，属于正常
```

## 6.3.3 同义词（Synonym）：别名机制

> [!definition] 同义词（Synonym）
> 数据库对象（表/视图/序列/存储过程/函数/同义词/DB链等）的**别名（Alias）**。主要用途：① 简化访问路径（不用写长Schema前缀）；② 应用代码中不写死Schema名/DBLink名，切换环境时只改同义词不用改代码；③ 权限控制（GRANT同义词的权限=底层对象权限）。

### 1. 两类同义词：PRIVATE vs PUBLIC

| 类型 | 创建语法 | 归属 | 访问方式 | 可见范围 | 生产适用场景 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| **PRIVATE（私有/用户同义词）** | CREATE SYNONYM | 归属某个具体用户/用户Schema | 直接用同义词名 | 只在该用户Schema内可见（其他用户访问要写owner.synonym） | 应用连接账户访问业务Schema对象：建别名 |
| **PUBLIC（公有同义词）** | CREATE **PUBLIC** SYNONYM | 归属PUBLIC用户，所有用户共享 | 所有用户**直接使用同义词名**（不用加前缀） | 全库所有用户都可见 | 通用系统包/常用视图/历史遗留系统 |

```sql
-- ===== 私有同义词：应用用户APP_USER访问HR Schema的EMPLOYEES表 =====
-- 先给权限（同义词不能代替权限，必须GRANT对象权限）：
CONNECT / AS SYSDBA
GRANT SELECT, INSERT, UPDATE, DELETE ON hr.employees TO app_user;
CONNECT app_user/app_password
CREATE SYNONYM employees FOR hr.employees;     -- 建别名employees=hr.employees
SELECT * FROM employees WHERE department_id = 10;   -- 直接用，不用写hr.employees前缀

-- ===== PUBLIC同义词：给所有用户访问DBA_视图的别名（Oracle系统有大量默认PUBLIC同义词）=====
CONNECT / AS SYSDBA
GRANT SELECT ON hr.departments TO PUBLIC;     -- 给所有人权限（慎选！PUBLIC就是所有用户）
CREATE PUBLIC SYNONYM departments FOR hr.departments;
-- 之后所有用户直接用departments：
CONNECT scott/tiger
SELECT * FROM departments;   -- 不用任何前缀，所有用户都能访问

-- ===== 同义词跨库（通过DBLink访问远程库）=====
CREATE PUBLIC SYNONYM remote_orders FOR app.orders@prod_dblink;   -- @后是DBLink名
SELECT * FROM remote_orders WHERE create_date > SYSDATE-30;   -- 就像访问本地表一样

-- ===== 查看/替换/删除同义词 =====
CREATE OR REPLACE SYNONYM employees FOR hr.employees_bak;   -- 替换同义词指向（上线切换神器：代码不用改，只改同义词指向从旧表切到新表）
DROP SYNONYM employees;            -- 删私有同义词
DROP PUBLIC SYNONYM departments;   -- 删PUBLIC同义词需要DROP PUBLIC SYNONYM权限
```

> [!warning] 同义词不解决权限问题！
> 同义词只是个**指针/别名**，最终访问的还是同义词FOR指向的底层对象。没有底层对象权限，建了同义词也用不了：
> ```sql
> -- A建同义词EMP FOR HR.EMPLOYEES，但B没HR.EMPLOYEES的SELECT权限
> -- B用A.EMP：还是报ORA-01031权限不足！权限必须GRANT给真正执行的用户
> ```
> PUBLIC同义词尤其危险：GRANT ... TO PUBLIC + PUBLIC同义词 = 全库任何用户都能访问该对象，生产慎用！

### 2. 查询同义词字典

```sql
-- DBA_SYNONYMS：所有同义词定义
SELECT owner, synonym_name, table_owner, table_name, db_link
  FROM dba_synonyms
 WHERE (synonym_name = 'EMPLOYEES' OR table_name = 'EMPLOYEES')
 ORDER BY owner, synonym_name;
-- OWNER=PUBLIC的是公有同义词
-- DB_LINK列有值=跨库同义词（通过远程DBLink）
```

## 6.3.4 视图（View）：逻辑虚表与权限控制

> [!definition] 视图（View）
> 存储在数据字典中的一条**预定义SELECT查询语句**，是一张"虚表"——本身不存数据（除物化视图Materialized View外），查询视图时Oracle会把视图定义的SQL合并进用户SQL再执行。核心用途：① 简化复杂SQL（把子查询封装成视图）；② 权限控制：只给用户视图权限不给基表权限，隐藏表中敏感列。

### 1. CREATE VIEW语法 + 安全选项

```sql
-- ===== 基础视图：封装一个复杂JOIN供报表用户用 =====
CREATE VIEW hr.emp_dept_v
(emp_id, emp_name, job_id, hire_date, dept_id, dept_name, location)   -- 自定义列名（可选）
BEQUEATH DEFINER                                  -- ★BEQUEATH定义者权限（默认，视图执行时用视图OWNER的权限）
AS
  SELECT e.employee_id, e.last_name, e.job_id, e.hire_date,
         e.department_id, d.department_name, l.city
    FROM hr.employees e
    LEFT JOIN hr.departments d ON e.department_id = d.department_id
    LEFT JOIN hr.locations l   ON d.location_id = l.location_id
WITH READ ONLY;                                   -- ★只读视图：禁止任何DML INSERT/UPDATE/DELETE，防止通过视图改基表
-- WITH CHECK OPTION CONSTRAINT emp_dept_v_check;   -- ★★另一类约束：允许DML，但WHERE条件过滤出来的行才能被DML（后面详解）
```

> [!note] BEQUEATH DEFINER vs CURRENT_USER（12c+新选项）
> - **DEFINER（默认）**：执行视图时，对象权限检查用**视图定义者（OWNER）**的权限。例：HR建视图EMP_V给SCOTT，HR有EMPLOYEES的SELECT权限，SCOTT没有EMPLOYEES权限，但SCOTT可以SELECT EMP_V——视图权限继承自定义者HR，这就是为什么视图能做权限隔离。
> - **CURRENT_USER（12c+，也叫调用者权限视图）**：执行时用当前会话用户权限，等价于用户自己写视图SQL。通常用于PL/SQL包AUTHID CURRENT_USER场景，普通视图极少用。

### 2. WITH CHECK OPTION：保护WHERE过滤出的行不被UPDATE出范围

```sql
-- 场景：销售部门的经理只能看+修改自己部门（dept_id=30）的员工，不能把员工修改到其他部门
CREATE VIEW hr.sales_staff_v
BEQUEATH DEFINER
AS
  SELECT employee_id, last_name, job_id, salary, department_id
    FROM hr.employees
   WHERE department_id = 30         -- 只暴露销售部30号的员工
WITH CHECK OPTION CONSTRAINT sales_staff_v_ck;   -- ★★★ CHECK OPTION约束

-- 允许：修改销售部员工自己的工资（行仍在dept_id=30范围内）
UPDATE hr.sales_staff_v SET salary = salary * 1.1 WHERE employee_id = 7499;
-- ❌ 禁止：如果要把某员工UPDATE dept_id=40（调到其他部门）→ 会违反CHECK OPTION约束，直接报错ORA-01402: view WITH CHECK OPTION where-clause violation
UPDATE hr.sales_staff_v SET department_id = 40 WHERE employee_id = 7499;
-- ❌ 禁止：INSERT一条dept_id=50的员工（不在30范围，也会被CHECK OPTION拒）
INSERT INTO hr.sales_staff_v VALUES (9999, 'New', 'SA_REP', 5000, 50);
```

### 3. 视图DML（INSERT/UPDATE/DELETE）的限制条件（什么时候视图可写？）

不是所有视图都能DML，简单单表视图一般可写；**键保留表（Key-Preserved Table）** 是基础：

| 视图类型 | 可否DML | 条件 |
| ---- | ---- | ---- |
| 单表简单视图（SELECT * FROM t WHERE ...）| ✅ 完全可写 | WITH READ ONLY除外 |
| 多表JOIN视图 | ⚠️ 只能DML键保留表一侧（PRIMARY KEY未被重复的那侧） | 单表UPDATE可以，INSERT一般不支持（除非INSTEAD OF触发器）|
| 带聚合函数（SUM/AVG/COUNT/GROUP BY/DISTINCT） | ❌ 不可DML | Oracle不知道要改哪一行基表 |
| 带UNION/UNION ALL集合运算 | ❌ 不可DML | 同上 |
| 带ROWNUM/序列NEXTVAL伪列 | ❌ 不可DML | 伪列不对应基表列 |

> [!tip] 复杂视图想做DML → 建**INSTEAD OF触发器**
> Oracle对视图DML会先触发INSTEAD OF触发器，你在触发器里写逻辑自己解析要怎么更新基表：
> ```sql
> CREATE TRIGGER hr.emp_dept_v_io_trg
> INSTEAD OF UPDATE ON hr.emp_dept_v
> FOR EACH ROW
> BEGIN
>   UPDATE hr.employees SET last_name = :NEW.last_name, salary = :NEW.salary
>    WHERE employee_id = :OLD.emp_id;
>   UPDATE hr.departments SET department_name = :NEW.dept_name
>    WHERE department_id = :OLD.dept_id;
> END;
> /
> ```

### 4. 视图查询与删除

```sql
-- DBA_VIEWS：视图定义（TEXT存长文本查询语句）
SELECT owner, view_name, text_length, bequeath, read_only, constraint_name  -- READ_ONLY='Y'是只读视图
  FROM dba_views WHERE owner = 'HR';
-- DBA_UPDATABLE_COLUMNS：哪些视图列允许UPDATE/INSERT/DELETE
SELECT owner, table_name, column_name, updatable, insertable, deletable
  FROM dba_updatable_columns
 WHERE owner='HR' AND table_name='SALES_STAFF_V';

-- 删除/替换视图
CREATE OR REPLACE VIEW hr.emp_v AS ... ;   -- 替换视图定义（不影响已授出的对象权限）
DROP VIEW hr.emp_v;
```

本节详解了Oracle索引、序列、同义词、视图四大数据库对象。索引部分详述了B树（默认OLTP高基数高并发用）、位图（OLAP低基数+极少DML）、函数基（WHERE列上带函数场景）、反向键（RAC防热块冲突）、域索引（全文/空间）五大类的适用场景与创建维护语法，重点强调了**FOREIGN KEY必须建索引**、**大表CREATE INDEX加ONLINE**、**OLTP不能建位图索引**三大生产坑。序列部分详解了CACHE/NOCYCLE/ORDER参数（CACHE 1000高并发，主键严禁CYCLE）。同义词分PUBLIC/PRIVATE两类，核心是不能用同义词代替权限GRANT。视图部分讲了BEQUEATH DEFINER权限隔离、WITH CHECK OPTION保护行范围、复杂视图INSTEAD OF触发器等要点。配合DBA_INDEXES/DBA_SEQUENCES/DBA_SYNONYMS/DBA_VIEWS形成完整的对象运维知识。
