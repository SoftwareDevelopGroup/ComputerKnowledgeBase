# 6.2 数据表、约束管理

本节解决的核心问题是：**如何在Oracle中创建一张满足生产规范的表？5类约束如何创建与管理？TRUNCATE与DELETE的本质区别？Oracle专有数据类型有哪些坑？** 表是数据库对象的核心，规范的表结构设计是性能、可维护性、可扩展性的基础。

## 6.2.1 CREATE TABLE完整语法（Oracle 19c）

> [!definition] CREATE TABLE语法（常用子句简化版）
> ```sql
> CREATE TABLE [schema.]表名
>   (列1 数据类型 [DEFAULT 默认值] [约束子句1] [约束子句2...],
>    列2 数据类型 [DEFAULT 默认值] [列级约束...],
>    ...,
>    [CONSTRAINT 约束名 PRIMARY KEY/UNIQUE/FOREIGN KEY/CHECK (条件) 表级约束...]
>   )
>   [ORGANIZATION HEAP            -- ★默认堆表，最常用
>    | ORGANIZATION INDEX          -- 索引组织表IOT（主键访问极快）
>    | ORGANIZATION EXTERNAL ...   -- 外部表（OS文本/CSV文件映射）
>    | CLUSTER 簇名(簇键1,簇键2...) ]
>   [PCTFREE 整数]                 -- 块预留%空闲（UPDATE膨胀用，ASSM下默认10）
>   [PCTUSED 整数]                 -- 块已用%阈值（MSSM下才用，ASSM下忽略）
>   [INITRANS 整数]                -- 块内初始事务槽数（默认1，高并发UPDATE的表设2~4）
>   [MAXTRANS 整数]                -- 最大事务槽数（10g+已自动255，不用设）
>   [TABLESPACE 表空间名]          -- ★★ 必写！否则默认建到SYSTEM/USERS表空间
>   [STORAGE (INITIAL 整数 NEXT 整数 MINEXTENTS 整数 MAXEXTENTS UNLIMITED PCTINCREASE 0)]  -- LMT下几乎不用
>   [COMPRESS { NOCOMPRESS | BASIC | OLTP | QUERY {LOW|HIGH} | ARCHIVE {LOW|HIGH} }]
>   [LOGGING | NOLOGGING]
>   [ENABLE ROW MOVEMENT]          -- 允许行跨分区迁移（分区表UPDATE分区键时用）/Flashback Table必需
>   [PARALLEL 整数 | NOPARALLEL]
>   [PARTITION BY ...];            -- 见6.4分区表节
> ```

### 1. 完整生产建表SQL示例（19c）

```sql
CREATE TABLE hr.employees (
  employee_id    NUMBER(6,0)
    CONSTRAINT emp_emp_id_pk PRIMARY KEY
    USING INDEX TABLESPACE hr_indx PCTFREE 10 STORAGE(INITIAL 64K NEXT 64K),
  first_name     VARCHAR2(20),
  last_name      VARCHAR2(25)
    CONSTRAINT emp_last_name_nn NOT NULL,
  email          VARCHAR2(25)
    CONSTRAINT emp_email_nn NOT NULL
    CONSTRAINT emp_email_uk UNIQUE,
  phone_number   VARCHAR2(20),
  hire_date      DATE
    DEFAULT SYSDATE
    CONSTRAINT emp_hire_date_nn NOT NULL,
  job_id         VARCHAR2(10)
    CONSTRAINT emp_job_nn NOT NULL,
  salary         NUMBER(8,2)
    DEFAULT 0
    CONSTRAINT emp_salary_min CHECK (salary >= 0),
  commission_pct NUMBER(2,2),
  manager_id     NUMBER(6,0)
    CONSTRAINT emp_manager_fk REFERENCES hr.employees(employee_id)
    ON DELETE SET NULL,                 -- 经理被删，下属manager_id置NULL
  department_id  NUMBER(4,0)
    CONSTRAINT emp_dept_fk REFERENCES hr.departments(department_id)
    ON DELETE SET NULL,
  create_time    TIMESTAMP(6) DEFAULT SYSTIMESTAMP,
  update_time    TIMESTAMP(6),
  is_deleted     CHAR(1) DEFAULT 'N'
    CONSTRAINT emp_is_deleted_ck CHECK (is_deleted IN ('Y','N'))
)
ORGANIZATION HEAP
PCTFREE 20 INITRANS 4                       -- 频繁UPDATE的表，PCTFREE=20留足膨胀空间，INITRANS=4防事务槽等待
TABLESPACE hr_data
STORAGE (INITIAL 64K NEXT 64K MINEXTENTS 1 MAXEXTENTS UNLIMITED PCTINCREASE 0)
COMPRESS FOR OLTP                              -- 12c+ OLTP压缩，1.5~3倍空间节省
LOGGING
ENABLE ROW MOVEMENT
PARALLEL 4
NOCACHE;
```

### 2. 关键表级参数说明

| 参数 | 作用 | 典型值 | 生产使用建议 |
| ---- | ---- | ---- | ---- |
| **TABLESPACE** | 所属永久表空间 | `hr_data`/`app_data_ts` | ★必须显式写！否则落到SYSTEM/USERS（CREATE USER默认表空间），影响数据组织与备份恢复粒度 |
| **ORGANIZATION HEAP** | 普通堆表（默认），数据按插入顺序无序存放 | 绝大多数场景 | 99%场景用默认HEAP |
| **ORGANIZATION INDEX（IOT）** | 索引组织表，整行数据存在主键B树索引叶子块中 | 主键访问极多、列少的小表（如配置表、字典表）| 主键访问占90%+、不需要二级索引时用；否则二级索引维护代价大 |
| **PCTFREE** | 每个数据块预留的空闲百分比，用于UPDATE行膨胀占用 | 默认10；频繁UPDATE表20~30；INSERT_ONLY表1~5 | 高并发UPDATE的订单表必须>=20；日志/历史表只用1省空间 |
| **INITRANS** | 块中初始事务槽数（每个并发修改块中不同行的事务需要独立事务槽） | 默认1；高并发UPDATE表2~4 | 死锁排查发现ITL等待（enq: TX - allocate ITL entry）时必须调大到4~8 |
| **COMPRESS FOR OLTP** | 12c+ OLTP高级行内压缩（算法先进对性能影响极小） | 所有非分区永久表必开 | 空间节省1.5~3倍；读写性能影响<5%；19c默认所有新建表开启（OEM/DBCA默认选项） |
| **ENABLE ROW MOVEMENT** | 允许Oracle物理移动行的ROWID（UPDATE分区键跨分区、Flashback Table需要） | 默认DISABLE，分区表开+闪回需求开 | 分区表、经常闪回回滚的业务表必开；普通表不开也行（开了不影响性能） |

## 6.2.2 Oracle专有数据类型与注意事项

> [!note] Oracle专有数据类型坑（MySQL/SQLServer用户必记！）
> 以下是Oracle特有的行为，其他数据库默认行为不同，最容易踩坑：

### 1. 核心数据类型对比表

| Oracle数据类型 | 含义/范围 | 对应其他数据库 | Oracle专有特性（坑！） |
| ---- | ---- | ---- | ---- |
| **CHAR(n)** | 定长字符，n字节（AL32UTF8中文3字节）；默认长度1 | CHAR（同） | 右边自动补空格填满n字节；比较时会忽略右侧空格；列短数据浪费空间 |
| **VARCHAR2(n)** | 变长字符，n最大4000字节（开启MAX_STRING_SIZE=EXTENDED后32767字节12c+） | VARCHAR(n)（MySQL等） | ★坑1：**空字符串'' = NULL**！`WHERE name = ''`查不到任何行，因为''等于NULL，等值比较永远FALSE（SQL Server中''不是NULL）<br/>★坑2：只存字节数不存Unicode字符数，AL32UTF8中文3字节，存100个中文要VARCHAR2(300) |
| **NUMBER(p,s)** | 可变长十进制数（内部1~22字节）；p总位数1~38，s小数位数；s负为左0截断 | DECIMAL/INT/FLOAT混合 | ★坑：Oracle没有原生INT/BIGINT/FLOAT/DOUBLE，都是NUMBER的别名；NUMBER(6)=整数6位；NUMBER(10,2)=金额；**NUMBER类型无精度损失，金融系统首选**（相比二进制FLOAT不会有0.1+0.2不等于0.3的问题） |
| **DATE** | 日期+时间（世纪/年/月/日/时/分/秒），无毫秒；公元前4712到公元后9999 | DATETIME + DATE混合 | ★坑：`WHERE dt = DATE'2024-01-01'`查不到当天08:00的数据！因为DATE'2024-01-01'等价于`TO_DATE('2024-01-01 00:00:00','YYYY-MM-DD HH24:MI:SS')`，必须`TRUNC(dt) = DATE'...'`或`BETWEEN DATE'...' AND DATE'...'+1-1/86400'` |
| **TIMESTAMP(n)** | 时间戳，n小数秒位数0~9（默认6=微秒）；TIMESTAMP(3)=毫秒精度 | DATETIME/DATETIME2 | 比DATE精确；但默认NLS_DATE_FORMAT不含小数秒，直接查会丢毫秒；推荐用于高并发事务排序 |
| **TIMESTAMP WITH TIME ZONE** | 带时区的时间戳（TSTZ），内部存UTC时间，显示时转会话时区 | DATETIMEOFFSET（SQL Server） | 跨国系统必须用；避免跨时区业务时间错乱 |
| **CLOB** | 字符大对象，最大4G×DB_BLOCK_SIZE | TEXT/VARCHAR(MAX) | 大文本存储；不能在GROUP BY/ORDER BY/DISTINCT直接用；ASSM表空间才支持SecureFile LOB（推荐，压缩+加密+去重） |
| **BLOB** | 二进制大对象，最大4G×块大小 | IMAGE/VARBINARY(MAX) | 图片、附件、PDF存储；同上SecureFile LOB |
| **RAW(n)** | 二进制字节串，最大2000字节 | VARBINARY | 小量二进制（如128位MD5、UUID）；不做字符集转换直接传字节 |
| **LONG / LONG RAW** | 老数据类型，最大2G | 已淘汰 | ❌ 不要用！1对表只能有1个LONG列；不能作为子查询/WHERE条件；迁移到CLOB/BLOB |
| **ROWID** | Oracle内部伪列（物理地址），10字节base64编码；唯一标识一行物理位置 | 无对应类型，内部使用 | 最快访问一行的方式；FLASHBACK TABLE查询返回旧ROWID |

> [!warning] 空字符串=NULL：Oracle最经典陷阱！
> ```sql
> -- MySQL/SQL Server：''和NULL是两个东西
> -- Oracle：''就是NULL
> INSERT INTO test(col) VALUES ('');          -- 存进去是NULL
> SELECT * FROM test WHERE col = '';          -- ❌ 永远0行！因为NULL = ''也是NULL，NULL等值比较=UNKNOWN，WHERE只取TRUE
> SELECT * FROM test WHERE col IS NULL;       -- ✅ 才可以查到！
> SELECT * FROM test WHERE NVL(col,'X') = ''; -- 另一种写法
> ```

### 2. 常用类型选择建议

| 场景 | 推荐类型 | 不推荐 |
| ---- | ---- | ---- |
| 身份证号/手机号/银行卡号（数字但不需要计算） | VARCHAR2 | NUMBER（前导0会丢，18位身份证号可能溢出） |
| 姓名/地址/标题 | VARCHAR2(80~200) | CHAR |
| 金额/价格/数量 | NUMBER(18,2) / NUMBER(10) | FLOAT/BINARY_DOUBLE（精度损失） |
| 创建时间/修改时间 | DATE（够了）/ TIMESTAMP(6) | VARCHAR2存字符串（无法索引范围扫描、无法计算间隔） |
| 跨国业务下单时间 | TIMESTAMP WITH TIME ZONE | DATE（时区错乱） |
| 文章正文/协议文本 | CLOB（SecureFile） | VARCHAR2(4000)（截断） |
| 附件/图片 | BLOB（SecureFile + 文件表空间） | 存文件路径（文件权限管理、备份一致性复杂） |
| UUID/MD5 | RAW(16) / CHAR(32) | VARCHAR2大小写不一致问题 |

## 6.2.3 5类约束详解（★★★必考）

> [!definition] 约束（Constraint）
> 对表中列/表级的数据合法性强制校验规则，防止不符合业务规则的脏数据写入。Oracle共5类约束：PRIMARY KEY、FOREIGN KEY、UNIQUE、NOT NULL、CHECK。

### 1. 5类约束对比总表

| 约束类型 | 作用 | 列级/表级 | 每表数量 | 是否允许NULL | 是否自动建索引 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| **NOT NULL** | 该列不允许存NULL值（必须写值） | 只能列级 | 可以多列 | ❌ 强制非空 | 否 |
| **UNIQUE**（唯一键） | 该列或列组合值不能重复，允许多行NULL（NULL≠NULL） | 都可以 | 可以多个 | ✅ 允许NULL | ✅ **是**，创建时自动建唯一B树索引（列名相同USING INDEX指定表空间） |
| **PRIMARY KEY**（主键）| 唯一标识每一行 = NOT NULL + UNIQUE | 都可以 | **1个表只能1个主键**（可以多列组合复合主键） | ❌ 所有主键列强制非空 | ✅ **是**，自动建唯一B树索引（USING INDEX指定表空间/参数） |
| **FOREIGN KEY**（外键） | 该列值必须在主表被引用列中存在（参照完整性）；或NULL | 都可以 | 可以多个（如订单表有用户ID外键+商品ID外键+部门ID外键） | ✅ 允许NULL（除非列上另加NOT NULL） | ❌ **不自动建**！生产强烈建议手动在外键列上建索引（防LOCK TABLE、防止级联删除性能差） |
| **CHECK** | 列值必须满足布尔条件（简单校验） | 都可以 | 可以多个列/表级CHECK | ✅ 满足CHECK即可，NULL=UNKNOWN允许（除非列加NOT NULL） | 否 |

### 2. 约束创建的3种方式

```sql
-- ===== 方式1：CREATE TABLE时列级内联（写在列定义后面）=====
CREATE TABLE t_demo1 (
  id NUMBER(10) CONSTRAINT demo1_id_pk PRIMARY KEY,   -- 列级主键，命名建议<表缩写>_<列>_<约束类型>
  name VARCHAR2(50) CONSTRAINT demo1_name_nn NOT NULL,
  email VARCHAR2(100) CONSTRAINT demo1_email_uk UNIQUE,
  dept_id NUMBER(4) CONSTRAINT demo1_dept_fk REFERENCES t_dept(dept_id)
);

-- ===== 方式2：CREATE TABLE时表级约束（单独CONSTRAINT子句，复合约束必须用表级）=====
CREATE TABLE t_demo2 (
  order_id NUMBER(18),
  item_id NUMBER(10),
  user_id NUMBER(10) NOT NULL,
  status VARCHAR2(10),
  amount NUMBER(18,2),
  -- 复合主键（两列共同做主键，只能表级写）
  CONSTRAINT demo2_order_item_pk PRIMARY KEY (order_id, item_id)
    USING INDEX TABLESPACE demo_indx PCTFREE 10,
  -- 复合UNIQUE（用户+状态的组合唯一）
  CONSTRAINT demo2_user_status_uk UNIQUE (user_id, status),
  -- 外键
  CONSTRAINT demo2_user_fk FOREIGN KEY (user_id) REFERENCES t_user(user_id)
    ON DELETE CASCADE,     -- 主表删用户时，级联自动删除此表中该用户的所有行
  -- CHECK
  CONSTRAINT demo2_amount_ck CHECK (amount > 0),
  CONSTRAINT demo2_status_ck CHECK (status IN ('NEW','PAID','SHIPPED','CANCEL'))
);

-- ===== 方式3：ALTER TABLE ADD CONSTRAINT（建表后追加，生产推荐，DDL分步骤）=====
CREATE TABLE t_demo3 (
  id NUMBER(10),
  name VARCHAR2(50),
  amount NUMBER(18,2)
);
ALTER TABLE t_demo3 ADD CONSTRAINT demo3_pk PRIMARY KEY (id)
  USING INDEX TABLESPACE demo_indx;
ALTER TABLE t_demo3 ADD CONSTRAINT demo3_amount_ck CHECK (amount > 0);
ALTER TABLE t_demo3 MODIFY name CONSTRAINT demo3_name_nn NOT NULL;  -- NOT NULL用MODIFY
```

> [!tip] 生产约束命名规范（极其重要！约束没有默认名时Oracle会给SYS_C0012345这种乱码名，报错无法定位）
> `<表缩写>_<列名/描述>_<约束类型后缀>`
> 后缀：_PK=PRIMARY KEY，_UK=UNIQUE，_NN=NOT NULL，_CK=CHECK，_FK=FOREIGN KEY
> 例：ORD_ORDER_ID_PK、ORD_USER_ID_FK、ORD_STATUS_CK、ORD_EMAIL_UK、ORD_CREATE_TIME_NN

### 3. 外键ON DELETE动作

```sql
-- 三种ON DELETE子句（缺省是NO ACTION）：
CREATE TABLE t_order (
  ...,
  user_id NUMBER(10) CONSTRAINT ord_user_fk REFERENCES t_user(id)
    ON DELETE NO ACTION -- ★默认：删除主表用户时，如果该用户还有订单就报错ORA-02292: integrity constraint violated - child record found，禁止删
);
CREATE TABLE t_log (
  ...,
  user_id NUMBER(10) CONSTRAINT log_user_fk REFERENCES t_user(id)
    ON DELETE CASCADE  -- 删除主表用户时，自动级联删除t_log中该用户的所有日志行（小心！日志可能不应该被自动删）
);
CREATE TABLE t_employee (
  ...,
  manager_id NUMBER(10) CONSTRAINT emp_mgr_fk REFERENCES t_employee(id)
    ON DELETE SET NULL -- 删除经理行时，该经理下属的manager_id自动UPDATE为NULL
);
```

> [!danger] 外键未建索引的经典死锁/锁表陷阱！
> 子表的FOREIGN KEY列如果**没有手动建B树索引**，当删除/更新主表主键时：
> 1. Oracle需要扫描子表全表找所有引用该主表行的外键行，判断能否删除 → 全表扫描LOCK子表所有行，锁粒度从行级飙升到表级，高并发时大量会话等待。
> 2. 级联删除ON DELETE CASCADE、ON DELETE SET NULL时没有外键索引，性能极差（子表100万行要扫100万次）。
> 3. 经典死锁场景：两个会话删除主表不同行，子表全表扫描互相等待导致死锁。
>
> **生产铁律：所有FOREIGN KEY列必须手动建索引！**
> ```sql
> -- 上面例子建完外键，立刻建索引：
> CREATE INDEX demo2_user_id_idx ON t_demo2(user_id) TABLESPACE demo_indx;
> CREATE INDEX ord_user_id_idx ON t_order(user_id) TABLESPACE demo_indx;
> ```

### 4. 约束的4种状态（ENABLE VALIDATE等）

| 约束状态 | 含义 | 典型使用场景 |
| ---- | ---- | ---- |
| **ENABLE VALIDATE**（默认） | ✅ 新插入/修改的行必须满足约束 ✅ 表中现有所有行也必须满足约束 | 生产正常状态，表中无脏数据 |
| **ENABLE NOVALIDATE** | ✅ 新DML要满足约束 ❌ 历史脏数据不校验，允许存在 | 数据仓库迁移：先导入历史脏数据，再ENABLE NOVALIDATE约束，阻止未来再进脏数据；配合索引NOPARALLEL创建后再VALIDATE |
| **DISABLE NOVALIDATE** | ❌ 新DML不校验约束 ❌ 历史数据也不校验 | 临时批量加载大量数据时，先DISABLE约束加速加载，加载完再ENABLE（大表加约束NOVALIDATE再VALIDATE比直接ENABLE快） |
| **DISABLE VALIDATE** | ❌ 新DML不校验约束（其实会锁表，DML直接禁止任何修改！）✅ 历史数据满足约束 | 数据仓库唯一性约束使用：索引不用UNIQUE（空间省），约束DISABLE VALIDATE照样保证唯一，且修改操作被禁止，适合历史只读分区表 |

```sql
-- 约束状态切换语法
ALTER TABLE t_order DISABLE CONSTRAINT ord_status_ck;   -- 临时关约束（批量导入时）
ALTER TABLE t_order ENABLE NOVALIDATE CONSTRAINT ord_status_ck;
ALTER TABLE t_order MODIFY CONSTRAINT ord_status_ck RELY DISABLE NOVALIDATE;   -- RELY告诉优化器：约束逻辑上是满足的，查询优化时当它有效用
```

### 5. 可延迟约束（DEFERRABLE，事务提交时才检查）

默认约束是**每条SQL语句执行完立即检查**（INITIALLY IMMEDIATE）。但复杂业务逻辑中，比如"先插入子订单再插入主订单"的逆序操作，需要等整个事务结束才校验完整性，用可延迟约束：

```sql
CREATE TABLE t_ord (
  ord_id NUMBER(10) CONSTRAINT ord_pk PRIMARY KEY,
  total_amount NUMBER(18,2),
  pay_amount NUMBER(18,2),
  -- CHECK：支付金额必须<=订单总额；业务中先插pay_amount=0后UPDATE为正确值，中间违反约束，延迟到提交时再查
  CONSTRAINT ord_pay_le_total_ck CHECK (pay_amount <= total_amount)
    DEFERRABLE INITIALLY DEFERRED     -- 延迟到COMMIT时检查
);
-- INITIALLY IMMEDIATE：默认每条SQL检查，但可以事务内SET CONSTRAINT ... DEFERRED临时改
-- INITIALLY DEFERRED：默认整个事务提交时检查

-- 事务内临时切换（用于INITIALLY IMMEDIATE的约束）
SET CONSTRAINT ord_pay_le_total_ck DEFERRED;  -- 本事务剩余部分延迟到提交查
SET CONSTRAINT ALL DEFERRED;
```

## 6.2.4 ALTER TABLE表结构修改

```sql
-- ===== 列修改 =====
ALTER TABLE t_emp ADD (mobile VARCHAR2(20) DEFAULT 'N/A' NOT NULL);   -- 加列（生产加列尽量带DEFAULT+NOT NULL才会在线立即加11g+，不然会锁表更新历史行）
ALTER TABLE t_emp MODIFY (email VARCHAR2(100));                      -- 改列长度/类型（类型改需清空列或用DBMS_REDEFINITION在线重定义）
ALTER TABLE t_emp DROP COLUMN salary;                                 -- 删除列
ALTER TABLE t_emp SET UNUSED COLUMN commission_pct;                   -- 标记列未使用（大表删除列极慢：逐行清，产生大量REDO；先SET UNUSED秒级完成，空闲时ALTER TABLE ... DROP UNUSED COLUMNS CHECKPOINT 256;）
ALTER TABLE t_emp RENAME COLUMN old_name TO new_name;                 -- 12c+ RENAME COLUMN

-- ===== 约束修改 =====
ALTER TABLE t_emp ADD CONSTRAINT ... PRIMARY KEY/UNIQUE/FOREIGN KEY/CHECK;
ALTER TABLE t_emp DROP CONSTRAINT emp_email_uk [CASCADE];             -- 删约束（PRIMARY KEY带CASCADE，删除同时删自动建的唯一索引+子表引用它的外键）
ALTER TABLE t_emp MODIFY CONSTRAINT ... ENABLE/DISABLE NOVALIDATE;

-- ===== 表级属性 =====
ALTER TABLE t_emp MOVE TABLESPACE new_ts;                              -- 迁移表到新表空间（会使所有索引UNUSABLE！MOVE完要REBUILD所有索引）
ALTER TABLE t_emp SHRINK SPACE COMPACT;                                -- 11g+ ASSM表空间：回收表高水位线下方的空块（DELETE大量行后用）
ALTER TABLE t_emp DEALLOCATE UNUSED KEEP 0;                           -- 释放段尾未用空间（高水位线以上）
ALTER TABLE t_emp RENAME TO t_employee_new;                            -- 重命名表
-- TRUNCATE分区见6.4节
```

> [!note] Oracle 11g+ 加列在线优化（极重要！）
> 当`ALTER TABLE ADD (col DEFAULT 'x' NOT NULL)`时，11g+不会逐行UPDATE所有行（锁表、大表几小时），而是把默认值存到数据字典中，查询时动态合并；秒级完成加列！
> 但如果加列**只有DEFAULT没有NOT NULL**，会回退为旧行为（全表UPDATE锁表），生产务必`DEFAULT + NOT NULL`成对写。

## 6.2.5 TRUNCATE TABLE vs DELETE FROM 终极对比（★★★必考）

| 对比维度 | DELETE FROM 表 [WHERE 条件] | TRUNCATE TABLE 表 [PARTITION(分区)] |
| ---- | ---- | ---- |
| **语言类型** | DML（数据操作语言） | DDL（数据定义语言），执行时**隐式COMMIT当前会话所有未提交事务**，执行完成不可ROLLBACK |
| **回滚性** | ✅ COMMIT之前ROLLBACK可撤销全部行 | ❌ 不可ROLLBACK，除非FLASHBACK TABLE（回收站）/RMAN备份恢复 |
| **执行速度** | 慢：逐行删除，每行产生**UNDO（回滚段）+ REDO（重做日志）**，大表DELETE 1亿行可能几小时+占满UNDOTBS | 极快：秒级完成，和数据量无关（1亿行也1秒）。不处理数据行，只在数据字典中把表/分区的段分配位图标记为"空闲"，TRUNCATE完HWM（高水位线）归零 |
| **DML触发器触发** | ✅ 逐行触发DELETE触发器（行级触发器每删一行触发一次） | ❌ **不触发任何DML触发器！** 有审计DELETE触发器的表用TRUNCATE会漏审计，必须额外记录日志 |
| **高水位线（HWM）** | ❌ 保留不变。DELETE 1亿行后，全表扫描FTS还是会扫HWM下的空块，性能和删前一样慢 | ✅ HWM重置到段起始位置。后续FTS全表扫描只需扫0行，速度极快 |
| **索引/段状态** | 索引叶子块还在，产生大量索引空块（碎片），后续INSERT可能变慢。需ALTER INDEX ... REBUILD/COALESCE整理碎片 | 所有关联索引、LOB段也同步TRUNCATE，索引段同步归零，无碎片最干净 |
| **WHERE条件（删部分行）** | ✅ `DELETE FROM emp WHERE deptno=10;`支持删部分行 | ❌ 只能TRUNCATE整表或整分区，不能加WHERE条件删部分行（需DELETE） |
| **引用外键约束** | 有子表引用本表且存在子行时：如果外键ON DELETE CASCADE会自动删子行；默认NO ACTION报ORA-02292 | 默认：子表有任何外键引用本表→TRUNCATE直接报错ORA-02266（即使子表是空的也报错），必须先DISABLE所有子表外键再TRUNCATE，12c+可`TRUNCATE TABLE 父表 CASCADE;`级联TRUNCATE所有子表（慎用！） |
| **所需权限** | 对象权限：GRANT DELETE ON schema.table TO user;（最小权限好控制） | 系统权限：需要DROP ANY TABLE或表Owner；相当于拥有DROP表的权限等级，极高风险权限不能随意授 |
| **闪回能力** | COMMIT前ROLLBACK；COMMIT后闪回查询FLASHBACK QUERY看旧数据 | 仅闪回表FLASHBACK TABLE TO BEFORE DROP；TRUNCATE不是DROP，回收站可能保留表结构但数据恢复依赖RMAN |
| **UNDOTBS影响** | 极大：产生大量UNDO回滚段，UNDOTBS 100%后快照过旧ORA-01555 | 几乎0 UNDO（只改数据字典，UNDO可忽略）|

```sql
-- TRUNCATE常用语法：
TRUNCATE TABLE hr.employees DROP STORAGE;    -- 默认：TRUNCATE后释放空闲EXTENT到表空间
TRUNCATE TABLE hr.employees REUSE STORAGE;   -- TRUNCATE后保留段空间给原表（频繁TRUNCATE的临时表用REUSE省反复分配开销）
TRUNCATE TABLE hr.employees CASCADE;         -- 12c+：级联TRUNCATE所有引用本表的子表（必须外键有ON DELETE CASCADE定义）
-- 分区表TRUNCATE见6.4节
```

> [!danger] TRUNCATE生产铁律！
> 1. **TRUNCATE前必须备份表**！`CREATE TABLE bak_20240101_emp AS SELECT * FROM hr.emp;` 或 RMAN备份。
> 2. 开发/测试环境发TRUNCATE生产命令前：**先确认连接的是哪个库！** `SELECT name FROM v$database;` + `SELECT instance_name FROM v$instance;`，避免连错库。
> 3. **绝对不要在SYSTEM/SYSAUX表空间下的系统表TRUNCATE**。
> 4. 有审计触发器的表：删前先手工记录"谁几点TRUNCATE了这张表"到独立审计日志，否则触发器不触发会留审计漏洞。

## 6.2.6 查询表/约束/数据字典

| 视图 | 用途 | 典型SQL |
| ---- | ---- | ---- |
| **DBA_TABLES / ALL_TABLES / USER_TABLES** | 表基本属性（表空间/行数统计/块数/压缩/LOB） | `SELECT owner, table_name, tablespace_name, num_rows, blocks*8/1024 mb, compression, compress_for FROM dba_tables WHERE owner='HR';` |
| **DBA_TAB_COLUMNS** | 列属性（类型/长度/DEFAULT/NOT NULL/HISTOGRAM） | `SELECT owner, table_name, column_name, data_type, data_length, nullable, data_default FROM dba_tab_columns WHERE owner='HR' AND table_name='EMPLOYEES';` |
| **DBA_CONSTRAINTS** | 约束定义（类型/状态/WHAT条件/REFERENCED约束） | `SELECT owner, constraint_name, constraint_type, table_name, status, validated, search_condition_vc search_condition FROM dba_constraints WHERE owner='HR';` 类型P=主键R=外键U=唯一C=CHECK/NN |
| **DBA_CONS_COLUMNS** | 约束列对应关系 | `SELECT owner, constraint_name, table_name, column_name, position FROM dba_cons_columns WHERE owner='HR' ORDER BY constraint_name, position;` |
| **DBA_INDEXES / DBA_IND_COLUMNS** | 索引定义（外键是否有索引查这两个）| `SELECT table_owner, table_name, index_name, uniqueness FROM dba_indexes WHERE table_owner='HR';` |

> [!tip] 约束类型编码速记（DBA_CONSTRAINTS.CONSTRAINT_TYPE）：P=PRIMARY KEY，R=REFERENTIAL FOREIGN KEY，U=UNIQUE，C=CHECK和NOT NULL（NOT NULL实际是CHECK列 IS NOT NULL），O=只读视图WITH READ ONLY，V=视图CHECK OPTION。
