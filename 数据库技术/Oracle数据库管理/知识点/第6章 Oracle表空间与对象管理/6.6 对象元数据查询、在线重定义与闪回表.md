# 6.6 对象元数据查询、在线重定义与闪回表

本节解决的核心问题是：**如何一键获取表/索引/存储过程的完整DDL脚本？如何无停机修改大表结构（修改列类型/加主键/改表压缩/迁移表空间等）而不中断业务DML？误删表/DROP表/TRUNCATE表了怎么秒级恢复？** 元数据查询、在线重定义、闪回是DBA处理生产变更、故障回退的三大神器。

## 6.6.1 DBMS_METADATA：获取完整对象DDL

> [!definition] DBMS_METADATA包
> Oracle内置的PL/SQL包，可以从数据字典中把任意数据库对象（表/索引/视图/序列/同义词/存储过程/函数/触发器/表空间/用户/约束/DBLink等）的完整定义DDL语句以CLOB形式提取出来。替代老工具imp show=y、exp indexfile的功能，是10g+生成对象创建脚本的标准方式。

### 1. DBMS_METADATA.GET_DDL核心函数（★最常用）

```sql
-- ========== 基础用法1：GET_DDL获取单个对象完整DDL ==========
-- 语法：DBMS_METADATA.GET_DDL(object_type, object_name, owner) RETURN CLOB
-- 返回CLOB，客户端需要SET LONG 1000000 LONGCHUNKSIZE 1000000 PAGESIZE 0 LINESIZE 32767才能正确显示不截断

-- 设置sqlplus环境（避免显示截断）
SET ECHO OFF FEEDBACK OFF HEADING OFF VERIFY OFF TRIMSPOOL ON
SET LONG 2000000000 LONGCHUNKSIZE 32767
SET PAGESIZE 0 LINESIZE 32767

-- 1. 获取单表DDL（含所有约束/索引/触发器/LOB/分区吗？默认含大部分，可用TRANSFORM_PARAM控制）
SELECT DBMS_METADATA.GET_DDL('TABLE','EMPLOYEES','HR') table_ddl FROM DUAL;

-- 2. 获取索引DDL
SELECT DBMS_METADATA.GET_DDL('INDEX','EMP_DEPT_ID_IDX','HR') FROM DUAL;

-- 3. 获取视图DDL
SELECT DBMS_METADATA.GET_DDL('VIEW','EMP_DEPT_V','HR') FROM DUAL;

-- 4. 获取用户/角色/权限的DDL（用户迁移导出神器！）
SELECT DBMS_METADATA.GET_DDL('USER','SCOTT') FROM DUAL;
-- 4.1 用户的系统权限GRANT语句
SELECT DBMS_METADATA.GET_GRANTED_DDL('SYSTEM_GRANT','SCOTT') FROM DUAL;
-- 4.2 用户的对象权限GRANT语句
SELECT DBMS_METADATA.GET_GRANTED_DDL('OBJECT_GRANT','SCOTT') FROM DUAL;
-- 4.3 用户拥有的角色
SELECT DBMS_METADATA.GET_GRANTED_DDL('ROLE_GRANT','SCOTT') FROM DUAL;
-- 4.4 用户的默认/配额/表空间设置完整脚本（组合4个一起就是全用户迁移）

-- 5. 获取表空间DDL
SELECT DBMS_METADATA.GET_DDL('TABLESPACE','USERS') FROM DUAL;

-- 6. 获取存储过程/函数/包
SELECT DBMS_METADATA.GET_DDL('PROCEDURE','MY_PROC','HR') FROM DUAL;
SELECT DBMS_METADATA.GET_DDL('PACKAGE','DBMS_STATS','SYS') FROM DUAL;
SELECT DBMS_METADATA.GET_DDL('PACKAGE_BODY','DBMS_STATS','SYS') FROM DUAL;
```

### 2. 精细化输出：TRANSFORM_PARAM（去掉多余的属性）

默认GET_DDL输出包含大量存储/段属性（INITIAL/NEXT/PCTINCREASE等LMT下不需要的旧参数），可以通过`set_transform_param`精简：

```sql
-- 先EXEC设置会话级的转换参数（每次新连接都要重设）
EXEC DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM,'PRETTY',TRUE);              -- 格式化换行（默认TRUE）
EXEC DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM,'SQLTERMINATOR',TRUE);       -- 每条DDL加分号";"结尾（默认FALSE，生产必开！不然复制出来没分号）
EXEC DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM,'STORAGE',FALSE);            -- ❌不要STORAGE子句（INITIAL/NEXT等，LMT下多余）
EXEC DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM,'TABLESPACE',TRUE);          -- ✅保留TABLESPACE子句（很重要，不然建到默认表空间）
EXEC DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM,'SEGMENT_ATTRIBUTES',FALSE); -- ❌不要PCTFREE/PCTUSED/INITRANS等段属性
EXEC DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM,'CONSTRAINTS',TRUE);         -- ✅输出约束
EXEC DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM,'REF_CONSTRAINTS',TRUE);     -- ✅输出外键约束
EXEC DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM,'CONSTRAINTS_AS_ALTER',TRUE);-- ✅约束作为独立ALTER TABLE ADD输出（默认TRUE，方便分步执行）
EXEC DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM,'PARTITIONING',TRUE);        -- ✅输出分区子句
EXEC DBMS_METADATA.SET_TRANSFORM_PARAM(DBMS_METADATA.SESSION_TRANSFORM,'BODY',TRUE);                -- ✅PACKAGE输出PACKAGE BODY部分

-- 设置完再GET_DDL，就得到生产可直接执行的精简DDL脚本！
SELECT DBMS_METADATA.GET_DDL('TABLE','EMPLOYEES','HR') FROM DUAL;
```

### 3. GET_DEPENDENT_DDL + 批量导出某Schema全部对象

```sql
-- 获取某Schema下全部对象的DDL：DBMS_METADATA.GET_DEPENDENT_DDL / 遍历DBA_OBJECTS
-- 例：批量导出HR用户下所有表的DDL：
SET PAGESIZE 0 LINESIZE 32767 LONG 2000000000 LONGC 32767 TRIMSPOOL ON
SPOOL /home/oracle/hr_schema_ddl.sql
-- 先设置转换参数（同上），再SELECT每个对象：
SELECT '---------------------------------------------------------'||CHR(10)||'-- DDL for '||object_type||' '||object_name||CHR(10)||'---------------------------------------------------------'||CHR(10)||
       DBMS_METADATA.GET_DDL(object_type, object_name, owner)
  FROM DBA_OBJECTS O
 WHERE OWNER='HR'
   AND OBJECT_TYPE IN ('TABLE','VIEW','SEQUENCE','PROCEDURE','FUNCTION','PACKAGE','TYPE','SYNONYM','TRIGGER')
   AND STATUS='VALID'
 ORDER BY CASE OBJECT_TYPE WHEN 'TABLE' THEN 1 WHEN 'SEQUENCE' THEN 2 WHEN 'VIEW' THEN 3 WHEN 'PROCEDURE' THEN 4 WHEN 'FUNCTION' THEN 5 WHEN 'PACKAGE' THEN 6 ELSE 9 END, OBJECT_NAME;
SPOOL OFF
```

## 6.6.2 在线重定义DBMS_REDEFINITION：无停机大表结构变更

> [!definition] 在线重定义（DBMS_REDEFINITION包）
> 9i+ Oracle内置的在线表结构重构功能：在不中断业务DML（INSERT/UPDATE/DELETE）的前提下，完成以下原本需要停机ALTER TABLE MOVE锁表几小时的操作：
> - 修改列数据类型（VARCHAR2(100)→VARCHAR2(500)、NUMBER→DATE等MOVE都做不了的）
> - 重新组织表消除行迁移/高水位线碎片（MOVE要停机，重定义不用）
> - 把普通HEAP表改成IOT索引组织表、分区表（大表改分区！）
> - 表加压缩（COMPRESS FOR OLTP/QUERY HIGH）
> - 迁移表到新表空间（MOVE要锁表+重建所有索引，重定义不锁）
> - 新增/删除列（特别是加NOT NULL列默认值11g+虽然优化了，但大表加多个带计算的NOT NULL列还是慢）

### 1. 在线重定义两种模式（BY PRIMARY KEY vs BY ROWID）

| 模式 | 前提条件 | 适用场景 |
| ---- | ---- | ---- |
| **BY PRIMARY KEY（默认）** | 表必须有主键（PRIMARY KEY约束，唯一索引不算，必须是PRIMARY KEY约束+VALID状态）| ★生产99%用这个！主键唯一标识行，重定义后ROWID变化但主键不变 |
| BY ROWID（老模式）| 表没有主键（不推荐的反模式） | 遗留老系统没主键的表，才用这个模式（最后会隐含M_ROW$$列，要DROP掉） |

### 2. 在线重定义7步流程（以大表加COMPRESS FOR OLTP+迁移到新表空间为例）

```sql
-- ===== 场景：HR.EMPLOYEES 1亿行，要加压缩FOR OLTP + 迁移到HR_DATA_NEW表空间，期间正常DML不中断 =====
-- Step1：验证表是否可以在线重定义（先检查，不然后面中间步骤报错）
BEGIN
  DBMS_REDEFINITION.CAN_REDEF_TABLE(
    uname       => 'HR',
    tname       => 'EMPLOYEES',
    options_flag=> DBMS_REDEFINITION.CONS_USE_PK    -- ★主键模式（CONS_USE_ROWID为ROWID模式）
  );
END;
/
-- 成功=无输出；失败会报具体原因（没有主键/有LONG列/属于SYS用户等）

-- Step2：创建中间表（空表），最终想让原表变成什么样，中间表就怎么CREATE！
-- ★★★ 中间表结构=目标状态结构（表空间/压缩/列类型/分区/约束等都先写好）
CREATE TABLE HR.EMPLOYEES_INT (
  employee_id NUMBER(6) PRIMARY KEY,
  first_name VARCHAR2(20),
  last_name VARCHAR2(25) NOT NULL,
  email VARCHAR2(25) NOT NULL,
  hire_date DATE DEFAULT SYSDATE NOT NULL,
  salary NUMBER(8,2) DEFAULT 0
)
TABLESPACE HR_DATA_NEW
COMPRESS FOR OLTP            -- ★最终目标：压缩+新表空间
PCTFREE 10 INITRANS 4
ENABLE ROW MOVEMENT;
-- 中间表先不要加约束/索引/触发器/外键（重定义完会自动同步，也可以手动COPY），只建基础列结构

-- Step3：启动在线重定义过程（START_REDEF_TABLE）
-- ★核心长操作：会把原表历史数据INSERT /*+APPEND PARALLEL*/ INTO 中间表（初始拷贝）
-- 期间业务DML操作记录到物化视图日志（MLOG$_EMPLOYEES自动建），后面SYNC_INTERIM_TABLE增量同步
BEGIN
  DBMS_REDEFINITION.START_REDEF_TABLE(
    uname             => 'HR',
    orig_table        => 'EMPLOYEES',      -- 原表名
    int_table         => 'EMPLOYEES_INT',  -- 中间表名
    col_mapping       => NULL,             -- 列映射：列名/类型不变=NULL；改列：'employee_id emp_id_new, salary*1.1 new_salary'
    options_flag      => DBMS_REDEFINITION.CONS_USE_PK,
    orderby_cols      => NULL,
    part_name         => NULL,             -- 单表重定义=NULL；只重定义某分区填分区名
    copy_statistics   => TRUE,             -- 拷贝原表统计信息（TRUE=省的重收集）
    parallelism       => 8                 -- 并行8度拷贝（大表加速，OLTP繁忙时调2~4）
  );
END;
/
-- 大表Step3可能几十分钟到几小时（看数据量），期间原表可以正常INSERT/UPDATE/DELETE完全不影响！

-- Step4：（可选但推荐）复制依赖对象：约束/索引/触发器/权限/统计信息（不然FINISH后原表只有列没索引）
-- ★用COPY_TABLE_DEPENDENTS自动复制，省得手动建N个索引
DECLARE
  num_errors PLS_INTEGER;
BEGIN
  DBMS_REDEFINITION.COPY_TABLE_DEPENDENTS(
    uname            => 'HR',
    orig_table       => 'EMPLOYEES',
    int_table        => 'EMPLOYEES_INT',
    copy_indexes     => DBMS_REDEFINITION.CONS_ORIG_PARAMS,   -- 1=复制所有索引（保留原存储参数，推荐）
    copy_triggers     => TRUE,
    copy_constraints  => TRUE,
    copy_privileges   => TRUE,
    ignore_errors     => FALSE,   -- FALSE=有依赖报错就停，TRUE=忽略单条错误继续其他依赖
    num_errors       => num_errors,
    copy_statistics  => TRUE,
    copy_mvlog       => FALSE
  );
  DBMS_OUTPUT.PUT_LINE('COPY_DEPENDENTS errors = '||num_errors);
END;
/
-- ★执行完检查num_errors=0就完美；>0看DBA_REDEFINITION_ERRORS视图具体哪个对象报错（多半是索引名冲突）

-- Step5：（推荐大表）同步增量DML（SYNC_INTERIM_TABLE）
-- 因为Step3到Step4期间业务又产生大量DML，FINISH_SWITCH时要追平所有增量，先手动SYNC一次减少最后FINISH的锁表时间
BEGIN
  DBMS_REDEFINITION.SYNC_INTERIM_TABLE(
    uname      => 'HR',
    orig_table => 'EMPLOYEES',
    int_table  => 'EMPLOYEES_INT'
  );
END;
/
-- 可以SYNC多次，直到最后一次SYNC很快（1秒内），再做Step6 FINISH

-- Step6：★★★ 完成切换（FINISH_REDEF_TABLE）—— 唯一一次短暂锁表！
-- 最后会：1. 再SYNC一次追平最后几毫秒的增量；2. 对原表+中间表加排他DDL锁（极短时间，毫秒~秒级）；3. 交换数据字典中两张表的名字、对象ID、所有权限/索引归属。
-- ⚠️ 切换前后表名对调：原表EMPLOYEES现在是中间表的数据（新压缩的），EMPLOYEES_INT变成了旧表数据（空壳留着删）
BEGIN
  DBMS_REDEFINITION.FINISH_REDEF_TABLE(
    uname      => 'HR',
    orig_table => 'EMPLOYEES',
    int_table  => 'EMPLOYEES_INT'
  );
END;
/
-- ✅ 成功！业务完全不感知（只有极短DDL锁，毫秒级，高并发可能1~2秒等待，业务基本无感）

-- Step7：删除旧中间表（现在它存的是原表旧结构的空壳，已经没人用了）
DROP TABLE HR.EMPLOYEES_INT PURGE;   -- PURGE直接删，不进回收站省空间
```

### 3. 异常回滚：中间步骤报错了怎么办？ABORT_REDEF_TABLE

如果Step3~Step6之间任何步骤出错、或者你中途不想做了，**必须执行ABORT**，不然MLOG$_表、物化视图日志残留，后续DROP原表会报错：

```sql
BEGIN
  DBMS_REDEFINITION.ABORT_REDEF_TABLE(
    uname      => 'HR',
    orig_table => 'EMPLOYEES',
    int_table  => 'EMPLOYEES_INT'
  );
END;
/
-- 执行完一切回到重定义前状态，中间表自己手动DROP即可。
```

> [!danger] 在线重定义生产注意事项
> 1. 重定义期间原表每1次DML都会额外写入MLOG$_日志，IO开销增加30%~50%。**不要在业务高峰期启动START_REDEF_TABLE**，选低峰期（晚上/周末）。
> 2. 中间表要预留2倍原表空间（原表+中间表+物化视图日志临时空间），表空间满了会自动ABORT。
> 3. 原表有外键引用：FINISH后外键会自动COPY到新表，但子表外键指向新表要校验（COPY_TABLE_DEPENDENTS会处理）。
> 4. 有物化视图/CDC/GoldenGate捕获原表：重定义后对象ID变化，要重建捕获/刷新MV。
> 5. 重定义前先在测试环境100%模拟全流程：CREATE TABLE T AS SELECT * FROM 原表 WHERE 1=1; 用测试表演练一遍所有步骤，确认不会报错再上生产！

## 6.6.3 闪回表与Recycle Bin回收站（★★★误操作救命神器）

> [!definition] 闪回表（Flashback Table）
> Oracle 10g+ 闪回技术：把**一张或多张表**（含关联索引/约束/触发器）闪回到过去某个时间点/SCN号的状态，利用UNDO表空间中的旧撤销数据（不是备份！）快速回滚误操作（误UPDATE全表/误DELETE全表/程序Bug批量改错）。秒级~分钟级恢复，比RMAN恢复快几个数量级。

### 1. 闪回表前提条件

| 条件 | 说明 |
| ---- | ---- |
| **表空间自动撤销管理AUM** | 默认11g+都是AUM（`SHOW PARAMETER UNDO_MANAGEMENT=AUTO`）|
| **撤销保留时间UNDO_RETENTION够长** | 默认900秒=15分钟，生产建议设`UNDO_RETENTION=86400`（24小时）+ GUARANTEE保证RETENTION |
| **表必须ENABLE ROW MOVEMENT** | 默认禁用！因为闪回表本质是DELETE+INSERT重建行，ROWID会变，必须先`ALTER TABLE ... ENABLE ROW MOVEMENT` |
| **闪回的UNDO数据还在UNDOTBS中** | 超过UNDO_RETENTION的UNDO可能被覆盖，闪回会报ORA-08180: no snapshot found based on specified time |

### 2. 闪回表SQL（★误UPDATE/DELETE救命）

```sql
-- 场景：开发误执行 UPDATE hr.employees SET salary = salary * 10; 全表工资改10倍并且COMMIT了！！！
-- 先查当前时间/SCN：
SELECT SYSTIMESTAMP now, DBMS_FLASHBACK.GET_SYSTEM_CHANGE_NUMBER current_scn FROM DUAL;
-- 假设现在 2024-05-15 14:30:00，误操作时间 14:25:00。闪回到14:24:00（误操作前1分钟）

-- Step0：★一定要先备份当前表状态！防止闪回错了再闪不回来！
CREATE TABLE hr.employees_bak_20240515_1430 NOLOGGING PARALLEL 4
  AS SELECT * FROM hr.employees;

-- Step1：启用行迁移（闪回要求，生产建议建表时就开）
ALTER TABLE hr.employees ENABLE ROW MOVEMENT;

-- Step2：按时间点闪回（★最简单）
FLASHBACK TABLE hr.employees
  TO TIMESTAMP TO_TIMESTAMP('2024-05-15 14:24:00','YYYY-MM-DD HH24:MI:SS');
-- ✅ 成功！employees表恢复到14:24的正确状态

-- Step2 alt：按SCN闪回（更精确，时间会受夏令时/DST调整影响，SCN是单调递增永不后退的，生产推荐用SCN）
-- 先通过时间转SCN：SELECT TIMESTAMP_TO_SCN(TO_TIMESTAMP('2024-05-15 14:24:00','YYYY-MM-DD HH24:MI:SS')) AS scn FROM DUAL;
FLASHBACK TABLE hr.employees TO SCN 1234567890;

-- Step3：恢复完如果ROW MOVEMENT不是默认状态，按需要DISABLE
-- ALTER TABLE hr.employees DISABLE ROW MOVEMENT;

-- Step4：确认数据没问题再DROP备份表
SELECT COUNT(*) FROM hr.employees WHERE salary > 1000000;  -- 检查高工资数据是否修复
DROP TABLE hr.employees_bak_20240515_1430 PURGE;
```

> [!tip] 多张表有外键关联？一次性闪回！
> 有主子表外键关系（订单+订单明细），单独闪回一张会外键冲突。一起写：
> ```sql
> FLASHBACK TABLE hr.orders, hr.order_items
>   TO TIMESTAMP TO_TIMESTAMP('2024-05-15 14:24:00','YYYY-MM-DD HH24:MI:SS');
> ```
> 多张表作为一个原子事务同时闪回，不会有中间状态外键冲突。

### 3. Recycle Bin回收站：误DROP TABLE秒级恢复

> [!definition] 回收站（Recycle Bin）
> 10g+ 默认启用：你`DROP TABLE xxx`时Oracle不是真删除段，而是把表+所有关联索引/约束/LOB段改名为BIN$xxx的乱码名移到回收站逻辑容器中。只要没PURGE、表空间没压力自动清除，就可以`FLASHBACK TABLE ... TO BEFORE DROP`秒级恢复（不用备份！）。

```sql
-- ===== 场景：DBA误执行 DROP TABLE HR.EMPLOYEES; 现在表不见了！！！=====
-- 1. 不要慌，先查回收站有没有（当前用户回收站）
SHOW RECYCLEBIN;
-- 或DBA视图查全库被删的对象：
SELECT owner, original_name, object_name, type, ts_name,
       droptime, can_undrop, can_purge, space*8/1024 mb
  FROM DBA_RECYCLEBIN
 WHERE original_name = 'EMPLOYEES' AND owner='HR'
 ORDER BY droptime DESC;
-- CAN_UNDROP=YES=可以闪回恢复！
-- OBJECT_NAME=乱码名BIN$qJk3zKqGQkCgUjE0wVqG0g==$0

-- 2. ★秒级从回收站闪回恢复（TO BEFORE DROP）
FLASHBACK TABLE HR.EMPLOYEES TO BEFORE DROP;
-- ✅ 瞬间恢复！所有约束/索引/触发器/权限跟原来一模一样（只是索引名/约束名还是乱码BIN$名，强迫症可以自己RENAME回原名）

-- 3. 如果同一张表被DROP了多次（回收站有多个版本），指定要恢复哪次删的（最新删的默认恢复）
FLASHBACK TABLE HR.EMPLOYEES
  TO BEFORE DROP
  RENAME TO EMPLOYEES_V1;   -- 恢复后重命名为V1（避免与现在已有的同名表冲突）

-- 4. 直接删除不进回收站（DROP ... PURGE）→ 无法恢复！
DROP TABLE HR.TEST_TBL PURGE;   -- ★PURGE = 直接删段不走回收站，确认100%不用才用
TRUNCATE TABLE HR.TEST_TBL;     -- ⚠️ TRUNCATE不DROP表也不进回收站，TRUNCATE只能RMAN备份恢复或Oracle Flashback Data Archive（FDA闪回归档）

-- 5. 手动清空回收站
PURGE RECYCLEBIN;                             -- 清空当前用户回收站
PURGE TABLESPACE USERS USER HR;               -- 只清USERS表空间中HR用户的回收站对象
PURGE DBA_RECYCLEBIN;                         -- 清空全库所有用户回收站（需SYSDBA）
```

> [!warning] 回收站的三大限制（无法恢复的情况）
> 1. **DROP TABLESPACE ... INCLUDING CONTENTS AND DATAFILES**：整个表空间+数据文件删了 → 所有在该表空间下的回收站对象自动失效，无法Flashback Table。
> 2. **DROP USER ... CASCADE**：用户被级联删 → 用户所有对象（含回收站对象）被删除，无法恢复。
> 3. 回收站对象的表空间空间压力大（新对象申请空间找不到空闲EXTENT），Oracle会自动**按FIFO（先进先出）清除最早进回收站的对象**腾出空间。所以DROP表后要尽快恢复，等几天空间满了可能被自动Purge。
> 4. **系统表空间SYSTEM下的表不进回收站**。

### 4. 闪回技术族总览（面试常考4+2种）

| 闪回技术 | 作用对象 | 依赖 | 典型使用场景 | 速度 |
| ---- | ---- | ---- | ---- | ---- |
| **Flashback Query（闪回查询）** | SELECT查询看过去数据 | UNDO | 查误操作前的旧数据`SELECT * FROM t AS OF TIMESTAMP ...` | 快 |
| **Flashback Version Query** | 行级版本历史（每次修改前的所有版本） | UNDO | 审计某行某段时间经历过什么修改 | 中 |
| **Flashback Transaction Query** | 事务级DML历史 | UNDO + Supplemental Log | 反查哪个事务改了数据，生成反向UNDO_SQL | 中 |
| **★ Flashback Table（本节讲）** | 整表闪回某时间点 | UNDO + ROW MOVEMENT | 误UPDATE/DELETE整表，回滚到误操作前 | 分钟级 |
| **★ Flashback Drop + Recycle Bin（本节讲）**| DROP表恢复 | Recycle Bin逻辑容器 | 误DROP TABLE秒级恢复 | 秒级 |
| **Flashback Database（闪回数据库）** | 整个数据库闪回过去时间点 | Flashback Logs闪回日志+快速恢复区FRA | 测试库批处理/升级失败，全库回退1小时（比RMAN快一个数量级） | 分钟级 |
| Flashback Data Archive（FDA闪回归档） | 整表几年历史在线查询 | FDA独立表空间+后台进程 | 合规审计（金融/医疗要求保留5年历史），用`AS OF TIMESTAMP 5年前`能查到 | 中 |

## 小结

本节详述了DBA变更运维的三大核心工具：① DBMS_METADATA.GET_DDL一键提取所有对象DDL+SET_TRANSFORM_PARAM精简输出+批量Schema迁移脚本；② DBMS_REDEFINITION在线重定义7步无停机大表重构流程（含CAN_REDEF_CHECK/START/COPY_DEPENDENTS/SYNC/FINISH/ABORT），对比ALTER TABLE MOVE的停机差异；③ 闪回表Flashback Table（按时间/SCN用UNDO回滚误DML）+回收站Recycle Bin（DROP表秒级恢复TO BEFORE DROP/PURGE），覆盖了误操作应急场景。最后给出闪回技术族总览对比。这三类工具是高级DBA区别于初级DBA的核心战斗力。
