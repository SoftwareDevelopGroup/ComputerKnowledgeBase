# 4.3 启动故障简单排查

本节解决的核心问题是：**数据库启动失败时，按什么流程排查？常见的ORA错误号对应什么问题？如何快速定位与解决？** 启动故障是DBA日常运维最常碰到的问题之一，掌握排查思路比死记单个解决方案更重要。

## 4.3.1 排查总流程

> [!definition] 启动故障排查方法论
> **启动失败 → 看告警日志 → 找ORA错误号 → 定位故障阶段 → 查对应V$视图/OS文件 → 执行解决方案 → 重启验证**
> 核心原则：**先看日志，再动手**。不要一上来就猜问题，告警日志会告诉你真相。

```mermaid
flowchart TD
    Start[STARTUP启动失败<br/>屏幕显示ORA错误] --> Step1[第一步：查看告警日志<br/>alert_SID.log]
    Step1 --> Step2{第二步：判断<br/>故障发生阶段}

    Step2 -->|NOMOUNT失败<br/>(还没读参数)| Fail1[监听/网络类<br/>ORA-125xx<br/>或OS权限问题]
    Step2 -->|NOMOUNT失败<br/>(读参数出错)| Fail2[参数文件问题<br/>ORA-01078/LRM-00109]
    Step2 -->|MOUNT失败| Fail3[控制文件问题<br/>ORA-00205]
    Step2 -->|OPEN失败| Fail4[数据文件问题<br/>ORA-01157<br/>ORA-01113]
    Step2 -->|OPEN失败<br/>(重做日志)| Fail5[重做日志问题<br/>CURRENT日志损坏]
    Step2 -->|OPEN失败<br/>(归档)| Fail6[归档空间不足<br/>ORA-00257]
    Step2 -->|登录失败| Fail7[密码文件/用户权限<br/>orapwd重建]

    Fail1 --> Fix1[启动监听/检查TNS配置<br/>lsnrctl start]
    Fail2 --> Fix2[恢复参数文件<br/>从备份恢复/从pfile重建]
    Fail3 --> Fix3[多路复用恢复<br/>用好的覆盖损坏的/重建控制文件]
    Fail4 --> Fix4[介质恢复/离线损坏文件<br/>RECOVER/ALTER DATABASE DATAFILE OFFLINE DROP]
    Fail5 --> Fix5[切换日志/清除日志组<br/>ALTER SYSTEM SWITCH LOGFILE]
    Fail6 --> Fix6[备份后删除过期归档<br/>RMAN DELETE ARCHIVELOG]
    Fail7 --> Fix7[重建密码文件<br/>orapwd file=...]

    Fix1 --> Verify[验证：重新启动<br/>STARTUP]
    Fix2 --> Verify
    Fix3 --> Verify
    Fix4 --> Verify
    Fix5 --> Verify
    Fix6 --> Verify
    Fix7 --> Verify
```

> [!note] 告警日志（Alert Log）路径
> - **Oracle 11g+（ADR自动诊断库）**：`$ORACLE_BASE/diag/rdbms/<dbname>/<SID>/trace/alert_<SID>.log`
> - **旧版本（10g及以前）**：`$ORACLE_BASE/admin/<SID>/bdump/alert_<SID>.log`
> - 可通过SQL查询：`SELECT value FROM v$diag_info WHERE name = 'Diag Trace';`
>
> **读告警日志技巧**：文件通常很大，用`tail -f alert_<SID>.log`实时查看尾部，或搜索`ORA-`、`Error`、`Starting`、`Completed`等关键词。

## 4.3.2 故障类型一：监听未启动（ORA-12514 / ORA-12505）

> [!warning] 监听未启动表现
> 在客户端（或服务器端用EZConnect连接）报错：
> - **ORA-12514**: TNS:listener does not currently know of service requested in connect descriptor
> - **ORA-12505**: TNS:listener does not currently know of SID given in connect descriptor
>
> **注意**：本机用`sqlplus / as sysdba`登录（BEQ协议，不走监听）**不会受影响**。但远程连接、应用连接都会失败。

### 1. 错误原因

| 原因 | 说明 |
| ---- | ---- |
| ① 监听服务未启动 | 最常见，监听进程tnslsnr没起。 |
| ② 数据库未注册到监听 | 数据库启动了，但动态注册（PMON自动注册）未完成，或静态注册配置错误。 |
| ③ tnsnames.ora / listener.ora配置错误 | SERVICE_NAME/SID拼写错误、端口不匹配（默认1521）。 |
| ④ 防火墙/网络问题 | 客户端无法到达服务器1521端口。 |

### 2. 排查步骤

```bash
# (1) 检查监听状态
lsnrctl status
# 输出若显示"The listener supports no services"或直接报错→监听未启动

# (2) 启动监听
lsnrctl start

# (3) 等待60秒让PMON动态注册数据库服务，再查看
lsnrctl status
# 应该能看到实例<SID>对应的服务<SID>.<domain>已注册

# (4) 若60秒后仍未注册，手动强制注册
sqlplus / as sysdba
ALTER SYSTEM REGISTER;
```

### 3. listener.ora静态注册示例（Oracle 19c）

```listener.ora
# listener.ora Network Configuration File
LISTENER =
  (DESCRIPTION_LIST =
    (DESCRIPTION =
      (ADDRESS = (PROTOCOL = TCP)(HOST = orcl-server)(PORT = 1521))
      (ADDRESS = (PROTOCOL = IPC)(KEY = EXTPROC1521))
    )
  )

# 静态注册（可选，用于数据库未启动时也要连接的场景，如DG备库）
SID_LIST_LISTENER =
  (SID_LIST =
    (SID_DESC =
      (GLOBAL_DBNAME = orcl)
      (ORACLE_HOME = /u01/app/oracle/product/19c/dbhome_1)
      (SID_NAME = orcl)
    )
  )
```

> [!tip] 快速验证
> - 客户端侧：`tnsping <tns别名>` 测试到监听的连通性。
> - 服务器侧：本机`sqlplus / as sysdba`能连上就说明数据库实例没问题，问题一定在**监听/网络/TNS配置**。

## 4.3.3 故障类型二：参数文件丢失或损坏（ORA-01078 / LRM-00109）

> [!warning] 参数文件损坏表现
> 执行STARTUP即报错：
> ```
> ORA-01078: failure in processing system parameters
> LRM-00109: could not open parameter file '/u01/.../dbs/initorcl.ora'
> ```
> 或：
> ```
> ORA-00821: Specified value of sga_target 1024M is too small
> ```
> （参数文件中某个参数值非法，读取成功但校验失败）

### 1. 错误原因

| 原因 | 说明 |
| ---- | ---- |
| ① spfile/pfile物理文件丢失 | 误删、文件系统损坏、$ORACLE_HOME/dbs下的spfile<SID>.ora不存在。 |
| ② 权限错误 | oracle用户对参数文件无读权限（属主/权限不对）。 |
| ③ 参数值非法 | 比如SGA_MAX_SIZE设得比服务器内存还大、非法字符写入spfile等。 |

### 2. 解决方案分级（Oracle 19c）

**方案A：有备份的spfile/pfile → 直接还原**
```bash
# (1) 确认参数文件位置
cd $ORACLE_HOME/dbs
ls -l spfile<SID>.ora init<SID>.ora   # 查看文件是否存在

# (2) 如果有RMAN备份，从备份恢复spfile
rman target /
RMAN> STARTUP NOMOUNT FORCE;   -- 可能报错，没关系继续
RMAN> RESTORE SPFILE FROM '/backup/rman/spfile_backup.bkp';
RMAN> STARTUP FORCE;   -- 用恢复的spfile启动
```

**方案B：spfile坏了但有历史pfile副本 → 从pfile重建spfile**
```sql
-- (1) 用历史pfile先启动到NOMOUNT
STARTUP NOMOUNT PFILE='$ORACLE_HOME/dbs/initorcl.ora.20240101';

-- (2) 从内存参数重建spfile（推荐，保留当前内存中运行过的有效参数）
CREATE SPFILE FROM PFILE='$ORACLE_HOME/dbs/initorcl.ora.20240101';
-- 或从内存创建：
CREATE SPFILE FROM MEMORY;

-- (3) 重启生效
SHUTDOWN IMMEDIATE;
STARTUP;
```

**方案C：完全没有任何参数文件备份 → 手工构造最小化pfile**
```pfile
# initorcl.ora 手工构造最小参数文件（根据实际环境修改路径）
db_name='orcl'
db_block_size=8192
memory_target=2G          # 11g+ 自动内存管理，或用sga_target + pga_aggregate_target
control_files='/u01/app/oracle/oradata/orcl/control01.ctl',
              '/u01/app/oracle/fast_recovery_area/orcl/control02.ctl'
# 如果记不住control_files路径，可以去OS下find一下数据文件目录
compatible='19.0.0'
```
然后用这个最小pfile启动到NOMOUNT，再从alert_SID.log的历史启动记录中找回其他参数值补全。

> [!tip] 参数文件预防措施
> 每次修改参数后（尤其是ALTER SYSTEM SET ... SCOPE=SPFILE），**立即备份参数文件**：
> ```sql
> CREATE PFILE='$ORACLE_HOME/dbs/initorcl.ora.'||TO_CHAR(SYSDATE,'YYYYMMDD') FROM SPFILE;
> ```

## 4.3.4 故障类型三：控制文件多路复用丢失/损坏（ORA-00205）

> [!warning] 控制文件损坏表现
> 启动到MOUNT阶段失败：
> ```
> ORA-00205: error in identifying control file, check alert log for more info
> ```
> 查看告警日志尾部，会明确指出哪个控制文件路径失败：
> ```
> Controlfile identified with first file /u01/.../control01.ctl
> ORA-00202: control file: '/u01/.../control02.ctl'
> ORA-27037: unable to obtain file status
> Linux-x86_64 Error: 2: No such file or directory
> ```

### 1. 错误原因

| 原因 | 说明 |
| ---- | ---- |
| ① 控制文件物理丢失/损坏 | 磁盘故障、误删、文件头损坏。 |
| ② 多路复用控制文件大小不一致 | 部分损坏导致多路镜像内容不同步。 |
| ③ 参数CONTROL_FILES路径错误 | 参数文件中CONTROL_FILES参数值拼错路径。 |

### 2. 解决方案分级（Oracle 19c）

**方案A：至少一个多路控制文件完好 → 复制覆盖（首选）**
```bash
# (1) 关闭数据库
sqlplus / as sysdba
SHUTDOWN ABORT;   -- MOUNT失败无法IMMEDIATE，只能ABORT
exit;

# (2) OS层面：用好的控制文件覆盖所有损坏/丢失的副本
cd $ORACLE_HOME/dbs
cp /u01/app/oracle/oradata/orcl/control01.ctl \
   /u01/app/oracle/fast_recovery_area/orcl/control02.ctl
# 注意：必须保持所有控制文件的字节数完全一致（cp覆盖就是完全一致）

# (3) 重启验证
sqlplus / as sysdba
STARTUP;
```

**方案B：所有控制文件全部丢失 → 备份恢复或CREATE CONTROLFILE重建**
```sql
-- (1) 从RMAN备份恢复控制文件（有备份的情况）
STARTUP NOMOUNT;
RESTORE CONTROLFILE FROM '/backup/rman/ctl_20240101.bkp';
ALTER DATABASE MOUNT;
RECOVER DATABASE;   -- 控制文件是旧的，必须做介质恢复
ALTER DATABASE OPEN RESETLOGS;

-- (2) 完全无备份 → 手工执行CREATE CONTROLFILE重建（需掌握完整文件清单！）
-- 步骤：
-- a. STARTUP NOMOUNT
-- b. 执行CREATE CONTROLFILE命令（列出所有数据文件+重做日志）
-- c. RECOVER DATABASE USING BACKUP CONTROLFILE
-- d. ALTER DATABASE OPEN RESETLOGS（通常需要resetlogs）
-- 详细步骤见第8章备份恢复
```

> [!danger] CREATE CONTROLFILE重建风险极高
> 重建控制文件需要你准确记住**所有数据文件、重做日志文件的完整路径清单**，以及数据库字符集、LOGFILE GROUP数、MAXLOGHISTORY等参数。任何一个遗漏都会导致重建失败或数据文件无法识别。**强烈建议平时备份控制文件到trace：**
> ```sql
> ALTER DATABASE BACKUP CONTROLFILE TO TRACE;   -- 在USER_DUMP_DEST生成重建脚本
> ALTER DATABASE BACKUP CONTROLFILE TO '/backup/control.bkp';  -- 二进制备份
> ```

## 4.3.5 故障类型四：数据文件丢失/损坏（ORA-01157 / ORA-01113）

> [!warning] 数据文件损坏表现
> 启动到OPEN阶段失败：
> ```
> ORA-01157: cannot identify/lock data file 6 - see DBWR trace file
> ORA-01110: data file 6: '/u01/app/oracle/oradata/orcl/users01.dbf'
> ```
> 或（文件存在但SCN不一致，需要恢复）：
> ```
> ORA-01113: file 6 needs media recovery
> ORA-01110: data file 6: '/u01/app/oracle/oradata/orcl/users01.dbf'
> ```

### 1. 错误原因

| 原因 | 说明 |
| ---- | ---- |
| ① 数据文件物理删除/磁盘损坏 | 最常见的介质故障。 |
| ② 数据文件SCN落后于控制文件 | 从旧备份恢复了某个数据文件，或SHUTDOWN ABORT后异常导致的不一致。 |
| ③ 数据文件被误OFFLINE且未恢复 | 之前OFFLINE的表空间未恢复就尝试OPEN。 |

### 2. 解决方案分级

**方案A：非关键业务用户表空间损坏（如USERS、INDEX） → 先OFFLINE再启动，后续恢复**
```sql
-- (1) 把损坏数据文件所在表空间OFFLINE（前提：SYSTEM/SYSAUX/UNDO不能OFFLINE）
STARTUP MOUNT;
ALTER DATABASE DATAFILE '/u01/.../users01.dbf' OFFLINE DROP;
ALTER DATABASE OPEN;
-- 此时数据库可用，只是USERS表空间下的对象无法访问

-- (2) 后续恢复（有备份的话）
ALTER TABLESPACE users OFFLINE;
-- RMAN还原恢复：
RESTORE TABLESPACE users;
RECOVER TABLESPACE users;
ALTER TABLESPACE users ONLINE;
```

**方案B：文件存在但SCN落后 → 直接介质恢复**
```sql
STARTUP MOUNT;
RECOVER DATAFILE 6;   -- 或 RECOVER TABLESPACE users;
-- Oracle自动应用归档日志+在线重做日志把文件推进到一致SCN
ALTER DATABASE OPEN;
```

**方案C：关键表空间SYSTEM/SYSAUX/UNDO损坏 → 必须完整介质恢复**
这些表空间无法OFFLINE，数据库不能OPEN。详见第8章备份恢复，基本步骤：
```sql
-- MOUNT状态下还原损坏表空间数据文件 + 恢复 + OPEN
RESTORE TABLESPACE system, sysaux, undotbs1;
RECOVER TABLESPACE system, sysaux, undotbs1;
ALTER DATABASE OPEN;
```

> [!note] 判断文件号与表空间
> ```sql
> -- MOUNT状态即可查
> SELECT file#, name, ts#, status FROM v$datafile WHERE file# = 6;
> SELECT ts#, name FROM v$tablespace WHERE ts# = <上面查出来的ts#>;
> -- 知道表空间名后再决定能否OFFLINE DROP
> ```

## 4.3.6 故障类型五：重做日志损坏

> [!warning] 重做日志损坏表现
> 启动到OPEN阶段，或实例恢复阶段报错：
> ```
> ORA-00313: open failed for members of log group 3 of thread 1
> ORA-00312: online log 3 thread 1: '/u01/.../redo03a.log'
> ORA-00312: online log 3 thread 1: '/u01/.../redo03b.log'
> -- 以及具体错误：
> ORA-27041: unable to open file / ORA-00354: corrupt redo log block header
> ```

### 1. 重做日志组状态分类

| V$LOG.STATUS | 含义 | 损坏后果 | 处理难度 |
| ---- | ---- | ---- | ---- |
| **INACTIVE** | 非当前组，已完成检查点，不再用于实例恢复 | 轻微 | ✅ 可直接DROP+重建 |
| **ACTIVE** | 刚切换不久，检查点可能还未完成 | 中等 | ⚠️ 可能需要CLEAR UNARCHIVED |
| **CURRENT** | LGWR当前正在写入的组 | **严重** | ❌ 可能需要不完全恢复+RESETLOGS，丢数据 |

### 2. 处理方案（按状态分级）

```sql
-- 查看日志组状态
SELECT group#, status, archived, members FROM v$log;
SELECT group#, member FROM v$logfile;

-- === 情况1：INACTIVE组损坏（最简单）===
-- 直接删除损坏的日志组，重建
ALTER DATABASE DROP LOGFILE GROUP 2;
ALTER DATABASE ADD LOGFILE GROUP 2 (
  '/u01/app/oracle/oradata/orcl/redo02a.log',
  '/u01/app/oracle/fast_recovery_area/orcl/redo02b.log'
) SIZE 500M BLOCKSIZE 512;

-- === 情况2：ACTIVE组损坏，且已归档 ===
-- 强制清除（需确认该组已归档！否则会丢归档链）
ALTER DATABASE CLEAR LOGFILE GROUP 2;

-- === 情况3：ACTIVE/CURRENT组损坏，无法正常清除 ===
-- 这是最严重的情况：通常是ABORT+CURRENT日志磁盘损坏同时发生
-- 处理步骤需做不完全恢复+OPEN RESETLOGS（会丢失最后未归档的事务）
-- 详见第8章备份恢复
```

> [!tip] 预防：重做日志必须多路复用
> 每个日志组至少2个成员，分别放在不同的物理磁盘/存储路径上。一个成员损坏只要组内还有其他好的成员，LGWR继续写好的，数据库完全不受影响。`V$LOGFILE`中STATUS=INVALID的坏成员可事后替换修复。

## 4.3.7 故障类型六：归档日志空间不足（ORA-00257）

> [!warning] 归档空间不足表现
> 业务正常运行中突然HANG住，或启动时报错：
> ```
> ORA-00257: archiver error. Connect internal only, until freed.
> ```
> **原因**：ARCHIVELOG模式下，FRA（Fast Recovery Area）空间满了，ARCH进程无法继续归档在线重做日志，导致LGWR被阻塞——**所有DML操作都挂起**（因为无法写重做日志）。这是生产环境的**高危故障**！

### 1. 解决方案（Oracle 19c）

**紧急处理：先备份归档再删除过期归档（释放空间）**
```bash
# (1) 先检查FRA使用率
rman target /
RMAN> REPORT NEED BACKUP;
RMAN> SHOW RETENTION POLICY;
```

```sql
-- 查看FRA使用情况
SELECT * FROM v$recovery_file_dest;
SELECT file_type, percent_space_used, number_of_files 
  FROM v$flash_recovery_area_usage;
```

```bash
# (2) 备份归档日志（有备份策略的情况下，备份后满足保留策略即可删）
rman target /
RMAN> BACKUP ARCHIVELOG ALL DELETE INPUT;   -- 备份所有归档，备份完删除输入

# 或快速：删除超过保留策略的过期归档
RMAN> CROSSCHECK ARCHIVELOG ALL;
RMAN> DELETE NOPROMPT EXPIRED ARCHIVELOG ALL;
RMAN> DELETE NOPROMPT OBSOLETE;
```

**长期方案：扩展FRA空间**
```sql
ALTER SYSTEM SET db_recovery_file_dest_size = 100G SCOPE=BOTH;   -- 调大到合适值
-- 或在OS层面给FRA所在文件系统加空间
```

> [!danger] 严禁直接用OS命令rm删除归档日志
> 直接rm会导致RMAN元数据（控制文件中）仍以为归档存在，下次备份会因找不到文件报错。**必须用RMAN的DELETE命令删除**，让RMAN同步更新控制文件。若已经rm了，补救：
> ```bash
> rman target /
> RMAN> CROSSCHECK ARCHIVELOG ALL;
> RMAN> DELETE NOPROMPT EXPIRED ARCHIVELOG ALL;
> ```

## 4.3.8 故障类型七：密码文件丢失（远程登录失败）

> [!warning] 密码文件丢失表现
> 本机`sqlplus / as sysdba`登录正常（走OS认证），但远程以SYSDBA身份登录失败：
> ```
> ERROR:
> ORA-01031: insufficient privileges
> ```
> （注意：如果是普通用户登录失败，可能是CREATE SESSION权限或账户锁定问题，不是密码文件。）

### 1. 重建密码文件（Oracle 19c，orapwd工具）

```bash
# 密码文件默认路径：$ORACLE_HOME/dbs/orapw<SID>
cd $ORACLE_HOME/dbs
ls -l orapworcl   -- 确认文件丢失或损坏

# 重建密码文件（Oracle 12c+推荐格式=12.2，支持大小写敏感密码和SYSDBA之外的SYSBACKUP等管理权限）
orapwd file=orapworcl entries=10 format=12.2 force=y
Enter password for SYS: <输入SYS新密码>
# 或非交互方式：
orapwd file=orapworcl password=SysPass123## entries=10 format=12.2 force=y
```

> [!note] 密码文件与REMOTE_LOGIN_PASSWORDFILE参数
> - `REMOTE_LOGIN_PASSWORDFILE = EXCLUSIVE`（默认）：启用密码文件，允许远程SYSDBA登录。
> - 如果设为`NONE`，则即使有密码文件，远程SYSDBA登录也会被拒绝。

## 小结

本节给出了启动故障的通用排查流程（**启动失败 → 告警日志 → ORA错误号 → 定位阶段 → V$视图 → 解决 → 验证**），并针对7类最常见启动故障（监听、参数文件、控制文件、数据文件、重做日志、归档空间、密码文件）分别给出了错误表现、根因分析与分级解决方案。掌握排查方法论+善用告警日志+V$动态视图，是DBA快速定位与解决启动故障的三大核心能力。
