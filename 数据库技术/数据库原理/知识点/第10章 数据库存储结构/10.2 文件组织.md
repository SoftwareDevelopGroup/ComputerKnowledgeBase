# 10.2 文件组织

本节解决的核心问题是：**关系表中的元组如何在存储介质上组织成文件、记录和块**。逻辑上的关系（表）需要映射为物理上的文件，记录的定长/变长存储、文件的物理组织方式直接决定了扫描、插入、查找的代价，并影响索引（[[10.3 索引结构（B+树、散列索引）]]）的选择与缓冲区（[[10.4 缓冲区管理]]）的效率。

## 10.2.1 基本概念：块、页与记录

> [!definition] 块（Block）/ 页（Page）
> **块**是存储介质与主存之间数据传输的基本单位，也是数据库在磁盘上分配空间的最小单元。在数据库实现中常称为**页**（Page）。一个块包含若干字节（典型 4 KB~16 KB），数据库读写以块为单位，不会只读写一条记录。
>
> 块与操作系统页面（OS page）概念相近，但 DBMS 通常自行管理数据块，以获得更精细的控制。

| 概念 | 含义 | 典型大小 |
| ---- | ---- | ---- |
| 扇区 | 磁盘硬件最小读写单位 | 512 B / 4 KB |
| 块 / 页 | DBMS 最小 I/O 单位 | 4 KB / 8 KB / 16 KB |
| 记录 | 一个元组在存储上的表示 | 不定（视字段） |

> [!note] MySQL InnoDB 的页大小
> InnoDB 默认页大小为 **16 KB**，可通过 `innodb_page_size` 参数配置（可选 4K/8K/16K/32K/64K，5.7+）。页是 InnoDB 管理存储空间的基本单位，B+ 树每个节点即一个或多个页。环境：MySQL 8.0 InnoDB。

## 10.2.2 记录的存储结构

### 1. 定长记录与变长记录

> [!definition] 定长记录（Fixed-Length Record）
> 每条记录占用相同且固定的字节数。每个字段按固定偏移定位，存取简单、计算偏移即可定位字段，适合所有字段长度固定的关系。

> [!definition] 变长记录（Variable-Length Record）
> 记录长度可变，通常因为含有变长字段（如 `VARCHAR`、`TEXT`、`BLOB`）或字段数可变。需额外的长度信息或指针来定位字段。

| 维度 | 定长记录 | 变长记录 |
| ---- | ---- | ---- |
| 记录长度 | 固定 | 可变 |
| 字段定位 | 固定偏移，直接计算 | 需长度前缀或指针数组 |
| 空间利用 | 可能浪费（短值填不满） | 紧凑，节省空间 |
| 实现复杂度 | 低 | 较高 |
| 适用 | 字段类型固定（如 CHAR、INT） | 含 VARCHAR/TEXT/BLOB |

### 2. 跨块记录与非跨块记录

一条记录可能跨越多个块：

- **非跨块记录（Non-spanned）**：记录不跨块边界，必须完整存放在一个块内。实现简单，但可能浪费块尾空间（记录放不下当前块就只能放到下一块）。
- **跨块记录（Spanned）**：允许一条记录跨越多个块，块尾可存放记录的一部分并指向下一块。空间利用率高，但实现与更新复杂。

> [!warning] 易错点
> 多数现代 DBMS（含 InnoDB）采用**非跨块**策略：若行过长则使用**溢出页**（overflow page）存放变长字段主体，行内只保留指针。InnoDB 中一行最长约半个页（默认 16 KB 页时约 8 KB），超出部分走溢出页。

## 10.2.3 块与记录的映射

一个块由**块头（Block Header）**和**记录区**组成。块头记录块的元信息，例如：

- 块标识、所属关系（表/索引）；
- 块中记录数目；
- 自由空间的起始偏移与可用字节数；
- 记录偏移表（每条记录在块内的位置）。

> [!example] 块内组织示意
> ```text
> +-----------------------------------+
> | 块头(块ID/记录数/空闲指针)        |
> +-----------------------------------+
> | 记录偏移表 (offset_1, offset_2,…)  |
> +-----------------------------------+
> | 记录区: R1  R2  R3  ...            |
> +---------------+-------------------+
> | ... 空闲空间 ...  |  增长方向 ↑       |
> +-----------------------------------+
> ```
> 偏移表自上向下增长，记录自下向上（或反之）写入，使插入只需调整偏移表。

## 10.2.4 文件结构类型

文件组织决定记录在文件中的物理排列方式。常见四种：

### 1. 堆文件（Heap File）

> [!definition] 堆文件
> 记录按插入顺序无序存放，新记录追加到文件末尾（或任意有空闲空间的块）。查找需**全表扫描**，无序。

- 优点：插入快（$O(1)$ 追加）；
- 缺点：查找慢（$O(n)$ 扫描），不支持范围查询；
- 适用：临时表、小表、数据加载阶段。

### 2. 顺序文件（Sequential File）

> [!definition] 顺序文件
> 记录按**排序码（ordering field）**有序存放，通常是主码或某查询字段。记录之间用指针链接或物理相邻。

- 优点：按排序码查找与范围查询快；
- 缺点：插入需维护有序性（常配合溢出区+定期重组）；
- 适用：按某字段频繁范围查询的场景。

### 3. 散列文件（Hash File）

> [!definition] 散列文件
> 记录通过**散列函数**映射到桶（bucket），同桶记录放在同一块或溢出块。按散列码等值查找快。

- 优点：等值查询接近 $O(1)$；
- 缺点：不支持范围查询；桶溢出需处理；
- 适用：等值查询为主的场景。详见 [[10.3 索引结构（B+树、散列索引）]]。

### 4. 聚簇文件（Clustered File）

> [!definition] 聚簇文件
> 将一个或多个相关关系的记录按**聚簇码（cluster key）**物理上存放在一起，使经常一起访问的数据位于相邻块，减少 I/O。

- 优点：连接查询性能高（相关记录同块）；
- 缺点：只对聚簇码有利，其他查询无益；插入维护成本高；
- 适用：频繁连接的关系对。

### 四种文件组织对比

| 文件类型 | 记录顺序 | 等值查找 | 范围查询 | 插入代价 | 典型场景 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| 堆文件 | 无序 | 慢（扫描） | 不支持 | 最快 | 临时表、小表 |
| 顺序文件 | 按码有序 | 较快（二分） | 快 | 较慢（维护有序） | 范围查询 |
| 散列文件 | 按桶分布 | 快 | 不支持 | 中 | 等值查询 |
| 聚簇文件 | 按聚簇码聚集 | 视码 | 视码 | 较慢 | 连接查询 |

## 10.2.5 MySQL InnoDB 的存储组织

InnoDB 采用**索引组织表（Index Organized Table, IOT）**模式：

> [!note] InnoDB 表 = 聚簇索引
> InnoDB 中表数据**按主键组织为聚簇索引**（一棵 B+ 树），叶子节点存放完整行数据。因此 InnoDB 表即聚簇索引，辅助索引叶子节点存储的是**主键值**而非行指针（回表机制详见 [[10.3 索引结构（B+树、散列索引）]]）。
>
> - 没有显式主键时，InnoDB 会选择第一个非空唯一索引；若都没有，则自动生成 6 字节 `ROW_ID` 作为隐式主键；
> - 每个页默认 16 KB，行数据存于页内，溢出部分走溢出页。

```sql
-- 查看 InnoDB 页大小（MySQL 8.0）
SHOW VARIABLES LIKE 'innodb_page_size';
-- 默认 16384（即 16 KB）
```

## 小结

本节将逻辑"关系"映射到物理"文件-块-记录"三层。定长/变长记录、跨块/非跨块、堆/顺序/散列/聚簇四种文件组织各有取舍；InnoDB 的索引组织表设计是"表即聚簇索引"这一关键事实，它解释了为什么辅助索引要回表、为什么主键应尽量短。这些机制直接决定后续索引结构与查询优化。
