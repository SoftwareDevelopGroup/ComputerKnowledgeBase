# 5.5 触发器实现完整性

实体完整性、参照完整性、用户定义完整性（前四节）都是声明式约束，简单高效，但表达能力有限——`CHECK` 不能跨元组或跨表，外码只能表达简单的引用关系。实际业务中存在大量复杂规则："工资不得低于本部门最低工资"、"删除员工时同时删除其日志记录并写入审计表"、"工资只能升不能降"。这些**跨表、跨元组、依赖状态变迁**的约束需要过程式手段实现，**触发器（Trigger）** 是 DBMS 提供的标准机制。本节是第5章重点，介绍触发器的概念、组成、CREATE TRIGGER 语法与典型应用，并对比触发器与声明式约束的优劣。

## 一、触发器的概念

> [!definition] 触发器（Trigger）
> 一种特殊的存储过程，由 DBMS 在用户对表执行特定操作（INSERT/UPDATE/DELETE）时**自动激活**执行。触发器基于**"事件-条件-动作"（Event-Condition-Action, ECA）模型**，无需用户显式调用。

触发器与普通存储过程的区别：

| 对比项 | 触发器 | 存储过程 |
| ---- | ---- | ---- |
| 触发方式 | 事件自动触发 | 用户显式调用（CALL） |
| 参数 | 无显式参数（通过 NEW/OLD 访问） | 可有显式参数 |
| 用途 | 完整性约束、审计、级联操作 | 业务逻辑封装 |
| 是否可独立调用 | 否 | 是 |

## 二、事件-条件-动作模型

> [!important] 触发器的 ECA 模型
> 触发器由三要素组成：
> 1. **事件（Event）**：触发触发器的操作，由"时机 + 类型"组成；
> 2. **条件（Condition）**：触发时需满足的条件（部分 DBMS 支持 WHEN 子句，MySQL 用 IF/WHEN 体内判断）；
> 3. **动作（Action）**：满足条件时执行的 SQL 语句块。

### 2.1 触发器组成

| 维度 | 取值 | 说明 |
| ---- | ---- | ---- |
| 时机 | BEFORE / AFTER | 在事件之前 / 之后执行 |
| 事件 | INSERT / UPDATE / DELETE | 触发操作类型 |
| 粒度 | FOR EACH ROW / FOR EACH STATEMENT | 行级 / 语句级（MySQL 仅支持行级） |
| 主体 | BEGIN ... END 语句块 | 触发时执行的逻辑 |

组合矩阵：

| | INSERT | UPDATE | DELETE |
| ---- | ---- | ---- | ---- |
| BEFORE | BEFORE INSERT | BEFORE UPDATE | BEFORE DELETE |
| AFTER | AFTER INSERT | AFTER UPDATE | AFTER DELETE |

### 2.2 NEW 与 OLD 行变量

| 事件 | OLD（旧值） | NEW（新值） |
| ---- | ---- | ---- |
| INSERT | 不可用 | 新插入的行 |
| UPDATE | 更新前的旧值 | 更新后的新值 |
| DELETE | 被删除的旧值 | 不可用 |

> [!note] BEFORE vs AFTER 的应用差异
> - **BEFORE 触发器**：在数据写入**前**触发，可**修改 NEW 值**（如自动填充默认值、校验并修正），常用于数据预处理与约束检查（违约可拒绝操作）。
> - **AFTER 触发器**：在数据写入**后**触发，无法修改已写入数据，常用于审计、级联操作、日志记录。

## 三、CREATE TRIGGER 语法

### 3.1 MySQL 8.0 语法

```sql
-- MySQL 8.0 触发器语法
CREATE TRIGGER 触发器名
{BEFORE | AFTER} {INSERT | UPDATE | DELETE}
ON 表名
FOR EACH ROW
[WHEN (条件)]              -- MySQL 不支持 WHEN 子句，需在主体中用 IF
BEGIN
    -- 触发器主体：可使用 NEW.列名 / OLD.列名 访问新旧值
    SQL 语句;
END;
```

> [!warning] MySQL 触发器的限制
> 1. MySQL 仅支持**行级触发器**（FOR EACH ROW），不支持语句级触发器；
> 2. MySQL 不支持 WHEN 子句，条件判断需用 `IF ... THEN ... END IF` 在主体内实现；
> 3. MySQL 触发器主体中**不能使用事务控制语句**（COMMIT/ROLLBACK/START TRANSACTION），也**不能返回结果集**；
> 4. 同一表同一事件同一时机的触发器，MySQL 不允许多个（可通过组合时机/事件规避）。

### 3.2 修改分隔符

触发器主体使用 `BEGIN ... END` 包含多条语句，需用 `DELIMITER` 临时改变语句分隔符，避免分号提前结束触发器定义：

```sql
-- 修改分隔符为 //
DELIMITER //

CREATE TRIGGER trg_check_age
BEFORE INSERT ON Student
FOR EACH ROW
BEGIN
    IF NEW.Sage < 0 OR NEW.Sage > 150 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '年龄必须在 0-150 之间';
    END IF;
END; //

DELIMITER ;
```

## 四、触发器实现复杂完整性约束的示例

### 4.1 示例表结构

```sql
-- MySQL 8.0，使用 scdb 数据库
USE scdb;

-- 员工表
CREATE TABLE Employee (
    EmpID    CHAR(9)        PRIMARY KEY,
    Name     VARCHAR(20)   NOT NULL,
    Dept     VARCHAR(20)   NOT NULL,
    Salary   DECIMAL(10,2) NOT NULL,
    UpdateTime DATETIME
);

-- 部门表（含部门最低工资）
CREATE TABLE Department (
    DeptName   VARCHAR(20) PRIMARY KEY,
    MinSalary  DECIMAL(10,2) NOT NULL,           -- 该部门最低工资
    ManagerID  CHAR(9)
);

-- 员工工资变更历史表（审计）
CREATE TABLE SalaryLog (
    LogID    INT AUTO_INCREMENT PRIMARY KEY,
    EmpID    CHAR(9),
    OldSalary DECIMAL(10,2),
    NewSalary DECIMAL(10,2),
    ChangeTime DATETIME DEFAULT CURRENT_TIMESTAMP,
    Operator   VARCHAR(50)
);
```

### 4.2 示例 1：BEFORE 触发器——工资不得低于本部门最低工资

> [!example] 跨表完整性约束
> 该约束需查询 Department 表的 MinSalary，CHECK 约束无法实现（不能跨表），用触发器实现。

```sql
DELIMITER //

CREATE TRIGGER trg_check_salary_before_insert
BEFORE INSERT ON Employee
FOR EACH ROW
BEGIN
    DECLARE v_min_salary DECIMAL(10,2);
    SELECT MinSalary INTO v_min_salary
    FROM Department WHERE DeptName = NEW.Dept;
    
    IF NEW.Salary < v_min_salary THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = '工资不得低于本部门最低工资';
    END IF;
END; //

DELIMITER ;

-- 测试
INSERT INTO Department VALUES ('研发部', 6000.00, NULL);
INSERT INTO Employee VALUES ('E001','张三','研发部',5000.00, NULL);
-- ERROR 1644 (45000): 工资不得低于本部门最低工资

INSERT INTO Employee VALUES ('E001','张三','研发部',6500.00, NOW());   -- 成功
```

### 4.3 示例 2：BEFORE 触发器——工资只能升不能降（动态约束）

> [!example] 动态完整性约束
> 该约束涉及状态变迁（旧值 → 新值），是动态约束，CHECK 只能检查静态值无法比较新旧值，用 BEFORE UPDATE 触发器实现。

```sql
DELIMITER //

CREATE TRIGGER trg_salary_not_decrease
BEFORE UPDATE ON Employee
FOR EACH ROW
BEGIN
    IF NEW.Salary < OLD.Salary THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = '工资只能升不能降';
    END IF;
END; //

DELIMITER ;

-- 测试
UPDATE Employee SET Salary = 6000.00 WHERE EmpID = 'E001';
-- ERROR 1644: 工资只能升不能降

UPDATE Employee SET Salary = 7000.00 WHERE EmpID = 'E001';    -- 成功
```

### 4.4 示例 3：AFTER 触发器——工资变更审计日志

> [!example] AFTER 触发器实现审计
> 工资变更后自动记录到 SalaryLog 表，实现审计功能。这是 [[4.4 视图机制、审计]] 中审计的另一种实现方式。

```sql
DELIMITER //

CREATE TRIGGER trg_salary_audit_after_update
AFTER UPDATE ON Employee
FOR EACH ROW
BEGIN
    IF NEW.Salary <> OLD.Salary THEN
        INSERT INTO SalaryLog(EmpID, OldSalary, NewSalary, Operator)
        VALUES (OLD.EmpID, OLD.Salary, NEW.Salary, CURRENT_USER());
    END IF;
END; //

DELIMITER ;

-- 测试
UPDATE Employee SET Salary = 7500.00 WHERE EmpID = 'E001';
-- 触发器自动在 SalaryLog 中插入一条记录

SELECT * FROM SalaryLog;
-- LogID | EmpID | OldSalary | NewSalary | ChangeTime         | Operator
-- 1     | E001  | 6500.00   | 7500.00   | 2026-08-02 ...     | root@localhost
```

### 4.5 示例 4：BEFORE 触发器——自动填充UpdateTime

```sql
DELIMITER //

CREATE TRIGGER trg_set_updatetime
BEFORE UPDATE ON Employee
FOR EACH ROW
BEGIN
    SET NEW.UpdateTime = NOW();
END; //

DELIMITER ;

-- 之后任何 UPDATE 都会自动更新 UpdateTime
UPDATE Employee SET Salary = 8000.00 WHERE EmpID = 'E001';
SELECT UpdateTime FROM Employee WHERE EmpID = 'E001';   -- 自动更新为当前时间
```

## 五、触发器与约束的对比

| 对比项 | 声明式约束（PRIMARY KEY/FOREIGN KEY/CHECK） | 触发器 |
| ---- | ---- | ---- |
| 定义方式 | DDL 声明 | 过程式代码 |
| 表达能力 | 简单、固定模式 | 灵活强大，可表达任意逻辑 |
| 跨表约束 | 仅外码能简单引用 | 可查询任意表 |
| 跨元组约束 | 不支持 | 支持（可聚合查询本表） |
| 动态约束（状态变迁） | 不支持 | 支持（OLD/NEW 比较） |
| 性能 | 高（DBMS 内部优化） | 较低（每行触发执行） |
| 开发与维护成本 | 低 | 高（需编程、调试） |
| 可移植性 | 高（SQL 标准） | 低（各 DBMS 语法差异大） |
| 调试难度 | 容易 | 困难（隐式执行、难追踪） |
| 典型场景 | 实体、参照、简单 CHECK | 复杂业务规则、审计、级联 |

> [!warning] 触发器使用原则
> 1. **优先用约束**：能用声明式约束表达的，不要用触发器；
> 2. **触发器用于约束无法覆盖的场景**：跨表约束、动态约束、复杂条件级联、审计日志；
> 3. **避免触发器链**：触发器内操作可能激活其他触发器，形成链式触发，难以调试且性能差；
> 4. **注意递归触发**：触发器内对本表的操作可能再次激活自身，导致无限递归（MySQL 默认禁止递归触发）；
> 5. **生产环境慎用**：触发器是隐式执行的"魔法"，会显著增加系统复杂度与调试难度。

## 六、触发器的管理

```sql
-- 查看数据库中所有触发器
SHOW TRIGGERS;

-- 查询 information_schema.TRIGGERS
SELECT TRIGGER_NAME, EVENT_MANIPULATION, EVENT_OBJECT_TABLE, ACTION_TIMING
FROM information_schema.TRIGGERS
WHERE TRIGGER_SCHEMA = 'scdb';

-- 删除触发器
DROP TRIGGER IF EXISTS trg_check_salary_before_insert;
```

## 小结

- 触发器是基于"事件-条件-动作"模型自动激活的特殊存储过程，用于实现复杂完整性约束。
- 触发器由时机（BEFORE/AFTER）+ 事件（INSERT/UPDATE/DELETE）+ 粒度（行级/语句级）+ 主体组成。
- BEFORE 触发器可修改 NEW 值、用于约束检查；AFTER 触发器用于审计、级联。
- MySQL 仅支持行级触发器，不支持 WHEN 子句，主体中不能使用事务控制语句。
- 触发器能实现 CHECK 无法表达的跨表约束、动态约束、审计；但性能开销大、调试困难，应优先用声明式约束。
