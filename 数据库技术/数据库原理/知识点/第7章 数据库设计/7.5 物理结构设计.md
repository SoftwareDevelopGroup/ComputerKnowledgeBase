# 7.5 物理结构设计

物理结构设计为逻辑结构设计得到的关系模式选取**合适的物理存储结构与存取方法**，使其在给定 DBMS 与硬件环境下达到性能、空间与维护代价的平衡。本节是设计阶段的最后一步，回答"数据存在哪里、用什么方式存取、是否建索引、如何评价优劣"。物理设计的产物是可直接用于 [[7.6 数据库实施]] 建库的物理结构说明（含索引方案与系统配置）。

## 物理结构设计的任务

> [!definition] 物理结构设计
> 数据库在物理设备上的存储结构与存取方法称为数据库的物理结构。物理结构设计就是为给定的逻辑数据模型选取一个最适合应用环境的物理结构的过程。

> [!note] 物理设计的两个核心任务
> 1. **确定数据库的物理结构**：存储记录结构、存储位置、存取方法（索引）、系统配置等。
> 2. **评价物理结构**：从时间效率、空间效率、维护代价三方面评价，若不满足要求则修改设计。
>
> 物理设计依赖于具体 DBMS，本章以 MySQL 8.0（InnoDB 存储引擎）为例说明。

## 确定数据库物理结构

物理结构设计的主要内容：

| 内容 | 说明 | MySQL 8.0 中的体现 |
| ---- | ---- | ---- |
| **存储记录结构** | 字段的类型、长度、是否可空、压缩方式 | `VARCHAR`、`INT`、`CHAR` 等类型选择，行格式 `DYNAMIC`/`COMPRESSED` |
| **存储位置** | 数据、索引、日志的物理存放 | `innodb_data_home_dir`、表空间 `TABLESPACE` |
| **存取方法（索引）** | 为哪些字段建索引、建什么类型索引 | `CREATE INDEX`、`PRIMARY KEY`、`UNIQUE`、`FULLTEXT` |
| **系统配置** | 缓冲区、并发、日志等参数 | `innodb_buffer_pool_size`、`max_connections` |

> [!tip] 物理设计的基本原则
> - **以查询为主**：优先为 WHERE、JOIN、ORDER BY 频繁出现的字段建索引；
> - **以更新为主**：少建索引（索引增加更新代价）；
> - **大表小索引**：索引本身也占空间，应控制索引数量与字段长度；
> - **复合索引遵循最左前缀**：把区分度高的字段放左边。

## 关系模式存取方法选择

存取方法（Access Method）是 DBMS 检索数据的底层机制，主要由**索引**实现。常见索引类型：

### B+ 树索引

> [!definition] B+ 树索引
> B+ 树是一种平衡多路查找树，所有数据存于叶节点，叶节点按关键字排序并用链表连接。B+ 树索引支持**等值查询**与**范围查询**，是关系数据库最常用的索引结构。

特点：
- 查询复杂度 $O(\log n)$，稳定；
- 支持等值、范围、前缀匹配查询；
- 叶节点链表便于范围扫描；
- 维护代价中等，插入删除可能引起节点分裂与合并。

> [!note] MySQL InnoDB 的 B+ 树
> InnoDB 的所有索引都是 B+ 树。InnoDB 区分：
> - **聚簇索引**（主键索引）：叶节点存储**完整行数据**；
> - **二级索引**（非主键索引）：叶节点存储**主键值**，查询时需"回表"（用主键再查一次聚簇索引）。

### 聚簇索引（Cluster Index）

> [!definition] 聚簇索引
> 聚簇索引（Cluster Index）将**数据行本身按索引顺序物理存储**，即索引与数据合为一体。一张表**只能有一个聚簇索引**，因为数据只能按一种顺序物理排列。

特点：
- 查询主键极快（一次 B+ 树查找即可定位行）；
- 范围查询连续存储，IO 高效；
- 主键值应**短且单调递增**，避免插入引起大量数据移动；
- InnoDB 中**主键即聚簇索引**；若无主键，InnoDB 会选第一个 NOT NULL 唯一索引；若都没有，会生成隐藏的 6 字节 `ROWID`。

> [!example] InnoDB 主键选择建议
> - 推荐 `BIGINT AUTO_INCREMENT` 作为代理主键，单调递增、短小；
> - 避免用 UUID 作主键——UUID 随机分布，插入会引起 B+ 树大量页分裂，性能下降；
> - 避免用业务字段（如身份证号、手机号）作主键——字段长且可能变更。

### Hash 索引

> [!definition] Hash 索引
> Hash 索引基于哈希表，对索引字段计算哈希值后定位数据。**仅支持等值查询**，不支持范围查询与排序。

特点：
- 等值查询复杂度 $O(1)$，极快；
- **不支持**范围、排序、前缀匹配；
- 存在哈希冲突，冲突多时性能退化；
- MySQL Memory 引擎原生支持 Hash 索引；InnoDB 通过**自适应哈希索引**（Adaptive Hash Index）在内存中自动为热点 B+ 树页建 Hash 索引。

### 三种索引对比

| 索引类型 | 查询类型 | 复杂度 | 范围查询 | 排序 | 一表可建数量 | 典型场景 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| **B+ 树索引** | 等值/范围/排序 | $O(\log n)$ | ✓ | ✓ | 多个 | 通用场景 |
| **聚簇索引** | 等值/范围/排序 | $O(\log n)$ | ✓（连续存储） | ✓ | **1 个** | 主键 |
| **Hash 索引** | 仅等值 | $O(1)$ | ✗ | ✗ | 多个 | 内存表、键值查询 |

> [!tip] 索引选择的工程建议
> 1. **主键**：选短小、单调递增的整型，自动成为聚簇索引；
> 2. **外键**：建议建 B+ 树索引，加速 JOIN 与参照完整性检查；
> 3. **频繁查询条件**：WHERE 子句中频繁出现的字段建索引；
> 4. **复合索引**：按区分度从高到低排列字段，遵循最左前缀原则；
> 5. **避免过度索引**：每增一个索引，更新/删除/插入都多一份维护成本，且占空间；
> 6. **避免在低区分度字段建单列索引**：如性别（只有"男/女"），索引效果差。

## 物理结构设计的评价

> [!note] 三方面评价指标
> 物理设计完成后需从三方面评价，不满足则返回修改：

| 评价维度 | 指标 | 优化方向 |
| ---- | ---- | ---- |
| **时间效率** | 查询响应时间、吞吐量 | 加索引、优化 SQL、调整缓冲区 |
| **空间效率** | 数据与索引占用空间 | 选择合适字段类型、压缩、控制索引数量 |
| **维护代价** | 更新、插入、删除的代价，备份恢复时间 | 减少冗余索引、合理安排备份策略 |

> [!warning] 评价中的权衡
> 三方面常相互冲突：
> - 加索引提升查询时间，但增加更新代价与空间占用；
> - 反规范化（冗余）提升查询性能，但增加空间与一致性维护代价；
> - 物理设计本质是在三方面间找平衡，需根据应用特征（读写比例、查询模式）权衡。

## MySQL 8.0 中索引创建示例

承接 [[7.4 逻辑结构设计]] 的关系模式，给出索引创建脚本：

```sql
-- DBMS: MySQL 8.0 (InnoDB)

-- 1. 主键索引（自动创建为聚簇索引）
CREATE TABLE Student (
    Sno  CHAR(8)     NOT NULL,
    Sname VARCHAR(20) NOT NULL,
    Ssex CHAR(2)     DEFAULT '男',
    Sage INT         DEFAULT 18,
    Dno  CHAR(4),
    PRIMARY KEY (Sno),                       -- 聚簇索引
    CONSTRAINT fk_student_dept FOREIGN KEY (Dno)
        REFERENCES Dept(Dno)
) ENGINE=InnoDB;

CREATE TABLE Course (
    Cno     CHAR(6)     NOT NULL,
    Cname   VARCHAR(40) NOT NULL,
    Ccredit INT         DEFAULT 2,
    Tno     CHAR(6),
    PRIMARY KEY (Cno),                       -- 聚簇索引
    CONSTRAINT fk_course_teacher FOREIGN KEY (Tno)
        REFERENCES Teacher(Tno)
) ENGINE=InnoDB;

CREATE TABLE SC (
    Sno   CHAR(8) NOT NULL,
    Cno   CHAR(6) NOT NULL,
    Grade DECIMAL(5,2),
    PRIMARY KEY (Sno, Cno),                  -- 复合主键（聚簇索引）
    CONSTRAINT fk_sc_student FOREIGN KEY (Sno) REFERENCES Student(Sno),
    CONSTRAINT fk_sc_course  FOREIGN KEY (Cno) REFERENCES Course(Cno)
) ENGINE=InnoDB;

-- 2. 二级索引（B+ 树）
-- 为外键 Dno 建索引，加速按系查询学生
CREATE INDEX idx_student_dno ON Student(Dno);

-- 为外键 Tno 建索引，加速教师查询所授课程
CREATE INDEX idx_course_tno ON Course(Tno);

-- 为成绩建索引，加速按成绩范围查询
CREATE INDEX idx_sc_grade ON SC(Grade);

-- 3. 复合索引（按查询模式设计）
-- 常见查询：按系查询学生姓名与年龄，按姓名排序
CREATE INDEX idx_student_dno_sname ON Student(Dno, Sname);

-- 4. 唯一索引（业务约束）
-- 教师姓名不可重复（假设业务要求）
CREATE UNIQUE INDEX uk_teacher_tname ON Teacher(Tname);

-- 5. 全文索引（文本检索）
-- 课程名全文检索（用于模糊查询课程名）
CREATE FULLTEXT INDEX ft_course_cname ON Course(Cname);
```

> [!example] 索引选择分析
> - `Student` 主键 `Sno` 自动成为聚簇索引，等值查询学号 $O(\log n)$；
> - `idx_student_dno` 加速"查询某系学生"的 JOIN 与 WHERE；
> - `idx_student_dno_sname` 复合索引支持"查询某系学生并按姓名排序"，覆盖索引避免回表；
> - `idx_sc_grade` 加速"查询成绩在 80 分以上的选课记录"；
> - `uk_teacher_tname` 既加速查询又保证业务唯一性；
> - `ft_course_cname` 支持 `MATCH ... AGAINST` 全文检索。

> [!warning] 索引失效的常见场景
> 即使建了索引，以下情况索引可能不生效：
> 1. 对索引字段使用函数或运算：`WHERE YEAR(birth) = 2000`；
> 2. 对索引字段使用 `LIKE '%xxx'`（前导通配符）；
> 3. 复合索引未遵循最左前缀：复合索引 `(A, B, C)`，查询只用 `B` 或 `C`；
> 4. 类型隐式转换：字段是 `VARCHAR`，查询用 `WHERE sno = 123`（数字）；
> 5. `OR` 连接的条件中有一个无索引。
>
> 应使用 `EXPLAIN` 检查执行计划，确认索引是否被使用。

## 物理结构设计示例

承接学生-课程-教师-系示例，物理设计结论：

| 表 | 主键（聚簇索引） | 二级索引 | 理由 |
| ---- | ---- | ---- | ---- |
| `Student` | `Sno` | `idx_student_dno`、`idx_student_dno_sname` | 按系查询、按姓名排序频繁 |
| `Course` | `Cno` | `idx_course_tno`、`ft_course_cname` | 教师查询所授课程、课程名检索 |
| `Teacher` | `Tno` | `uk_teacher_tname` | 业务唯一约束 |
| `Dept` | `Dno` | — | 表小，无需额外索引 |
| `SC` | `(Sno, Cno)` | `idx_sc_grade`、`idx_sc_cno`（外键索引） | 成绩范围查询、按课程统计选课人数 |

## 小结

> [!summary] 本节核心
> 1. 物理结构设计为逻辑模式选取物理存储结构与存取方法，并评价时间、空间、维护三方面代价。
> 2. 物理结构包括存储记录结构、存储位置、存取方法（索引）、系统配置。
> 3. 三种索引：B+ 树（通用，支持等值/范围/排序）、聚簇索引（数据按索引物理排列，一表一个）、Hash（仅等值，$O(1)$）。
> 4. InnoDB 中主键即聚簇索引，二级索引叶节点存主键值需回表。
> 5. 索引选择遵循：主键短小递增、外键建索引、复合索引按区分度排列、避免过度索引。
> 6. MySQL 8.0 用 `CREATE INDEX` 创建索引，用 `EXPLAIN` 验证索引使用情况。
