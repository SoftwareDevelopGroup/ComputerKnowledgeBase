# 7.7 数据库运行与维护

数据库试运行通过并正式投入生产后，即进入**运行与维护阶段**。这是数据库生命周期中**持续时间最长**的阶段，由 DBA（数据库管理员）负责日常维护，保证数据库**安全、稳定、高效**运行。本节是六阶段的最后一节，回答"数据库上线后做什么、维护包括哪些工作、重组与重构有何区别"。

## 数据库运行维护的任务

> [!definition] 数据库运行维护的任务
> 数据库运行维护的任务由 DBA 完成，主要包括：
> 1. **数据库的转储与恢复**：定期备份，发生故障时恢复；
> 2. **数据库安全性、完整性控制**：管理用户权限，维护完整性约束；
> 3. **数据库性能的监督、分析与改进**：监控运行状态，优化性能；
> 4. **数据库的重组与重构**：根据需要整理存储或调整逻辑结构。

> [!note] 运行维护的重要性
> - 数据库是企业的核心资产，停机或数据丢失会造成重大损失；
> - 业务与数据量随时间增长，初始设计不可能永久满足需求；
> - DBA 的运维工作保证数据库长期可用、高效、安全。
>
> 运行维护阶段涉及的技术（恢复、并发控制）是 [[MOC - 第8章]] 与 [[MOC - 第9章]] 的内容，本节只做工程层面的概述。

## 维护工作内容

### 1. 数据库转储与恢复

> [!definition] 转储与恢复
> **转储**（Dump）是 DBA 定期将数据库全部或部分内容复制到磁带、磁盘或其他存储介质的过程，是数据库恢复的基础。**恢复**（Recovery）是在数据库发生故障后，利用转储副本与日志将数据库恢复到故障前一致状态的过程。

| 转储类型 | 含义 | 特点 |
| ---- | ---- | ---- |
| **海量转储** | 转储全部数据库 | 简单，恢复快，但转储时间长 |
| **增量转储** | 只转储上次转储后变化的部分 | 转储快，但恢复需结合多个备份 |
| **静态转储** | 转储期间无事务运行 | 一致性好，但需停机 |
| **动态转储** | 转储期间允许事务运行 | 不停机，但需日志保证一致性 |

> [!tip] 实践中的转储策略
> - **完整备份 + 增量备份**：每周一次完整备份，每天一次增量备份；
> - **热备份**：使用 `mysqldump --single-transaction` 或 Percona XtraBackup，不停机备份；
> - **异地备份**：备份副本应存放异地，防止单点灾害；
> - **定期演练**：定期恢复演练，验证备份可用性。
>
> 详细恢复机制见 [[MOC - 第8章|第8章 数据库恢复技术]]。

```sql
-- MySQL 8.0 备份示例（命令行）
-- 完整逻辑备份
-- mysqldump -u root -p CourseSelection > backup_full.sql

-- 增量备份依赖二进制日志（binlog）
-- 查看当前 binlog 位置
SHOW MASTER STATUS;
```

### 2. 安全性、完整性控制

> [!note] 安全性与完整性维护
> - **安全性**：管理用户、角色与权限，定期审计访问日志，及时撤销离职用户权限；
> - **完整性**：随业务变化调整约束（如新增字段约束、修改 CHECK 条件）。
>
> 详见 [[4.3 存取控制]]、[[4.4 视图机制、审计]]、[[5.1 完整性约束概念]]。

```sql
-- 用户与权限管理示例
CREATE USER 'app_user'@'%' IDENTIFIED BY 'strong_password';
GRANT SELECT, INSERT, UPDATE ON CourseSelection.* TO 'app_user'@'%';
REVOKE DELETE ON CourseSelection.* FROM 'app_user'@'%';

-- 审计（需启用 audit 插件）
-- 记录敏感操作日志
```

### 3. 性能监督、分析与改进

> [!definition] 性能监督
> DBA 需持续监控数据库运行状态，发现性能瓶颈并优化。主要监控指标：
> - 查询响应时间、慢查询数量；
> - 锁等待与死锁；
> - 缓冲区命中率；
> - 磁盘 IO 与 CPU 利用率；
> - 连接数与并发数。

| 监控工具 | 用途 | MySQL 8.0 示例 |
| ---- | ---- | ---- |
| **慢查询日志** | 记录执行时间长的 SQL | `slow_query_log = ON` |
| **EXPLAIN** | 分析查询执行计划 | `EXPLAIN SELECT ...` |
| **Performance Schema** | 监控数据库内部运行状态 | `performance_schema = ON` |
| **SHOW STATUS** | 查看数据库状态变量 | `SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%'` |
| **第三方工具** | 可视化监控 | Prometheus + Grafana、PMOMySQL |

> [!tip] 性能优化方向
> 1. **SQL 优化**：重写低效 SQL，使用合适的索引（见 [[7.5 物理结构设计]]）；
> 2. **索引优化**：添加缺失索引，删除无用索引，重建碎片化索引；
> 3. **配置优化**：调整 `innodb_buffer_pool_size`、`max_connections` 等参数；
> 4. **硬件升级**：SSD、扩内存、增加 CPU；
> 5. **分库分表**：超大规模数据考虑水平拆分（超出本章范围）。

### 4. 数据库的重组与重构

> [!warning] 重组 vs 重构（重要区分）
> 这是两个常被混淆的概念：

| 项目 | 数据库重组（Reorganization） | 数据库重构（Restructuring） |
| ---- | ---- | ---- |
| **定义** | 整理数据库的**物理存储**，消除碎片、回收空间 | 调整数据库的**逻辑结构**，修改模式 |
| **层次** | 物理层 | 逻辑层 |
| **是否改模式** | 否（模式不变） | 是（模式变化） |
| **触发原因** | 长期增删改导致存储碎片、性能下降 | 业务变化、新增需求、规范化调整 |
| **影响** | 不影响应用程序 | 可能影响应用程序，需同步修改 |
| **频率** | 较高（定期执行） | 较低（业务变化时） |
| **示例** | 重建索引、整理表空间、压缩数据 | 新增字段、拆分表、合并表、修改约束 |

#### 数据库重组

> [!definition] 数据库重组
> 数据库重组是在不改变数据库逻辑模式的前提下，重新组织数据库的物理存储，以消除因长期增删改产生的碎片，提升性能。

> [!note] 重组的必要性
> 频繁的 INSERT、UPDATE、DELETE 会导致：
> - B+ 树索引页分裂，索引碎片化；
> - 表数据页出现空洞；
> - 物理存储顺序与逻辑顺序不一致，IO 效率下降。
>
> 重组可消除碎片、回收空间、恢复性能。

```sql
-- MySQL 8.0 重组操作示例

-- 重建表（重组数据与索引，回收空间）
OPTIMIZE TABLE Student;
OPTIMIZE TABLE SC;

-- 重建索引（消除索引碎片）
-- MySQL 8.0 不支持 REINDEX，用 ALTER TABLE ... ENGINE=InnoDB 或重建索引
ALTER TABLE SC DROP INDEX idx_sc_grade, ADD INDEX idx_sc_grade (Grade);

-- 分析表（更新统计信息，帮助优化器）
ANALYZE TABLE Student;
ANALYZE TABLE Course;
```

#### 数据库重构

> [!definition] 数据库重构
> 数据库重构是在不改变数据库语义的前提下，**修改数据库的逻辑模式**，以适应业务变化或改进设计。

重构的常见场景：
- **新增字段**：业务要求记录新信息，如学生表加 `Email`；
- **拆分表**：原模式设计不合理，需进一步规范化（见 [[6.5 模式分解]]）；
- **合并表**：查询频繁的两个表合并（反规范化）；
- **修改约束**：业务规则变化，如成绩上限从 100 改为 150；
- **新增表与关系**：新增业务模块。

```sql
-- 重构示例：学生表新增 Email 字段并加唯一约束
ALTER TABLE Student
    ADD COLUMN Email VARCHAR(50) COMMENT '邮箱',
    ADD UNIQUE INDEX uk_student_email (Email);

-- 重构示例：将 Student 中的 Sage 拆为 BirthDate（更符合业务）
ALTER TABLE Student
    ADD COLUMN BirthDate DATE COMMENT '出生日期';
-- 迁移数据后删除原字段
-- UPDATE Student SET BirthDate = DATE_SUB(CURDATE(), INTERVAL Sage YEAR);
-- ALTER TABLE Student DROP COLUMN Sage;
```

> [!warning] 重构的工程注意
> 重构会改变模式，可能影响依赖该模式的应用程序。重构时应：
> 1. **评估影响范围**：找出所有使用该模式的应用；
> 2. **保持向后兼容**：通过视图提供旧接口，逐步迁移应用；
> 3. **分步执行**：先加新结构，迁移数据，最后删旧结构；
> 4. **备份与回滚计划**：重构前完整备份，准备回滚脚本。

## 运行维护的重要性

> [!summary] 运行维护的核心价值
> 1. **保证可用性**：通过转储与恢复，应对故障，减少停机时间；
> 2. **保障安全**：通过权限控制与审计，防止数据泄露与未授权访问；
> 3. **维持性能**：通过性能监控与重组，长期保持数据库高效运行；
> 4. **适应变化**：通过重构，使数据库随业务演进，延长生命周期。
>
> 数据库设计的六阶段并非线性流程——运行维护阶段的反馈常引发新一轮需求分析与重构，体现数据库设计的**反复性**（见 [[7.1 数据库设计概述]]）。

## 小结

> [!summary] 本节核心
> 1. 数据库运行维护是六阶段中持续时间最长的阶段，由 DBA 负责。
> 2. 维护工作包括四类：转储与恢复、安全性完整性控制、性能监督与改进、重组与重构。
> 3. **重组**整理物理存储（消除碎片），不改模式；**重构**调整逻辑结构（修改模式），可能影响应用。
> 4. 转储分海量/增量、静态/动态；恢复机制见第 8 章。
> 5. 性能监控用慢查询日志、EXPLAIN、Performance Schema 等工具，从 SQL、索引、配置、硬件多层面优化。
> 6. 运行维护阶段的反馈会引发新一轮设计与重构，体现数据库设计的反复性。
