# 9.5 意向锁

[[9.2 封锁技术]] 介绍了 X/S 锁与封锁粒度。当事务在**多种粒度**（如表与行）上封锁时，每加一个行锁都要检查整个表是否被加锁——开销巨大。**意向锁**通过"自顶向下声明意图"的方式大幅提高加锁效率。本节介绍 IS、IX、SIX 三种意向锁、它们的相容性矩阵与加锁规则，并简介 InnoDB 的实现。

## 意向锁的引入动机

> [!info] 多粒度封锁的问题
> 设事务 $T$ 想对表 `account` 加表级 X 锁（如做表级批量更新）。在此之前，$T$ 必须检查该表的**每一行**是否被其他事务加了行级锁——若有任何一行被锁住，$T$ 不能加表级锁。逐行检查代价高昂。

> [!theorem] 意向锁的思想
> 引入意向锁：事务在加**细粒度锁（行锁）**之前，先在**粗粒度对象（表）**上加一个"意向锁"，声明"我打算在此表的某些行上加锁"。这样后续事务想加表级锁时，只需检查表上的意向锁即可判断，无需逐行检查。

> [!note] 意向锁的本质
> 意向锁是一种**"指示器"锁**，本身不真正封锁数据，而是声明"下层有锁"。它是**多粒度封锁**的优化机制。

## 意向锁类型

### IS 意向共享锁

> [!definition] 意向共享锁
> **意向共享锁（Intention Shared Lock，IS 锁）**表示事务**打算**在数据对象的**下层**（更细粒度）加 **S 锁**。例如事务想读表中某些行，先在表上加 IS 锁。

### IX 意向排他锁

> [!definition] 意向排他锁
> **意向排他锁（Intention Exclusive Lock，IX 锁）**表示事务**打算**在数据对象的**下层**加 **X 锁或 S 锁**（即打算修改或读取下层）。例如事务想修改表中某些行，先在表上加 IX 锁。

### SIX 共享意向排他锁

> [!definition] 共享意向排他锁
> **共享意向排他锁（Shared Intention Exclusive Lock，SIX 锁）**表示事务**对数据对象本身加 S 锁**，同时**打算在下层加 X 锁**。即事务读取整个对象，并修改其中某些下层。

> [!example] SIX 锁的应用
> 设事务 $T$ 要读取 `account` 表全部数据，并修改其中若干行。$T$ 在表上加 SIX 锁：
> - S 锁部分允许其他事务读全表（不阻塞读）。
> - IX 锁部分表示要修改某些行。
>
> 若不加 SIX，则需在表上同时加 S 锁和 IX 锁，SIX 锁作为单一锁简化了管理。

## 意向锁相容性矩阵

加入意向锁后，锁类型共有 5 种：S、X、IS、IX、SIX。完整相容性矩阵如下：

| 已有 \ 请求 | S | X | IS | IX | SIX |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **S** | ✓ | ✗ | ✓ | ✗ | ✗ |
| **X** | ✗ | ✗ | ✗ | ✗ | ✗ |
| **IS** | ✓ | ✗ | ✓ | ✓ | ✓ |
| **IX** | ✗ | ✗ | ✓ | ✓ | ✗ |
| **SIX** | ✗ | ✗ | ✓ | ✗ | ✗ |

> [!note] 矩阵解读要点
> - **X 锁**与任何锁都不相容（最严格）。
> - **IS 锁**只与 S、IS、IX、SIX 相容，不与 X 相容。
> - **IX 锁**与 IS、IX 相容，与 S、X、SIX 不相容（因为 IX 意味着要修改下层，与读整个对象冲突）。
> - **SIX 锁**只与 IS 相容——其他事务可以在 SIX 持有期间加 IS 锁（即读下层某些行），但不能加 S、X、IX、SIX。

> [!warning] 矩阵记忆技巧
> - 意向锁（IS、IX）之间大多相容（声明意图，不冲突），但 IX 与 SIX 不相容（IX 要写，SIX 也在写）。
> - 实际锁（S、X、SIX）与 X 锁都不相容。
> - 完整记忆需要理解每种锁的语义，死记矩阵不可取。

## 意向锁加锁规则

> [!theorem] 多粒度封锁的加锁规则
> 1. 事务必须**自顶向下**逐层加锁——先在粗粒度（如表）上加意向锁，再在细粒度（如行）上加实际锁。
> 2. 事务必须**自底向上**逐层释放锁——先释放细粒度锁，再释放粗粒度锁。
> 3. 事务在任何层加锁前，必须确保**所有上层都加了合适的意向锁**：
>    - 加行级 S 锁前，先在表上加 IS 或更高级别锁。
>    - 加行级 X 锁前，先在表上加 IX 或更高级别锁。
> 4. 锁的级别需满足"包含"关系，例如已有 SIX 锁可不再加 IS 锁（SIX 隐含 S 与 IX）。

> [!example] 加锁流程示例
> 设 $T$ 想读表 `account` 全部行并修改其中 id=100 的行：
> 1. 在表上加 SIX 锁（声明：读全表 + 修改部分行）。
> 2. 在 id=100 的行上加 X 锁（实际修改）。
> 3. 执行读取与修改操作。
> 4. 释放行级 X 锁。
> 5. 释放表级 SIX 锁（按事务结束协议统一释放）。

## 意向锁的作用与 InnoDB 实现

> [!info] 意向锁的作用
> 1. **提高加锁效率**：检查表级锁时无需逐行扫描，只检查表上的意向锁即可。
> 2. **支持多粒度封锁**：表锁与行锁可以共存，且互不冲突时不会阻塞。
> 3. **声明意图**：明确事务的范围（读、写或读写），便于调度器决策。

> [!example] MySQL InnoDB 的意向锁
> InnoDB 自动管理意向锁，无需用户显式申请：
> - 事务对行加 S 锁前，InnoDB 自动在表上加 IS 锁。
> - 事务对行加 X 锁前，InnoDB 自动在表上加 IX 锁。
>
> 查看当前锁情况：
> ```sql
> -- MySQL 8.0+ 推荐使用 performance_schema.data_locks
> SELECT * FROM performance_schema.data_locks;
>
> -- 老版本可使用 INFORMATION_SCHEMA.INNODB_LOCKS
> SELECT * FROM INFORMATION_SCHEMA.INNODB_LOCKS;
> ```
> 输出中的 `LOCK_MODE` 字段会显示 `IS`、`IX`、`S`、`X`、`S,REC_NOT_GAP` 等模式。

> [!note] InnoDB 不支持 SIX 锁
> InnoDB 在标准协议上做了简化：**不直接实现 SIX 锁**。若事务需要"读全表 + 改部分行"，InnoDB 会用表级 S 锁 + 行级 X 锁组合（或在 RC/RR 隔离级别下用 MVCC 避免表级锁）。这是工程实现上的取舍。

## 小结

> [!summary] 本节核心
> - 意向锁用于多粒度封锁场景，声明"下层将加锁"，避免逐行检查。
> - 三种意向锁：**IS（意向共享）**、**IX（意向排他）**、**SIX（共享意向排他）**。
> - 相容性矩阵：意向锁间多相容；X 锁排斥一切；SIX 只与 IS 相容。
> - 加锁规则：**意向锁自顶向下**，**实际锁自底向上**释放。
> - InnoDB 自动管理意向锁（IS、IX），不直接实现 SIX。
