<summary>简答题答案</summary>

**1. ACID 四特性及实现机制：**
| 特性 | 含义 | DBMS 实现机制 |
| ---- | ---- | ---- |
| 原子性 A | 事务不可分割，要么全做要么全不做 | 恢复子系统 + 日志 + UNDO |
| 一致性 C | 事务执行使数据库从一个一致性状态转到另一个一致性状态 | A+I+D 综合 + 完整性约束子系统 |
| 隔离性 I | 并发执行的各事务相互隔离 | 并发控制子系统 + 封锁/MVCC |
| 持久性 D | 事务提交后更改永久保存 | 恢复子系统 + 日志 + REDO |

参见 [[8.1 事务基本概念与ACID]]。

**2. 四类故障及恢复策略：**
| 故障 | 别名 | 破坏 | 恢复策略 |
| ---- | ---- | ---- | ---- |
| 事务内部故障 | — | 单事务的更新 | 反向 UNDO 该事务 |
| 系统故障 | 软故障 | 内存缓冲区丢失 | REDO 已提交 + UNDO 未提交 |
| 介质故障 | 硬故障 | 磁盘数据破坏 | 重装副本 + REDO 日志 |
| 计算机病毒 | — | 数据库文件 | 类比介质故障 + 软件重装 |

参见 [[8.2 故障种类]]。

**3. WAL 原则：**
- **含义**：先写日志后写数据库——DBMS 在把数据库更新写入磁盘之前，必须先把对应的日志记录写入磁盘持久化。
- **必要性**：保证故障时日志已落盘，可据此恢复数据库状态。
- **后果**：若先写数据库后写日志，故障发生时数据库已改而日志未记，无法 UNDO 未完成事务的更新（违反原子性），也无法 REDO 已提交事务的更新（违反持久性）。
参见 [[8.3 恢复实现技术（日志、副本）]]。

**4. 检查点技术原理与改进：**
- **原理**：DBMS 在日志中定期建立检查点记录，记录检查点时刻的活动事务清单与最近日志地址，同时把缓冲区数据刷盘。
- **改进**：恢复时只需从最近的检查点开始扫描日志，把事务按状态分四类（$T_1$/$T_2$/$T_3$/$T_4$）处理，避免扫描整个日志。
- **效果**：大幅降低恢复扫描范围与延迟。
参见 [[8.4 恢复策略与检查点技术]]。

<details>
<summary>分析题答案与完整推导</summary>

**1. 事务内部故障恢复过程分析。**

**(1) $T_1$ 的日志记录序列：**
```
(T1, BEGIN)
(T1, UPDATE, account[A], 1000, 500)    -- A 余额 1000→500
(T1, UPDATE, account[B], 2000, 2500)    -- B 余额 2000→2500
(T1, ABORT/ROLLBACK)
```

**(2) 恢复过程：**
- 反向扫描日志，找到 $T_1$ 的更新记录。
- 对第二条 UPDATE（B：2000→2500）执行 UNDO：把 B 余额恢复为前像 2000。
- 对第一条 UPDATE（A：1000→500）执行 UNDO：把 A 余额恢复为前像 1000。
- 扫描到 $T_1$ 的 BEGIN 记录，恢复结束。

**最终余额**：A = 1000，B = 2000（恢复到事务开始前状态）。

---

**2. 系统故障恢复分析。**

**(1) 各事务处理：**
| 事务 | 已 COMMIT | 更新已落盘 | 处理 |
| ---- | ---- | ---- | ---- |
| $T_1$ | 是 | 否 | REDO |
| $T_2$ | 否 | 是 | UNDO |
| $T_3$ | 是 | 是 | 不处理（但 REDO 仍幂等执行也可） |

**(2) 执行顺序：先 UNDO 后 REDO**。先撤销未提交事务的"脏"更新，再重做已提交事务的更新。这样可避免 UNDO 时被 REDO 的数据覆盖。

**(3) REDO 须幂等的原因：**
有些已提交事务（如 $T_3$）的更新已经落盘，REDO 时会再次按后像覆盖。若 REDO 不幂等（如做加法而非赋值），多次执行结果会改变。因此 REDO 的实现必须是"按后像覆盖"——多次覆盖同一值，结果不变。

---

**3. 日志记录分析。**

**(1) 事务状态：**
- $T_2$ 已提交（COMMIT）。
- $T_1$ 已回滚（ROLLBACK）。

**(2) 对 $T_2$ 执行 REDO：**
正向扫描日志，对 $T_2$ 的 UPDATE 记录按后像重做：
- $(T2, UPDATE, R2, 200, 250)$：把 $R2$ 设为 250。

**(3) 对 $T_1$ 执行 UNDO：**
反向扫描日志，对 $T_1$ 的 UPDATE 记录按前像撤销：
- $(T1, UPDATE, R3, 50, 80)$：把 $R3$ 恢复为 50。
- $(T1, UPDATE, R1, 100, 150)$：把 $R1$ 恢复为 100。

注意：即使 $T_1$ 已显式 ROLLBACK，恢复时仍需 UNDO 它已做的更新以把数据库恢复到一致状态。

---

**4. 介质故障恢复步骤。**

**(1) 恢复步骤：**
1. 重装最近的海量后备副本（上周日的海量转储），使数据库恢复到上周日的状态。
2. 依次应用周一、周二的增量转储。
3. 装入自周二增量转储之后到故障时刻的日志文件。
4. 正向扫描日志，对已提交事务执行 REDO，把数据库推进到故障前的最新状态。

**(2) 日志文件的作用：**
- 增量转储只能恢复数据到上次转储时刻，日志用于把数据库从该时刻推进到故障前。
- 日志也是处理"已提交未落盘"与"未提交已落盘"两类问题的依据。

**(3) 动态转储需配合日志的原因：**
动态转储期间允许事务并发执行，副本可能保存的是事务执行中间的不一致状态。必须用日志记录的更新操作把副本恢复到一致性状态（已提交事务的更新 REDO，未提交事务的更新 UNDO）。仅靠副本无法恢复到一致性状态。

<summary>综合题答案与完整推导</summary>

**1. 检查点恢复完整过程。**

**(1) 各事务处理：**
| 事务 | $t_c$ 时刻 | $t_c$ 后 | 处理 | 理由 |
| ---- | ---- | ---- | ---- | ---- |
| $T_1$ | 已 COMMIT | — | 不处理 | 检查点建立时其更新已落盘 |
| $T_2$ | 活动 | COMMIT | REDO | 提交后更新可能未落盘 |
| $T_3$ | 活动 | 未 COMMIT | UNDO | 未完成事务的更新已落盘需撤销 |
| $T_4$ | 未开始 | 未 COMMIT | UNDO | 未完成事务的更新已落盘需撤销 |
| $T_5$ | 未开始 | COMMIT | REDO | 提交后更新可能未落盘 |

**(2) 扫描位置与方向：**
- **起始位置**：从最近一个检查点记录开始（不必扫描检查点之前的日志）。
- **方向**：先**正向**扫描建立 REDO 与 UNDO 队列，再**反向**扫描执行 UNDO，最后**正向**扫描执行 REDO。

**(3) 完整恢复步骤：**
1. 找到最近一个检查点记录，获取检查点时刻活动事务清单 $\{T_2, T_3\}$。
2. 正向扫描检查点之后的日志，分类：
   - 检查点后出现 COMMIT 的事务 → REDO 队列：$\{T_2, T_5\}$
   - 检查点后无 COMMIT 的事务 → UNDO 队列：$\{T_3, T_4\}$
   - 检查点前已 COMMIT 的事务（$T_1$）不处理。
3. **反向扫描日志**对 UNDO 队列 $\{T_3, T_4\}$ 执行 UNDO，按前像撤销它们的更新。
4. **正向扫描日志**对 REDO 队列 $\{T_2, T_5\}$ 执行 REDO，按后像重做它们的更新。
5. 恢复完成，在日志中写入结束记录。

参见 [[8.4 恢复策略与检查点技术]]。

---

**2. 动态转储+日志恢复过程。**

**(1) 副本为何可能不一致：**
动态转储期间事务 $T_a$、$T_b$、$T_c$ 在并发执行，转储过程中数据库的某些数据块可能被复制时是旧值，另一些数据块可能是新值（事务已修改但未提交）。副本保存的是转储期间的"动态快照"，可能包含未提交事务的部分更新，处于不一致状态。

**(2) 利用副本与日志恢复到一致性状态：**
1. 重装动态转储得到的副本。
2. 装入自转储开始到故障时刻的日志。
3. 用日志对副本进行处理：
   - 已提交事务的更新执行 REDO（重做）；
   - 未提交事务的更新执行 UNDO（撤销）。
4. 数据库恢复到一致性状态。

**(3) $T_a$、$T_b$、$T_c$ 在恢复中的处理：**
| 事务 | 转储期间 | 转储后 | 处理 |
| ---- | ---- | ---- | ---- |
| $T_a$ | $t_0$ 前已开始，$t_0$~$t_1$ 间 COMMIT | 已提交 | REDO |
| $T_b$ | $t_0$~$t_1$ 间 BEGIN 与 COMMIT | 已提交 | REDO |
| $T_c$ | $t_0$~$t_1$ 间 BEGIN，$t_1$ 后未 COMMIT | 未提交 | UNDO |

$T_a$、$T_b$ 已提交，但其更新可能未完整落盘到副本中，需 REDO 补齐。$T_c$ 未提交，但其部分更新可能已落盘到副本中，需 UNDO 撤销。

**(4) 完整介质故障恢复步骤：**
1. 重装动态转储得到的后备副本。
2. 装入自 $t_0$（转储开始时刻）到 $t_2$（故障时刻）的日志文件。
3. 正向扫描日志建立 REDO/UNDO 队列：
   - REDO 队列：$\{T_a, T_b\}$（已提交事务）
   - UNDO 队列：$\{T_c\}$（未提交事务）
4. 反向扫描日志对 UNDO 队列执行 UNDO，撤销 $T_c$ 的更新。
5. 正向扫描日志对 REDO 队列执行 REDO，重做 $T_a$、$T_b$ 的更新。
6. 数据库恢复到一致性状态，恢复完成。

</details>
