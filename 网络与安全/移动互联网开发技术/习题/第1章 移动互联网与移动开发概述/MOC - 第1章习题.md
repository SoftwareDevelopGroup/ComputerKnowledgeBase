## 一、选择题（5 题）

### 1. 下列哪一项不属于移动互联网区别于传统互联网的核心特点？

A. 随身性
B. 定位能力
C. 传感器丰富
D. 高带宽

<details>
<summary>查看答案</summary>

**答案：D**

解析：移动互联网的核心特点是随身性、定位能力、传感器丰富、碎片化。高带宽并非移动互联网的本质特征——3G 时代带宽有限但移动互联网已兴起，且传统互联网同样可具备高带宽。参见 [[1.1 移动互联网发展、主流移动平台#1.1.3 移动互联网的特点|1.1.3]]。
</details>

### 2. 关于 Android 与 iOS 生态对比，下列说法正确的是？

A. iOS 开发可在 Windows 平台上进行
B. Android 应用只能通过 Google Play 分发
C. Android 系统基于开源的 AOSP，设备碎片化程度高于 iOS
D. iOS 用户付费意愿低于 Android 用户

<details>
<summary>查看答案</summary>

**答案：C**

解析：
- A 错误：iOS 编译需 macOS + Xcode
- B 错误：Android 允许第三方分发（国内厂商商店、直接安装 APK）
- C 正确：Android 开源且设备厂商众多，碎片化远高于 iOS
- D 错误：iOS 用户付费意愿通常高于 Android

参见 [[1.2 Android、iOS 生态对比|1.2]]。
</details>

### 3. Flutter 跨平台方案的核心技术特征是？

A. 通过 JSBridge 调用原生能力
B. 使用自绘引擎（Skia/Impeller）渲染 UI
C. 将 JS 组件映射到原生控件
D. 完全依赖系统 WebView 渲染

<details>
<summary>查看答案</summary>

**答案：B**

解析：
- A 是 WebView 混合开发
- B 是 Flutter 的核心特征（自绘引擎）
- C 是 React Native
- D 是 Cordova/Ionic 等

参见 [[1.3 原生开发、跨平台开发方案对比#1.3.2 跨平台开发方案|1.3.2]]。
</details>

### 4. 移动应用开发流程的正确顺序是？

A. 需求分析 → 测试 → 开发 → 设计 → 发布 → 迭代
B. 需求分析 → UI 设计 → 开发 → 测试 → 发布 → 运营迭代
C. UI 设计 → 需求分析 → 开发 → 发布 → 测试 → 迭代
D. 开发 → 设计 → 需求分析 → 测试 → 迭代 → 发布

<details>
<summary>查看答案</summary>

**答案：B**

解析：标准流程为"需求分析 → UI/UX 设计 → 开发 → 测试 → 发布 → 运营与迭代"，运营反馈回流到需求形成迭代闭环。参见 [[1.4 移动应用开发流程与工程规范#1.4.1 移动应用开发流程|1.4.1]]。
</details>

### 5. 关于 Android 资源文件命名，下列哪一项合法？

A. `ActivityMain.xml`
B. `activity_main.xml`
C. `Activity_Main.xml`
D. `activityMain.XML`

<details>
<summary>查看答案</summary>

**答案：B**

解析：Android 资源文件名必须为小写字母、数字与下划线，不能包含大写字母。`activity_main.xml` 是合法命名；A、C 含大写；D 扩展名小写但资源命名习惯使用 `.xml` 小写后缀。参见 [[1.4 移动应用开发流程与工程规范#命名规范|1.4.2 命名规范]]。
</details>

## 三、简答题（4 题）

### 9. 简述移动互联网的四大特点及其对应用设计的影响。

<details>
<summary>查看答案</summary>

**参考答案：**

| 特点 | 对应用设计的影响 |
| ---- | ---------------- |
| 随身性 | 短时高频使用、推送通知、需关注启动速度/电量/离线可用 |
| 定位能力 | 提供 LBS 服务（地图、附近、导航），需申请定位权限 |
| 传感器丰富 | 支持拍照、扫码、运动、AR 场景，需处理传感器异步与硬件差异 |
| 碎片化 | 需多机型适配、多分辨率资源、不同厂商行为兼容测试 |

核心要点：随身性带来短时高频使用模式；定位与传感器扩展了应用场景；碎片化是 Android 开发的主要适配成本来源。参见 [[1.1 移动互联网发展、主流移动平台#1.1.3 移动互联网的特点|1.1.3]]。
</details>

### 10. 对比 Android 与 iOS 在应用分发与审核机制上的差异。

<details>
<summary>查看答案</summary>

**参考答案：**

| 维度 | Android | iOS |
| ---- | ------- | --- |
| 官方商店 | Google Play | App Store |
| 第三方分发 | 允许（国内厂商商店、APK 直装） | 不允许（除企业证书/MDM） |
| 审核严格度 | 较宽松，几小时至数天 | 严格，1—7 天，常被拒 |
| 上架费用 | 一次性 $25 | 年费 $99 |
| 抽成 | 15%—30% | 15%—30%（"苹果税"） |

特别地，中国大陆 Google Play 不可用，需同时提交至华为、小米、OPPO、vivo、应用宝等多家商店，是国内 Android 发布的主要工作量来源。参见 [[1.2 Android、iOS 生态对比#1.2.4 应用分发与审核|1.2.4]]。
</details>

### 11. 说明原生开发、Flutter、React Native、WebView 混合四种方案的渲染机制差异。

<details>
<summary>查看答案</summary>

**参考答案：**

- **原生开发**：业务代码直接调用平台 SDK，由系统渲染原生控件（Android 的 View 体系、iOS 的 UIKit）
- **Flutter**：使用 Dart 编写 UI，通过自带的 Flutter Engine（C++，底层 Skia/Impeller）直接绘制像素，**不依赖平台原生控件**，因此双端 UI 高度一致
- **React Native**：JS 通过 Bridge/JSI 调用原生模块，**将 JS 组件映射到原生控件**渲染，体验接近原生但有通信开销
- **WebView 混合**：H5 页面在系统 WebView（浏览器内核）内渲染，原生壳仅提供容器与 JSBridge 通信能力

关键区别在于渲染层：原生与 RN 使用系统控件，Flutter 自绘，WebView 浏览器内核渲染。参见 [[1.3 原生开发、跨平台开发方案对比#1.3.3 架构对比图|1.3.3]]。
</details>

## 四、分析题（3 题）

### 13. 某创业团队计划开发一款"周边餐厅推荐"应用，团队由 2 名前端工程师与 1 名产品经理组成，无 Android/iOS 原生经验，预算有限，要求 3 个月内双端上线。请分析应选择哪种技术方案并说明理由。

<details>
<summary>查看答案</summary>

**参考答案：**

**推荐方案：React Native（次选 Flutter）**

**分析过程：**

1. **需求特征**：内容展示 + 定位 + 简单交互，非高性能游戏/AR 场景，对原生能力要求中等
2. **团队能力**：2 名前端工程师 → JS/TS 技能可直接复用，RN 学习成本最低
3. **成本约束**：预算有限 → 避免双端原生开发（人力成本翻倍）
4. **时间约束**：3 个月双端 → 跨平台方案是唯一可行路径

**方案对比：**

| 候选 | 适配度 | 理由 |
| ---- | ------ | ---- |
| 原生 | ★★ | 团队无经验，3 个月无法完成双端 |
| Flutter | ★★★★ | 性能好，但需学习 Dart，前端技能迁移稍慢 |
| **React Native** | ★★★★★ | JS/TS 直接复用，生态成熟，热更新可行 |
| WebView 混合 | ★★★ | 性能偏弱，定位/列表体验差 |

**理由：** RN 在团队技能匹配度与开发效率上最优，定位、列表等餐厅推荐核心场景的性能可接受；建议搭配原生模块处理定位与推送（必要时）。参见 [[1.3 原生开发、跨平台开发方案对比#1.3.5 选型建议|1.3.5]]。
</details>

### 14. 阅读 Android 项目下 `app/build.gradle`（Groovy DSL）片段，回答问题。

```gradle
android {
    namespace 'com.example.myapp'
    compileSdk 34

    defaultConfig {
        applicationId "com.example.myapp"
        minSdk 24
        targetSdk 34
        versionCode 1
        versionName "1.0"
    }
}
```

**(1)** `compileSdk`、`minSdk`、`targetSdk` 各表示什么？
**(2)** 若 `minSdk 24` 对应 Android 7.0，应用最低可运行在哪个系统版本？为何要明确该值？
**(3)** `versionCode` 与 `versionName` 的区别是什么？

<details>
<summary>查看答案</summary>

**参考答案：**

**(1) 三个 SDK 字段含义：**

- `compileSdk 34`：编译时使用的 Android SDK 版本（API 34 = Android 14），决定编译期可调用的 API
- `minSdk 24`：应用最低支持的系统版本（API 24 = Android 7.0），低于此版本无法安装
- `targetSdk 34`：表明应用已针对该版本完成兼容性测试，系统据此启用/禁用某些行为变更

**(2) 最低运行版本与意义：**

最低可运行在 Android 7.0。明确该值的原因：
- 决定可用 API 的下限（高于 minSdk 的 API 需做版本判断或降级处理）
- 影响目标用户覆盖范围与适配工作量
- 商店上架时声明支持的设备范围

**(3) versionCode vs versionName：**

- `versionCode`：整数，用于**系统与商店判断版本先后**，每次发布必须递增
- `versionName`：字符串，**展示给用户**的版本号（如 `1.0`、`2.1.3`）

参见 [[1.4 移动应用开发流程与工程规范#1.2.3 工具链对比|1.4.3]] 与 [[1.2 Android、iOS 生态对比#Gradle 构建示例 Android|1.2.3]]。
</details>

### 15. 某团队 Android 项目 `.gitignore` 中遗漏了 `*.jks` 与 `local.properties`，可能造成哪些后果？应如何修复？

<details>
<summary>查看答案</summary>

**参考答案：**

**潜在后果：**

| 文件 | 后果 |
| ---- | ---- |
| `*.jks`（签名密钥） | 密钥泄露后，攻击者可签名同名应用覆盖你的应用，可发布恶意更新；属于严重安全事故 |
| `local.properties` | 包含本机 SDK 路径，团队协作时他人 clone 后构建失败；不同成员路径不同会反复冲突 |

**修复步骤：**

1. **立即补全 `.gitignore`：**

```gitignore
# 签名相关
*.jks
*.keystore
keystore.properties

# 本地配置
local.properties

# 构建产物
build/
.gradle/
captures/

# IDE
.idea/
*.iml
```

2. **从历史中清除已入库的密钥（关键）：**
   - 仅删除工作区文件不够，需用 `git filter-repo` 或 BFG Repo-Cleaner 清理历史
   - 命令示例（BFG）：`bfg --delete-files "*.jks"`，再 `git reflog expire` + `git gc --prune=now`

3. **重置签名密钥：**
   - 假定已泄露的密钥不再安全，需生成新密钥
   - 在 Google Play 控制台启用"应用签名密钥升级"机制（Play App Signing）
   - 国内各商店需重新提交密钥变更申请

4. **CI/CD 注入：** 密钥通过 CI 环境变量或密钥管理服务（如 KMS）注入，**绝不入库**

参见 [[1.4 移动应用开发流程与工程规范#移动开发特有的 Git 注意事项|1.4.4]]。
</details>
