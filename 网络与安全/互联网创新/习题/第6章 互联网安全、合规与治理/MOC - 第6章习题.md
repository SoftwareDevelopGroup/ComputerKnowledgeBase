## 一、选择题（6 题）

**1.** CIA 三要素是信息安全的经典框架，以下哪一项不属于 CIA 三要素？（ ）

A. 机密性（Confidentiality）
B. 完整性（Integrity）
C. 可用性（Availability）
D. 可追溯性（Traceability）

**2.** 下列关于中国《个人信息保护法》（PIPL）的描述，错误的是（ ）

A. 处理敏感个人信息应当取得单独同意
B. 个人信息主体享有查询、复制、更正、删除等权利
C. PIPL 只适用于中国境内的企业
D. 违法处理个人信息最高可处 5000 万元罚款

**3.** 根据避风港原则，网络服务提供者在收到权利人的侵权通知后，实施下列哪项行为可以免除赔偿责任？（ ）

A. 拒绝删除被指控的内容
B. 在合理期限内删除或屏蔽被指控的内容
C. 要求权利人提供更多证据
D. 将内容转移到其他服务器

**4.** 下列关于杀猪盘诈骗的描述，最准确的是（ ）

A. 通过冒充公检法进行诈骗
B. 通过刷单返利进行诈骗
C. 通过建立恋爱关系诱导投资进行诈骗
D. 通过发送虚假链接进行诈骗

**5.** 大数据杀熟的本质是（ ）

A. 提高老用户的购买价格
B. 利用算法实施价格歧视
C. 为不同用户推荐不同商品
D. 收集用户数据用于营销

**6.** 互联网金融中，客户资金由银行独立存管的核心目的是（ ）

A. 提高资金收益
B. 防止平台形成资金池
C. 简化交易流程
D. 增加用户便利度

<details>
<summary>选择题答案</summary>

1. **D**。CIA 三要素包括机密性（Confidentiality）、完整性（Integrity）、可用性（Availability）。可追溯性是后来扩展的要素，不属于经典 CIA 三要素。

2. **C**。PIPL 具有域外效力，处理中国自然人个人信息的境外企业同样适用。

3. **B**。避风港原则的核心是"通知-删除"——平台在收到通知后及时删除或屏蔽侵权内容的，可以免除赔偿责任。

4. **C**。杀猪盘是指诈骗分子通过社交平台与受害人建立恋爱关系，获取信任后诱导投资虚假平台，最终卷款消失的诈骗方式。

5. **B**。大数据杀熟是平台利用算法分析用户画像，对不同用户展示不同价格的行为，本质是价格歧视。

6. **B**。资金银行存管的核心目的是防止平台形成资金池，确保客户资金与平台自有资金隔离，避免平台挪用客户资金。

</details>

## 二、填空题（4 题）

**1.** CIA 三要素分别是：______、______、可用性（Availability）。

**2.** PIPL 规定的个人信息主体核心权利包括：知情权、决定权、______、______、更正权、删除权、可携带权。

**3.** 网络诈骗的"三不一多"防范原则是：______、______、______、多核实。

**4.** 合规设计的三大原则是：______、______、技术赋能。

<details>
<summary>填空题答案</summary>

1. **机密性（Confidentiality）**、**完整性（Integrity）**。CIA 三要素是信息安全的基石。

2. **查询权**、**复制权**。PIPL 规定了个人信息主体的七大权利：知情权、决定权、查询权、复制权、更正权、删除权、可携带权。

3. **不轻信**、**不透露**、**不转账**。"三不一多"是公安部推广的反诈口诀。

4. **合规前置**、**风险导向**。合规设计三大原则：合规前置（事前合规）、风险导向（优先处理高风险）、技术赋能（技术实现自动化合规）。

</details>

## 三、简答题（6 题）

**1.** 对比主动攻击与被动攻击的核心差异，并各举两个典型例子。

**2.** 简述中国 PIPL 与欧盟 GDPR 在数据主体权利方面的三个主要差异。

**3.** 什么是避风港原则和红旗原则？说明两者的关系和适用场景。

**4.** 简述刷单返利诈骗的典型作案流程，并说明防范要点。

**5.** 什么是隐私设计（Privacy by Design）？其核心原则有哪些？

**6.** 简述互联网金融合规的六大维度。

<details>
<summary>简答题答案</summary>

**1. 主动攻击 vs 被动攻击**

| 维度 | 主动攻击 | 被动攻击 |
| ---- | -------- | -------- |
| 核心行为 | 直接修改或破坏系统资源 | 监听和分析数据但不修改 |
| 危害 | 数据篡改、服务中断 | 数据泄露、隐私侵犯 |
| 检测难度 | 相对容易 | 极其困难 |

**典型例子**：
- 主动攻击：DDoS 攻击（通过海量请求导致服务中断）、SQL 注入（通过注入恶意 SQL 语句窃取或篡改数据）
- 被动攻击：网络嗅探（通过抓包分析网络传输数据）、流量分析（通过分析通信模式获取信息）

**2. PIPL 与 GDPR 的数据主体权利差异**

| 维度 | GDPR | PIPL |
| ---- | ---- | ---- |
| **权利种类** | 被遗忘权、限制处理权、可携带权 | 决定权、删除权、可携带权 |
| **同意机制** | 严格单独同意，拒绝不影响核心服务 | 单独同意，可随时撤回 |
| **权利行使** | 数据主体可向数据控制者主张权利 | 个人信息主体可向处理者主张权利 |

**具体差异**：
- GDPR 强调"被遗忘权"（Right to be Forgotten），要求数据控制者在特定情况下必须删除数据；PIPL 强调"决定权"，更突出个人对其信息的控制权
- GDPR 明确规定数据主体有权"限制处理"；PIPL 对此未作明确规定
- GDPR 的可携带权要求数据控制者以结构化、通用的格式提供数据；PIPL 仅要求提供"便捷的"数据导出功能

**3. 避风港原则与红旗原则**

| 原则 | 核心含义 | 适用场景 |
| ---- | -------- | -------- |
| **避风港原则** | 平台收到侵权通知后及时删除的，可免除赔偿责任 | 一般侵权内容（如普通用户上传的侵权视频） |
| **红旗原则** | 如果侵权事实像红旗一样显而易见，平台应当主动采取措施 | 明显违法内容（如色情、暴力、盗版内容） |

**关系**：红旗原则是避风港原则的例外和补充。避风港原则为平台提供了"被动免责"——不知道且收到通知后处理即可免责；红旗原则要求平台承担"主动义务"——明知或应知侵权内容存在时必须主动干预，否则即使没有收到通知也要承担责任。

**4. 刷单返利诈骗的流程与防范**

**作案流程**：
1. **小额返利**：让受害者刷单小额任务（100-500 元），立即返利获取信任
2. **中额返利**：逐步增加刷单金额（500-5000 元），继续返利巩固信任
3. **大额不返**：当受害者投入大额资金（5000+ 元）后，以"系统故障"、"卡单"为由不返利
4. **连环套**：要求受害者继续投入资金"激活"或"完成连单任务"才能返款
5. **失联**：当受害者无法或不愿继续投入时，诈骗分子消失

**防范要点**：
- 所有刷单都是诈骗，正规电商不存在刷单兼职
- 不扫描陌生二维码，不下载陌生 App
- 任何声称"返利"的都是陷阱
- 遇到诈骗立即拨打 96110 反诈专线

**5. Privacy by Design**

Privacy by Design 是将隐私保护贯穿于产品/系统设计全生命周期的理念，由加拿大隐私专家 Ann Cavoukian 提出。

**七大核心原则**：
1. **主动预防**：在设计阶段预防隐私侵犯
2. **隐私默认**：默认设置即为最高隐私保护级别
3. **隐私嵌入设计**：隐私保护是核心功能而非附加模块
4. **全功能双赢**：保护隐私的同时提供完整功能
5. **端到端安全**：全链路保护数据
6. **可见性与透明度**：让用户清楚知道数据如何处理
7. **尊重用户隐私**：以用户为中心

**6. 互联网金融合规的六大维度**

| 维度 | 核心要求 |
| ---- | -------- |
| **资金安全合规** | 客户备付金集中交存央行、实名制、反洗钱监测 |
| **数据安全合规** | 交易数据加密存储、令牌化技术、数据访问控制 |
| **反诈骗合规** | 实时风险监测、延迟到账机制、与公安系统对接 |
| **消费者权益合规** | 费率明示、交易通知、争议处理机制 |
| **算法合规** | 算法透明、利率明示、不得差异化定价 |
| **跨境合规** | 外汇许可、反洗钱国际标准、数据跨境合规 |

</details>

## 四、案例分析题（4 题）

**1.（数据安全案例）** 阅读以下材料，回答问题：
> 2023 年，某在线教育平台被曝发生大规模数据泄露，涉及 500 多万学生和家长的身份证号、手机号、家庭住址、学习记录等信息。泄露原因是平台的用户查询接口存在 SQL 注入漏洞，且数据库使用了弱密码（admin123）。
>
> (1) 分析该教育平台数据泄露的主要原因。
> (2) 从 CIA 三要素角度，分析此次泄露侵犯了哪些安全要素。
> (3) 如果你是该平台的安全负责人，如何设计一套数据安全整改方案？

<details>
<summary>案例分析1解答</summary>

**(1) 数据泄露原因分析**

| 原因 | 具体表现 | 根源 |
| ---- | -------- | ---- |
| **技术漏洞** | 用户查询接口存在 SQL 注入漏洞 | 开发阶段未进行安全编码和代码审计 |
| **弱密码策略** | 数据库使用 admin123 弱密码 | 缺乏密码强度要求和定期更换机制 |
| **安全意识缺失** | 数据库直接暴露在公网 | 网络架构设计不合理，未进行网络隔离 |
| **加密不足** | 用户密码使用 MD5 加密（已被破解） | 未采用安全的加密算法（如 bcrypt、Argon2） |
| **管理缺失** | 缺乏定期安全扫描和渗透测试 | 未建立常态化的安全检测机制 |

**(2) CIA 三要素分析**

| 要素 | 是否被侵犯 | 说明 |
| ---- | ---------- | ---- |
| **机密性（Confidentiality）** | ✅ 严重侵犯 | 500 万用户的身份证号、手机号等敏感信息被未授权获取 |
| **完整性（Integrity）** | ⚠️ 可能被侵犯 | 攻击者可能通过 SQL 注入修改数据（虽然案例未提及，但存在风险） |
| **可用性（Availability）** | ⚠️ 间接影响 | 数据泄露后可能引发系统信任危机，影响服务可用性 |

**(3) 数据安全整改方案**

**第一阶段：紧急处置（1-3 天）**
- 立即修复 SQL 注入漏洞，采用参数化查询替代字符串拼接 SQL
- 修改所有数据库密码，使用强密码（16 位以上，字母+数字+特殊符号）
- 将数据库从公网迁移到内网，通过防火墙白名单限制访问 IP
- 通知受影响用户，提供身份保护建议

**第二阶段：基础加固（1-2 周）**
- 部署 WAF（Web 应用防火墙），拦截 SQL 注入等 Web 攻击
- 升级密码加密算法为 bcrypt 或 Argon2
- 建立数据访问权限控制，实施最小权限原则
- 对敏感数据进行加密存储（身份证号、手机号）

**第三阶段：体系建设（1-3 个月）**
- 建立 SDLC 安全流程，将安全测试嵌入开发全流程
- 定期进行安全扫描和渗透测试（每季度至少一次）
- 建立数据安全监控和审计系统，实时监测异常访问
- 开展员工安全培训，提升安全意识
- 制定数据泄露应急预案，定期演练

</details>

**2.（隐私保护案例）** 阅读以下材料，回答问题：
> 某初创公司想开发一款"AI 健康管理 App"，需要收集用户的健康数据（心率、睡眠、运动记录）和生活数据（饮食、体重），通过 AI 分析提供健康建议。
>
> (1) 根据 PIPL，分析该 App 在数据收集阶段需要遵守哪些核心规则？
> (2) 如何用 Privacy by Design 原则指导该 App 的数据合规设计？
> (3) 该 App 在数据使用过程中可能面临哪些合规风险？如何应对？

<details>
<summary>案例分析2解答</summary>

**(1) PIPL 数据收集规则**

| 规则 | 具体要求 | App 实现要点 |
| ---- | -------- | ------------ |
| **合法、正当、必要** | 收集目的明确，限于最小必要范围 | 仅收集提供健康建议所必需的数据 |
| **告知-同意** | 收集前需充分告知并取得同意 | 首次使用时弹窗说明数据用途，获取单独同意 |
| **敏感信息特殊保护** | 健康数据属于敏感个人信息，需单独同意 | 健康数据收集需单独弹窗授权，不与其他同意捆绑 |
| **数据最小化** | 不收集非必要数据 | 不收集与健康无关的通讯录、相册等 |
| **主体权利保障** | 用户享有查询、更正、删除、导出权利 | 提供"我的数据"页面，支持数据管理 |

**(2) Privacy by Design 指导设计**

| 原则 | 应用 |
| ---- | ---- |
| **主动预防** | 在产品架构设计阶段就考虑数据保护，而非事后添加 |
| **隐私默认** | 默认关闭非必要数据收集（如默认不收集位置信息） |
| **隐私嵌入设计** | 数据收集功能与隐私保护功能同步设计，而非分离 |
| **全功能双赢** | 提供完整健康建议功能的同时保护用户隐私 |
| **端到端安全** | 数据从收集到存储到分析全链路加密 |
| **可见性与透明度** | 用户可随时查看自己的数据被如何使用 |
| **尊重用户隐私** | 用户可以随时停止数据收集并删除历史数据 |

**技术实现**：
- 采用差分隐私分析用户健康数据，防止个体被识别
- 使用联邦学习训练健康模型，数据不出本地
- 健康数据加密存储，密钥由用户控制

**(3) 数据使用合规风险**

| 风险 | 说明 | 应对措施 |
| ---- | ---- | -------- |
| **目的捆绑风险** | 将健康数据用于广告投放等非初始目的 | 明确告知数据用途，变更用途时重新获取同意 |
| **数据泄露风险** | 健康数据泄露会严重影响用户权益 | 加密存储、访问控制、数据脱敏 |
| **算法歧视风险** | AI 健康建议可能基于性别、年龄产生歧视 | 算法公平审计，确保建议不因性别/年龄而异 |
| **跨境传输风险** | 涉及健康数据的跨境传输需安全评估 | 数据存储在境内，跨境传输需申报评估 |
| **第三方共享风险** | 与第三方（如保险公司）共享数据需合规 | 签订数据处理协议，取得单独同意 |

</details>

**3.（平台责任案例）** 阅读以下材料，回答问题：
> 某短视频平台上出现大量"刷单返利"的诈骗信息，包括文字广告、短视频教程、评论区引流等形式。平台用户小张看到广告后被骗 2 万元。小张将平台告上法庭，认为平台未尽到审核义务。
>
> (1) 根据避风港原则和红旗原则，分析平台是否应当承担赔偿责任。
> (2) 如果你是该平台的合规负责人，如何设计一套反诈内容治理方案？
> (3) 平台治理与用户权益保护如何平衡？

<details>
<summary>案例分析3解答</summary>

**(1) 平台责任分析**

| 原则 | 适用分析 | 结论 |
| ---- | -------- | ---- |
| **避风港原则** | 平台是否收到过小张或其他用户的投诉通知？如果平台收到通知后及时删除了诈骗内容，则可免于赔偿。但如果未收到通知，避风港原则可能适用。 | 视情况而定 |
| **红旗原则** | 刷单返利广告具有明显的违法特征（"日赚万元"、"零风险"、"高佣金"等），如果这些内容像"红旗"一样显而易见，平台不能以"不知道"为由免责。 | 平台可能需要承担责任 |

**法律分析**：
- 如果平台**已经收到大量用户投诉**但未处理，根据红旗原则，平台可能被认定为"明知"侵权存在，需承担连带责任
- 如果平台**从未收到任何投诉**，但刷单返利的广告特征非常明显，法院可能适用红旗原则，认定平台"应知"而未尽注意义务
- 如果平台**建立了有效的审核机制**（关键词过滤+人工审核），但诈骗信息通过审核绕过了机制，且平台在收到投诉后立即处理，避风港原则可能适用

**(2) 反诈内容治理方案**

**第一层：事前预防**
- 建立"诈骗关键词库"（刷单、返利、日赚、零风险、高佣金等）
- 利用 AI 审核系统自动识别疑似诈骗内容
- 对新注册账号进行行为画像分析，识别诈骗特征

**第二层：事中干预**
- 建立人工审核团队，对疑似内容进行 24 小时轮班审核
- 设置"诈骗举报"快捷入口，用户举报后 1 小时内响应
- 对疑似诈骗内容采取限流、打标、删除等分级处置

**第三层：事后追溯**
- 建立诈骗账号"黑名单"机制，关联身份信息
- 与公安机关建立数据对接，协助案件调查
- 定期发布《平台反诈治理报告》，公开处置数据

**协同机制**：
- 与电商平台建立"刷单信息共享"机制
- 与金融机构建立"诈骗预警"联动机制
- 与教育机构合作开展反诈宣传

**(3) 平台治理与用户权益平衡**

| 平衡维度 | 治理措施 | 用户权益保障 |
| -------- | -------- | ------------ |
| **治理vs效率** | 机器审核为主，人工审核为辅 | 减少审核对正常内容创作者的影响 |
| **治理vs创新** | 治理规则公开透明，给予创作者改进空间 | 不过度限制内容创新 |
| **治理vs隐私** | 审核过程保护用户隐私信息 | 审核人员签署保密协议 |
| **治理vs救济** | 建立申诉机制，被误判的内容可申诉恢复 | 保障创作者的正当权益 |

</details>

**4.（合规设计案例）** 阅读以下材料，回答问题：
> 某互联网公司想推出一款"面向中小企业的一站式 SaaS 办公平台"，核心功能包括：在线文档、项目管理、客户关系管理（CRM）、财务报表。平台需要处理大量企业敏感数据（客户信息、财务数据、员工数据）。
>
> (1) 从数据合规角度，如何对平台涉及的数据进行分类分级？
> (2) 如何设计平台的数据处理全流程合规方案？
> (3) 如果你是该平台的合规负责人，如何平衡"数据价值利用"与"数据安全保护"？

<details>
<summary>案例分析4解答</summary>

**(1) 数据分类分级**

| 数据级别 | 数据类型 | 具体内容 | 保护要求 |
| -------- | -------- | -------- | -------- |
| **第 4 级（核心数据）** | 财务核心数据 | 企业财务报表、银行账户信息、税务数据 | 加密存储、严格访问控制、多因素认证 |
| **第 3 级（重要数据）** | 客户与员工数据 | 客户联系人信息、员工薪酬信息、合同数据 | 加密存储、数据脱敏、访问审计 |
| **第 2 级（一般数据）** | 业务运营数据 | 项目管理数据、在线文档、沟通记录 | 加密传输、基础访问控制 |
| **第 1 级（公开数据）** | 公开信息 | 企业公开介绍、产品信息 | 无特殊要求 |

**(2) 数据处理全流程合规方案**

| 流程 | 合规措施 | 技术实现 |
| ---- | -------- | -------- |
| **数据收集** | 告知-同意、数据最小化、目的绑定 | 首次使用弹窗告知数据用途，仅收集必要数据 |
| **数据存储** | 分级加密、访问控制、数据备份 | AES-256 加密、RBAC 权限管理、异地备份 |
| **数据使用** | 目的限制、数据脱敏、行为审计 | 数据使用日志记录、敏感字段脱敏展示 |
| **数据共享** | 单独同意、数据协议、安全评估 | 与第三方签订数据处理协议、数据传输加密 |
| **数据销毁** | 定期清理、彻底删除、不可恢复 | 数据到期自动删除、物理销毁存储介质 |

**关键机制**：
- **数据主体权利机制**：提供自助的查询、更正、导出、删除渠道
- **数据泄露应急机制**：72 小时内通知用户和监管机构
- **合规审计机制**：每季度进行一次数据合规审计

**(3) 数据价值与安全的平衡**

**策略一：隐私增强技术（PET）**
- 使用差分隐私进行数据分析，在保护个体隐私的同时获取统计价值
- 使用联邦学习进行跨企业协同建模，数据不出本地
- 使用同态加密在加密状态下进行数据计算

**策略二：数据分类分级使用**
- 核心数据：仅用于必要的业务功能，不进行数据分析
- 重要数据：在脱敏后可用于数据分析（如 CRM 数据脱敏后用于营销分析）
- 一般数据：可在合规框架内进行分析和挖掘

**策略三：合规沙箱**
- 在可控环境中测试数据创新应用
- 与监管机构沟通，探索数据利用的合规路径
- 建立数据创新的"容错机制"

**策略四：数据安全能力建设**
- 建立数据安全团队，投入数据安全技术研发
- 培养全员数据安全意识，将安全嵌入业务流程
- 定期进行数据安全评估和演练

**核心理念**：数据安全不是数据利用的障碍，而是数据利用的保障。通过技术创新和合规设计，可以实现"数据可用不可见，价值可享不泄露"的理想状态。

</details>
