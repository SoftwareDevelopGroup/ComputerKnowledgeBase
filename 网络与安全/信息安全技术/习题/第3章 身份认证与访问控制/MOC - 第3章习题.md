### 第 1 题　认证与授权辨析　[[3.1 认证方式：口令、生物特征、硬件令牌|📖 3.1]]

以下描述属于**授权（Authorization）**而非认证（Authentication）的是：

A. 用户输入口令后系统校验其是否为 alice
B. 系统判断 alice 是否有权读取 report.doc
C. 用户用指纹解锁手机
D. 用户插入 U2F 密钥完成网站登录

<details>
<summary>查看答案</summary>

**答案：B**

- A、C、D 都是验证"你是谁"——认证（AuthN）
- B 是在身份已知后判断"能做什么"——授权（AuthZ）
- 关键区分：认证输出身份，授权输出权限范围
</details>

### 第 2 题　口令存储方式选择　[[3.1 认证方式：口令、生物特征、硬件令牌|📖 3.1]]

下列口令存储方案中，**抗彩虹表 + 抗 GPU 暴力破解**能力最强的是：

A. `SHA-256(password)`
B. `SHA-256(password + salt)`
C. `bcrypt(password, salt, cost=12)`
D. `AES-Encrypt(password, key)`

<details>
<summary>查看答案</summary>

**答案：C**

- A 无盐，相同口令哈希相同，彩虹表可直接命中
- B 加盐抗彩虹表，但 SHA-256 太快，GPU 可高速试算
- C bcrypt 是慢哈希，内置盐且 cost 可调，故意慢以抗暴力破解
- D 可逆加密存储违规，密钥泄露全部口令暴露
</details>

### 第 3 题　Bell-LaPadula 安全规则　[[3.3 访问控制模型：自主、强制、角色 RBAC|📖 3.3]]

在 Bell-LaPadula 模型中，密级为"秘密"（Secret）的用户**可以**执行的操作是：

A. 读取"机密"（TopSecret）文件
B. 往"公开"（Unclassified）文件写数据
C. 往"机密"（TopSecret）文件写数据
D. 把自己持有的"秘密"文件降级为"公开"

<details>
<summary>查看答案</summary>

**答案：C**

- A 违反"no read up"（向下读：主体密级 ≥ 客体密级才能读）
- B 违反"no write down"（向上写：主体密级 ≤ 客体密级才能写）
- C 正确：秘密用户往机密文件写，符合"向上写"允许
- D MAC 下用户无权自主降级，必须经脱密程序
</details>

### 第 4 题　RBAC 模型要素　[[3.3 访问控制模型：自主、强制、角色 RBAC|📖 3.3]]

关于 RBAC 模型，下列说法**错误**的是：

A. 权限直接授予角色，用户通过被分配角色获得权限
B. 角色继承（RH）允许主管角色继承专员角色的权限
C. 职责分离（SoD）要求互斥角色可分配给同一用户以提高效率
D. 会话（Session）中用户可激活其角色的一个子集

<details>
<summary>查看答案</summary>

**答案：C**

- C 错误：SoD 要求互斥角色**不可**同时分配给同一用户，目的是防止单人完成全流程（如制单+审批）
- A、B、D 均为 RBAC 标准特性
</details>

### 第 5 题　MFA 因素组合判断　[[3.2 单点登录、多因素认证 MFA|📖 3.2]]

以下组合中，**属于真正的多因素认证（MFA）**的是：

A. 用户名 + 登录口令 + 密保问题答案
B. 邮箱口令 + 动态口令卡上的 6 位 TOTP
C. PIN 码 + 另一个 6 位数字 PIN
D. 指纹 + 人脸 + 虹膜（同一设备）

<details>
<summary>查看答案</summary>

**答案：B**

- A 全是"你知道什么"，单一因素，不是 MFA
- B "口令（知道）+ TOTP（拥有令牌）"，双因素，正确
- C 两个都是"你知道什么"，单因素
- D 三个都是"你是什么"，单因素（生物特征叠加仍是同一类别）
- MFA 强调"不同类别"因素叠加
</details>

## 二、填空题（3 题）

### 第 6 题　生物特征指标　[[3.1 认证方式：口令、生物特征、硬件令牌|📖 3.1]]

生物特征认证中，把冒充者误判为合法用户的概率称为（1）______，把合法用户误判为冒充者的概率称为（2）______，二者相等时的错误率称为（3）______，该值越（4）______说明算法精度越高。

<details>
<summary>查看答案</summary>

- (1) FAR（误识率，False Acceptance Rate）
- (2) FRR（拒真率，False Rejection Rate）
- (3) EER（等错误率，Equal Error Rate）
- (4) 小

调严阈值会降低 FAR 但升高 FRR，二者此消彼长；EER 越小算法越好。
</details>

### 第 7 题　TOTP 生成公式　[[3.1 认证方式：口令、生物特征、硬件令牌|📖 3.1]]

TOTP（RFC 6238）将 HOTP 中的计数器替换为时间步，其计数器 $C$ 的计算公式为 $C = $ (1)______，其中 $T_0$ 为纪元起点，$\Delta t$ 通常取（2）______ 秒。OTP 的核心计算式为 $\text{OTP} = \text{Truncate}(\text{(3)______}) \mod 10^d$，其中共享密钥 $K$ 必须（4）______。

<details>
<summary>查看答案</summary>

- (1) $\left\lfloor \dfrac{T_{\text{now}} - T_0}{\Delta t} \right\rfloor$
- (2) 30
- (3) $\text{HMAC-SHA-1}(K, C)$
- (4) 仅在令牌与服务器各存一份（注册时安全下发，不可泄露）

TOTP 抗截获重放（一次性），但仍可被实时钓鱼转发，高安全场景需 FIDO2。
</details>

### 第 8 题　RBAC 与访问控制要素　[[3.3 访问控制模型：自主、强制、角色 RBAC|📖 3.3]]

访问控制的三要素是主体、（1）______、操作。RBAC 在用户与权限之间引入（2）______ 层，其中用户-角色分配记为（3）______，角色-权限分配记为（4）______。在 Linux 文件权限中，`-rw-r--r--` 的属主权限是（5）______。

<details>
<summary>查看答案</summary>

- (1) 客体（Object）
- (2) 角色（Role）
- (3) UA（User-Assignment）
- (4) PA（Permission-Assignment）
- (5) `rw-`（读写，无执行）

Linux 文件权限是 DAC 的典型实现，9 位分别对应属主、属组、其他的 rwx。
</details>

## 三、简答题（4 题）

### 第 9 题　口令存储为何不能用通用哈希　[[3.1 认证方式：口令、生物特征、硬件令牌|📖 3.1]]

简述为什么用 SHA-256 等通用哈希存储口令不安全，并说明应采用什么方案及其原因。

<details>
<summary>查看答案</summary>

**通用哈希不安全的原因**：
- SHA-256 等设计目标是"快"，单次微秒级；现代 GPU 每秒可算数十亿次
- 攻击者拿到哈希库后可对候选口令高速试算（字典攻击/暴力破解）
- 即便加盐也只能防彩虹表，无法防高速暴力

**应采用方案**：慢哈希算法（bcrypt / scrypt / Argon2），并配合每口令独立盐。

**原因**：
- 慢哈希故意拉高单次计算成本（如 bcrypt 通过 cost 参数控制迭代次数），把"每秒 10 亿次"压到"每秒几千次"
- scrypt / Argon2 还消耗大量内存，使 GPU/ASIC 并行加速收益大减
- 盐保证相同口令哈希不同，彻底失效彩虹表
- 新项目首选 Argon2（PHC 大赛胜出），存量系统 bcrypt 仍可接受

补充：服务端只存"盐 + 慢哈希"，永不明文落库或写日志；传输走 TLS。
</details>

### 第 10 题　SSO 协议对比　[[3.2 单点登录、多因素认证 MFA|📖 3.2]]

对比 CAS、SAML 2.0、OAuth 2.0、OpenID Connect 四种协议的定位、数据格式与典型场景，并说明为什么不能把 OAuth 2.0 当作认证协议使用。

<details>
<summary>查看答案</summary>

| 协议 | 定位 | 数据格式 | 典型场景 |
| ---- | ---- | -------- | -------- |
| CAS | Web SSO | 票据 Ticket | 高校/企业内网 |
| SAML 2.0 | 跨组织身份联邦 | XML | 企业 B2B、教育联邦（Shibboleth） |
| OAuth 2.0 | 授权框架 | JSON | 第三方授权访问资源（"用微信登录"） |
| OIDC | 在 OAuth 2.0 上加认证层 | JSON（JWT） | 互联网身份、移动端标准化联合 |

**OAuth 2.0 不能当认证协议的原因**：
- OAuth 2.0 解决的是"授权第三方访问用户资源"，核心产物是 access_token，**没有定义如何证明用户身份**
- access_token 是给资源服务器用的凭证，不含可验证的身份声明；把它当身份凭证会出严重漏洞（如攻击者用他人 access_token 冒充登录）
- OIDC 才是标准修复：在 OAuth 2.0 之上增加 id_token（JWT，由授权服务器签名），客户端通过验证 id_token 签名获得可靠的身份认证结果
</details>

### 第 11 题　四类访问控制模型对比　[[3.3 访问控制模型：自主、强制、角色 RBAC|📖 3.3]]

对比 DAC、MAC、RBAC、ABAC 四类访问控制模型的决策依据、灵活性、典型场景，并说明 Bell-LaPadula 模型的两条核心规则。

<details>
<summary>查看答案</summary>

| 模型 | 决策依据 | 灵活性 | 典型场景 |
| ---- | -------- | ------ | -------- |
| DAC | 资源所有者自主授权（ACL） | 高 | Linux 文件权限 |
| MAC | 系统统一的安全标签 | 低 | 军方、涉密系统 |
| RBAC | 角色分配（用户→角色→权限） | 中 | 企业 ERP、OA |
| ABAC | 主体/客体/环境属性 + 策略 | 高 | 云平台、零信任 |

**Bell-LaPadula 两条核心规则**（针对保密性）：
1. **简单安全属性（向下读 / no read up）**：主体密级 ≥ 客体密级才可读——防止低密级用户读取高密级信息
2. ***-属性（向上写 / no write down）**：主体密级 ≤ 客体密级才可写——防止高密级信息被写入低密级客体造成泄露

补充：BLP 只保证保密性，完整性由 Biba 模型（"向上读、向下写"）补充；BLP 不能阻止隐信道。
</details>

### 第 12 题　最小权限与权限分离落地　[[3.4 权限管理、最小权限原则|📖 3.4]]

简述最小权限原则和权限分离（SoD）的含义，并各举一个工程落地示例。说明 RBAC 中如何实现权限分离。

<details>
<summary>查看答案</summary>

**最小权限原则（PoLP）**：每个主体只被授予完成合法任务所必需的最小权限，且仅在需要时、最短时间内有效。
- 落地示例：Web 应用进程不以 root 运行，而以低权限专用账号运行；CI/CD 部署密钥只对生产环境特定目录可写而非全集群
- 目的：缩小攻击面与爆炸半径，账号被盗或误操作影响有限

**权限分离（SoD）**：将一项敏感操作拆分给多个互斥角色，使任何单一主体都无法独立完成全流程。
- 落地示例：财务付款流程中"制单人 ≠ 审批人 ≠ 付款人"，防单人挪用；代码上线"开发 ≠ 评审 ≠ 发布"，防后门植入
- 目的：强制"串谋"才能违规，把单人作案风险降到极低

**RBAC 中的实现**：通过互斥角色约束（RBAC2）实现——定义"制单"与"审批"互斥，系统拒绝把二者同时分配给同一用户。高敏操作强制 SoD，日常低风险操作按效率优先。

补充：SoD 会增加流程成本，应仅对高敏感操作（金额超阈值、影响生产、涉密）强制，避免一刀切。
</details>

## 四、方案设计题（3 题）

### 第 13 题　企业单点登录 + MFA 方案　[[3.2 单点登录、多因素认证 MFA|📖 3.2]]　[[3.4 权限管理、最小权限原则|📖 3.4]]

某集团有 OA、邮件、ERP、代码仓库、云控台 5 个系统，员工抱怨反复登录，且近期发生过弱口令撞库事件。请设计一套单点登录 + MFA 改造方案，要求：

(1) 选定 SSO 协议并说明理由；
(2) 设计 MFA 策略（区分普通员工与特权账号）；
(3) 给出权限回收与离岗处理流程；
(4) 指出至少 2 个安全风险及缓解措施。

<details>
<summary>查看答案</summary>

**(1) SSO 协议选型**：选 OIDC（或 CAS）。
- 理由：5 个系统多为 Web/移动端，OIDC 基于 JSON/JWT 比 SAML XML 轻量、对接成本低；标准化、有 id_token 提供可靠认证；移动端友好
- 部署统一身份中心（IdP），各系统改造为 OIDC 客户端（RP），用户在 IdP 一次登录获 id_token + access_token 访问全部系统

**(2) MFA 策略**：
- **普通员工**：口令 + TOTP App（Google Authenticator 等），性价比高；首登强制绑定
- **特权账号（管理员、DBA、财务）**：口令 + FIDO2 硬件密钥（抗钓鱼）；高敏操作（如云控台改配置）触发 step-up 二次认证
- 风险自适应：异地登录、新设备触发额外 MFA 挑战
- 提供备用恢复码，加密存储，一次性使用

**(3) 权限回收与离岗流程**：
- HR 离职流程与 IdP 强耦合：离职当日自动停用账号、撤销 OIDC 会话、通知各系统销毁本地会话（单点登出 SLO）
- 特权账号经 PAM 临时授权，到期自动回收；离职立即回收所有特权
- 季度权限复核，长期未用权限自动回收，遵循 [[3.4 权限管理、最小权限原则|最小权限原则]]

**(4) 安全风险及缓解**：
| 风险 | 缓解措施 |
| ---- | -------- |
| IdP 成为单点失败点（被攻破全线沦陷） | IdP 强制 MFA + FIDO2、独立部署、严格审计、限速防爆破 |
| 单点登出（SLO）跨域残留会话 | 配合短会话超时（如 2 小时）；高敏系统每次重新 MFA |
| TOTP 实时钓鱼 | 高敏账号升级 FIDO2（基于域名的挑战-响应抗钓鱼） |
| MFA 疲劳攻击（推送误点） | 推送显示登录地点/设备/时间；限制推送次数；改挑战-响应式 |

补充：方案应包含分阶段实施（先 OA/邮件低风险系统，后 ERP/云控台），并保留应急账号（如 IdP 故障时）。
</details>

### 第 14 题　银行核心系统访问控制方案　[[3.3 访问控制模型：自主、强制、角色 RBAC|📖 3.3]]　[[3.4 权限管理、最小权限原则|📖 3.4]]

某银行核心系统需对不同岗位员工（柜员、主管、审计员、DBA）实施访问控制，要求：
- 柜员只能查询/修改自己网点的客户数据
- 主管可审批本网点大额转账，但不能修改审计日志
- 审计员可读所有操作日志但不能修改业务数据
- DBA 可维护数据库但不能直接查看客户明文数据

请选择访问控制模型并设计角色-权限方案，说明如何满足"职责分离"与"最小权限"。

<details>
<summary>查看答案</summary>

**(1) 模型选择**：以 **RBAC 为主 + ABAC 为辅**混合模型。
- RBAC 管岗位职责（柜员/主管/审计员/DBA 角色固定，权限映射稳定）
- ABAC 管细粒度条件（"仅本网点""仅大额审批""仅日志不可改业务"等动态约束）
- 关键数据（客户明文）加密存储，DBA 持维护权限但不持解密密钥（密钥由应用层 HSM 管控）

**(2) 角色-权限方案**：

| 角色 | 权限 | ABAC 约束 |
| ---- | ---- | --------- |
| 柜员 | 客户数据查询/修改 | 客户.网点 = 柜员.网点 |
| 主管 | 大额转账审批 | 客户.网点 = 主管.网点 且 金额>阈值 |
| 审计员 | 全量日志只读 | 客体.类型=日志；操作=只读 |
| DBA | 数据库维护（DDL/监控） | 不可访问应用层解密后明文；操作全程审计 |

**(3) 职责分离（SoD）落地**：
- 互斥角色约束：柜员 ≠ 主管 ≠ 审计员 ≠ DBA，同一人不可兼任
- 大额转账需"柜员制单 + 主管审批"双人完成，单人无法完成全流程
- DBA 维护数据库但不能审批转账、不能查看业务日志的语义解释（只能看技术日志）
- 审计员独立于业务线，直接向合规部门汇报，避免被业务主管干预

**(4) 最小权限落地**：
- 柜员默认仅本网点、仅客户基础字段；敏感字段（身份证、余额）按需申请 step-up 授权
- DBA 日常用低权限监控账号；高危操作（DROP/ALTER）走工单临时提权，限时回收
- 所有操作经引用监控器判定，默认拒绝；操作全程审计，审计日志独立存储，特权账号无权删改

补充：可叠加 MAC 思想给数据分级（如"高敏客户数据"标密级，仅特定角色可读），但银行场景 RBAC+ABAC 已足够，纯 MAC 太重。
</details>

### 第 15 题　特权账号管理 PAM 方案　[[3.4 权限管理、最小权限原则|📖 3.4]]

某企业运维团队 6 人长期共享一个 root 口令（写在团队 wiki），多个离职人员 root 未回收，曾发生误删库无法定位操作人的事故。请设计 PAM 改造方案，包含：

(1) 整改目标与核心能力清单；
(2) 运维登录与高危操作的完整流程；
(3) 与 HR 离职流程的对接；
(4) 改造后的审计与合规收益。

<details>
<summary>查看答案</summary>

**(1) 整改目标与核心能力**：
- 目标：消除共享 root、权限按需临时授权、操作可定位到人、特权全程留痕
- PAM 核心能力：凭证保险箱、临时授权（限时）、会话代理、会话录制、命令审计与告警、密码自动轮换

**(2) 运维登录与高危操作流程**：
```
① 运维在 PAM 提交申请（理由、目标系统、时长，如 30 分钟）
② 主管 + 安全值班审批通过
③ PAM 临时授权：运维经 PAM 代理通道登录目标，PAM 代为注入 root 凭证
   —— 运维始终不接触 root 真实口令
④ 会话全程录屏录键；高危命令（rm -rf、DROP TABLE、shutdown）实时告警安全值班
⑤ 到期 PAM 自动切断会话、回收权限、轮换目标 root 口令
⑥ 操作录像与命令日志归档，安全团队可按需回放
```
配合 [[3.2 单点登录、多因素认证 MFA|MFA]]：登录 PAM 本身需口令 + FIDO2/TOTP，防 PAM 凭证被盗。

**(3) 与 HR 离职流程对接**：
- HR 离职系统与 PAM 强耦合：离职状态变更自动触发 PAM 停用该用户所有特权
- 离职当日（甚至提前）切断 PAM 访问、撤销进行中的临时授权、归档其操作录像
- 调岗场景：新岗位需重新申请对应特权，旧岗位特权自动回收
- 季度权限复核：PAM 生成特权使用报表，长期未用权限自动回收

**(4) 审计与合规收益**：
| 维度 | 整改前 | 整改后 |
| ---- | ------ | ------ |
| 凭证管理 | 6 人共享 root，写在 wiki | root 入保险箱，按需临时授权 |
| 操作定位 | 无法定位操作人 | 录屏录键，5 分钟内可回放 |
| 权限回收 | 离职 root 未回收 | HR 联动自动回收 |
| 高危告警 | 无 | rm -rf/DROP 实时告警 |
| 合规审计 | 等保扣分 | 符合等保 2.0 三级访问控制要求 |

补充：整改应分阶段（先收回共享 root 接入 PAM，再上会话录制与告警，最后对接 HR 流程），并保留应急 break-glass 账号（如 PAM 故障时）由双人开封使用并事后审计。
</details>

### 复习建议

> [!tip] 按薄弱点回看
> 1. **概念辨析类易错**（第1、4、5题）：牢记 AuthN/AuthZ、MFA"不同类别"、RBAC 互斥约束不可同人的定义
> 2. **计算/公式类**（第7题）：背 TOTP 公式与时间步，理解 HOTP→TOTP 的演进
> 3. **对比类**（第10、11题）：动手默写 SSO 协议对比表与四模型对比表，能举出每个的典型场景
> 4. **方案设计类**（第13–15题）：先列模型选型理由，再画角色/流程，最后写风险缓解；答案要覆盖"选型→流程→SoD→最小权限→审计"五段式
> 5. **跨节关联**：认证（3.1/3.2）的身份喂给授权（3.3/3.4），方案题常需贯通四节，复习时按"凭证产生→认证协议→访问控制→权限治理"主线串起来

> - 简答/方案题先给结论再展开，避免只罗列术语不解释

> - Bell-LaPadula 题务必区分"读/写"与"向上/向下"，方向写反即全错
