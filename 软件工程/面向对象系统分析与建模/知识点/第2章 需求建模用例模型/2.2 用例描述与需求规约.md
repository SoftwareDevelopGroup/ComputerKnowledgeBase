# 2.2 用例描述与需求规约

用例图只给出用例名，要真正理解一个用例“怎么执行、何时触发、异常怎么处理”，必须用结构化的用例描述（用例规约）补充。用例描述是连接用例图与设计/测试的桥梁：它既是对需求的精化，也是编写顺序图与测试用例的依据。

## 用例描述模板

一个完整的用例描述通常包含以下字段：

| 字段 | 说明 |
| --- | --- |
| 用例编号 | 唯一标识，如 `UC-Order-001` |
| 用例名 | 动宾结构，如“下单购买” |
| 参与者 | 主要参与者及次要参与者 |
| 简要说明 | 一句话描述用例目标 |
| 前置条件 | 用例开始前系统必须满足的状态 |
| 后置条件 | 用例成功结束后系统进入的状态 |
| 主成功场景 | 一切顺利时的标准交互步骤序列 |
| 扩展场景 | 主场景中某步骤的异常或分支处理 |
| 特殊需求 | 性能、安全、可用性等非功能约束 |
| 假设与补充 | 其他需要说明的前提 |

> [!definition] 前置条件与后置条件
> **前置条件**（Precondition）：用例开始前必须为真的事实，是系统状态的约束，而非触发事件。**后置条件**（Postcondition）：用例成功完成后系统保证达到的状态。两者都描述“状态”而非“动作”。

## 主成功场景与扩展场景

> [!concept] 主成功场景
> 主成功场景（Main Success Scenario，又称主流程）是参与者在无任何异常情况下达成目标的标准路径。它用编号步骤描述参与者与系统的一问一答，每步明确“谁做什么”。

> [!concept] 扩展场景
> 扩展场景（Extensions，又称备选流程）是对主场景中某一步骤的异常或条件分支处理。通常格式为“主场景步骤号 + 条件 → 处理动作”，处理完后可返回主场景或终止用例。

编写要点：

1. 主场景只写“一切顺利”，把异常留给扩展场景；
2. 每步明确发起方（参与者或系统）；
3. 步骤编号便于扩展场景引用（如“3a: 步骤3失败时…”）；
4. 扩展场景应覆盖主要异常路径（如密码错误、库存不足、支付超时）。

## 用例规约文档编写

把用例描述整理成统一格式的《用例规约文档》，是需求规约的核心内容。编写时注意：

- **一致**：用例名、参与者名与用例图保持一致；
- **可测**：每条主场景步骤都应对应一条测试用例；
- **无歧义**：避免“适当处理”“可能”等模糊表述；
- **可追溯**：每条需求能映射到具体用例（参见 [[2.3 用例关系与需求追踪]]）。

## 用例粒度控制

用例粒度决定模型的详细程度，过细导致用例爆炸，过泛失去指导意义。

| 粒度 | 表现 | 问题 |
| --- | --- | --- |
| 过细 | “点击登录按钮”“输入密码” | 把界面操作当用例，失去业务价值 |
| 合适 | “用户登录”“下单购买” | 一个完整业务目标，可独立测试 |
| 过泛 | “使用系统”“管理一切” | 无法指导设计与测试 |

> [!tip] 粒度判断标准
> 一个用例应当：①对参与者有明确价值；②能独立完成一个业务目标；③可作为测试单元；④通常对应 3–10 步主场景。

## 用例编号与优先级

- **编号**：采用分层编码，如 `UC-{模块}-{序号}`（`UC-Order-001`），便于检索与追踪；
- **优先级**：按业务重要性与实现紧迫度分级（如高/中/低或 MoSCoW：Must/Should/Could/Won't），指导迭代规划。

## 示例：在线下单用例描述

> [!example] 用例规约：下单购买
> - **用例编号**：UC-Order-001
> - **用例名**：下单购买
> - **参与者**：顾客（主要）、支付网关（次要）
> - **简要说明**：顾客选购图书并完成在线支付，生成订单。
> - **前置条件**：顾客已登录系统；购物车中至少有一件商品。
> - **后置条件**：系统生成已支付订单；库存相应扣减；订单状态为“待发货”。
>
> **主成功场景**：
> 1. 顾客在购物车页面点击“去结算”；
> 2. 系统显示收货地址与订单摘要；
> 3. 顾客确认地址并选择支付方式；
> 4. 系统跳转支付网关，请求支付；
> 5. 支付网关返回支付成功；
> 6. 系统生成订单，扣减库存，显示订单号。
>
> **扩展场景**：
> - *3a*：顾客修改收货地址 → 系统保存新地址后返回步骤 3；
> - *4a*：支付网关超时 → 系统提示重试，订单标记为“待支付”；
> - *4b*：支付余额不足 → 系统提示更换支付方式，返回步骤 3；
> - *6a*：库存不足 → 系统提示库存短缺，订单挂起待人工处理。
>
> **特殊需求**：支付步骤须在 30 秒内响应；支付信息传输须加密。

## 小结

用例描述用结构化字段（前置条件、主成功场景、扩展场景、后置条件等）把用例图中的椭圆展开为可执行、可测试的规约。控制好用例粒度、规范编号与优先级，配合需求追踪矩阵，能保证需求不丢失、可验证、可演化。
