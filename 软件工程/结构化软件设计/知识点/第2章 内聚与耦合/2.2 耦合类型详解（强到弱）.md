# 2.2 耦合类型详解（强到弱）

耦合（Coupling）衡量模块之间的依赖程度，是 [[1.3 设计目标、高内聚低耦合核心准则|模块独立性]]的两个度量维度之一。本节按由强到弱系统介绍七种耦合类型——内容、公共、外部、控制、标记、数据、非直接，每种配代码/模块示例，阐明判定方法。理解耦合谱系是降低模块间依赖、改进设计的直接依据。

## 耦合的强弱谱系

```mermaid
flowchart LR
    A["内容耦合<br/>最强"] --> B["公共耦合"]
    B --> C["外部耦合"]
    C --> D["控制耦合"]
    D --> E["标记耦合"]
    E --> F["数据耦合"]
    F --> G["非直接耦合<br/>最弱"]
    style A fill:#f00
    style B fill:#f55
    style C fill:#f88
    style D fill:#fa8
    style E fill:#fc8
    style F fill:#8f8
    style G fill:#0c0
```

> [!note] 谱系说明
> 前三种（内容、公共、外部）为**强耦合**，应避免；控制耦合为**中耦合**，应尽量消除；后三种（标记、数据、非直接）为**弱耦合**，是设计目标。数据耦合是最常见、可接受的协作方式。

## 内容耦合（Content Coupling）

> [!definition] 内容耦合
> 一个模块直接访问另一模块的内部数据或代码（如直接修改另一模块的变量、跳入另一模块内部执行）。

```text
模块A 直接读写 模块B 的内部变量
模块A 跳转到 模块B 的某一行代码执行
```

```python
# 内容耦合示例：模块A直接修改模块B的内部状态
class ModuleB:
    def __init__(self):
        self._internal_state = 0  # 内部状态，应私有

def module_a(b):
    b._internal_state = 999  # 直接侵入修改，内容耦合
```

> [!warning] 内容耦合最差
> 一个模块直接侵入另一模块内部，内部任何改动都会直接影响对方，模块完全丧失独立性。现代语言通过访问控制（private/protected）从语法上抑制内容耦合，应严格避免。

## 公共耦合（Common Coupling）

> [!definition] 公共耦合
> 多个模块共享同一全局数据结构（全局变量、公共数据区），任一模块对该数据的修改都会影响所有共享模块。

```text
全局变量: g_config
模块A 读写 g_config
模块B 读写 g_config
模块C 读写 g_config
```

```python
# 公共耦合示例：多个模块共享全局配置
g_config = {"debug": False, "timeout": 30}  # 全局数据

def module_a():
    g_config["timeout"] = 60  # 修改全局数据

def module_b():
    if g_config["debug"]:     # 读取全局数据
        print("debug mode")
```

> [!tip] 改进方向
> 把公共数据封装为一个模块的内部数据，通过接口（getter/setter）访问，使数据变化可追踪、可控。公共耦合的问题在于：数据被多方自由修改，难以定位错误来源，模块间存在隐式依赖。

## 外部耦合（External Coupling）

> [!definition] 外部耦合
> 模块通过外部的公共数据环境（如外部文件格式、通信协议、设备接口）连接，多个模块都依赖同一外部约定。

```text
外部文件: data.csv
模块A 按 CSV 格式写 data.csv
模块B 按 CSV 格式读 data.csv
模块C 按 CSV 格式追加 data.csv
```

```python
# 外部耦合示例：多个模块依赖同一外部文件格式
def module_a():
    with open("data.csv", "w") as f:
        f.write("id,name,score\n")       # 依赖 CSV 格式

def module_b():
    with open("data.csv", "r") as f:
        for line in f:
            fields = line.strip().split(",")  # 依赖 CSV 格式
```

> [!note] 外部耦合 vs 公共耦合
> 外部耦合依赖的是**外部环境约定**（文件格式、协议），公共耦合依赖的是**程序内全局数据**。外部耦合强于公共耦合的外部表现，但通常弱于公共耦合的内部影响。改进方向：把对外部约定的访问集中到一个模块，其他模块通过该模块间接访问。

## 控制耦合（Control Coupling）

> [!definition] 控制耦合
> 一个模块向另一模块传递控制信息（标志、开关、状态码），控制其执行逻辑——接收方根据控制信号选择分支。

```text
模块A 调用 模块B(flag, data)
  flag = "compute" → B 执行计算分支
  flag = "sort"    → B 执行排序分支
```

```python
# 控制耦合示例：传入标志控制分支
def module_b(action, data):
    if action == "compute":
        return sum(data)
    elif action == "sort":
        return sorted(data)

def module_a():
    result = module_b("sort", [3, 1, 2])  # 传入控制标志
```

> [!tip] 改进方向
> 将控制标志转化为数据参数，或拆分被控模块为多个功能内聚模块。上例可拆为 `compute(data)` 与 `sort(data)`，调用方直接调用所需功能。控制耦合的问题在于：调用方需了解被调方的内部逻辑，被调方无法独立决策。

## 标记耦合（Stamp Coupling）

> [!definition] 标记耦合
> 模块间传递数据结构（记录/对象）的引用，但接收方只使用其中的部分字段。

```text
模块A 传入完整 Student 记录给 模块B
模块B 只使用 Student.score 字段
```

```python
# 标记耦合示例：传递整个记录但只用部分字段
class Student:
    def __init__(self, name, age, score):
        self.name = name
        self.age = age
        self.score = score

def module_b(student):       # 接收整个 Student 对象
    return student.score > 60  # 只用 score 字段

def module_a():
    stu = Student("Alice", 20, 85)
    passed = module_b(stu)    # 传递整个对象
```

> [!tip] 改进方向
> 只传递模块实际需要的数据字段，而非整个数据结构。上例改为 `module_b(student.score)`，仅传 `score` 值（转为数据耦合）。标记耦合的问题在于：接收方依赖了它不需要的字段，数据结构变化会波及接收方。

## 数据耦合（Data Coupling）

> [!definition] 数据耦合
> 模块间仅通过参数传递必要的数据值（而非数据结构引用或控制信号），接口清晰、依赖最小。

```text
模块A 调用 模块B(score, threshold)
模块B 仅使用传入的 score 与 threshold 两个数据值
```

```python
# 数据耦合示例：仅传递必要数据值
def module_b(score, threshold):
    return score > threshold

def module_a():
    passed = module_b(85, 60)  # 仅传数据值
```

> [!note] 数据耦合最可接受
> 数据耦合是模块间正常的协作方式——接口明确、依赖最小、易于理解与测试。设计应使模块间尽量保持数据耦合，这是“低耦合”的实践目标。

## 非直接耦合（No Direct Coupling）

> [!definition] 非直接耦合
> 两个模块之间没有直接关系，各自独立运行，互不调用、互不共享数据。

```text
模块A: 计算工资
模块B: 生成报表
二者无调用、无共享数据，仅通过上层模块间接协调
```

```python
# 非直接耦合示例：两个独立模块
def compute_salary(hours, rate):
    return hours * rate

def generate_report(title, content):
    print(f"=== {title} ===\n{content}")

# 二者无直接关系，由上层模块分别调用
```

> [!note] 非直接耦合最弱
> 非直接耦合模块完全独立，耦合度最低，复用性最好。但实际系统中模块间通常需要协作，非直接耦合是理想极限，数据耦合是务实的实践目标。

## 七种耦合对比

| 类型 | 强弱 | 依赖内容 | 典型示例 | 设计建议 |
| --- | --- | --- | --- | --- |
| 内容耦合 | 最强 | 直接访问内部 | 修改另一模块私有变量 | 严格避免 |
| 公共耦合 | 强 | 共享全局数据 | 多模块读写全局变量 | 应避免，封装 |
| 外部耦合 | 较强 | 外部约定 | 共依赖文件格式 | 应减少，集中访问 |
| 控制耦合 | 中 | 传递控制信号 | 传入标志选分支 | 尽量消除 |
| 标记耦合 | 较弱 | 传数据结构引用 | 传整个记录只用部分 | 应改进为数据耦合 |
| 数据耦合 | 弱 | 仅传数据值 | 传入必要参数 | 务实目标 |
| 非直接耦合 | 最弱 | 无直接关系 | 两个独立模块 | 理想极限 |

## 小结

耦合按由强到弱分为七种：内容（直接访问内部）、公共（共享全局数据）、外部（依赖外部约定）、控制（传递控制信号）、标记（传数据结构只用部分）、数据（仅传数据值）、非直接（无直接关系）。前三种为强耦合应避免，控制耦合为中耦合应消除，后三种为弱耦合是设计目标，数据耦合是最常见的可接受协作方式。判定耦合类型时，依次检查是否直接访问内部、是否共享全局数据、是否依赖外部约定、是否传递控制信号、是否传递数据结构但只用部分、是否仅传数据值，最终落到“无直接关系”即非直接耦合。
