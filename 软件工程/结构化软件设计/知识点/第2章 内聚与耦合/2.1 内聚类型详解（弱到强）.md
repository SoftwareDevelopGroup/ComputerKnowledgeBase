# 2.1 内聚类型详解（弱到强）

内聚（Cohesion）衡量模块内部各成分之间的关联程度，是 [[1.3 设计目标、高内聚低耦合核心准则|模块独立性]]的两个度量维度之一。本节按由弱到强系统介绍七种内聚类型——偶然、逻辑、时间、过程、通信、顺序、功能，每种配代码/模块示例，阐明判定方法。理解内聚谱系是评估模块质量、改进设计的直接依据。

## 内聚的强弱谱系

```mermaid
flowchart LR
    A["偶然内聚<br/>最弱"] --> B["逻辑内聚"]
    B --> C["时间内聚"]
    C --> D["过程内聚"]
    D --> E["通信内聚"]
    E --> F["顺序内聚"]
    F --> G["功能内聚<br/>最强"]
    style A fill:#f55
    style B fill:#f88
    style C fill:#fa8
    style D fill:#fc8
    style E fill:#8f8
    style F fill:#5f5
    style G fill:#0c0
```

> [!note] 谱系说明
> 前三种（偶然、逻辑、时间）为**低内聚**，应避免；中间两种（过程、通信）为**中内聚**，可接受但非理想；后两种（顺序、功能）为**高内聚**，是设计目标。功能内聚是最理想状态——模块只做一件事。

## 偶然内聚（Coincidental Cohesion）

> [!definition] 偶然内聚
> 模块内各成分之间没有实质关联，仅因随意、方便（如“看起来相关”或减少文件数）被放在一起。

```text
模块: misc_utils()
  - 打开日志文件
  - 计算两数之和
  - 格式化日期
  - 校验邮箱字符串
```

```python
# 偶然内聚示例：成分之间无逻辑关联
def misc_utils():
    log = open("app.log", "a")      # 日志操作
    total = add(2, 3)               # 算术运算
    date_str = format_date(now())   # 日期格式化
    valid = is_valid_email("a@b.c") # 字符串校验
```

> [!warning] 偶然内聚的危害
> 各成分无关联，修改某一成分可能误伤其他成分；模块无法用一句话描述其功能；难以命名、难以测试、难以复用。应拆分为多个功能内聚模块。

## 逻辑内聚（Logical Cohesion）

> [!definition] 逻辑内聚
> 模块完成逻辑上相关的多种功能，由调用方传入的参数（标志/开关）选择执行其中之一。

```text
模块: print_report(type, data)
  if type == "PDF":    生成PDF报表
  if type == "Excel":  生成Excel报表
  if type == "HTML":   生成HTML报表
```

```python
# 逻辑内聚示例：由 type 标志选择分支
def print_report(report_type, data):
    if report_type == "PDF":
        generate_pdf(data)
    elif report_type == "Excel":
        generate_excel(data)
    elif report_type == "HTML":
        generate_html(data)
```

> [!tip] 改进方向
> 拆分为 `generate_pdf(data)`、`generate_excel(data)`、`generate_html(data)` 三个功能内聚模块，调用方直接调用所需模块，消除标志参数。逻辑内聚的问题在于：调用方需知道标志含义，且修改某一报表逻辑会影响整个模块。

## 时间内聚（Temporal Cohesion）

> [!definition] 时间内聚
> 模块内各成分在同一时间段内执行（如系统启动时的初始化、关闭时的清理），但成分之间无数据或逻辑依赖。

```text
模块: initialize()
  打开数据库连接
  加载配置文件
  初始化全局变量
  启动日志系统
```

```python
# 时间内聚示例：初始化时同时执行多个无依赖操作
def initialize():
    open_db_connection()
    load_config("config.ini")
    init_global_vars()
    start_logger()
```

> [!note] 时间内聚的可接受性
> 时间内聚在初始化/清理场景中较为常见且可接受，但仍不如功能内聚理想。可进一步拆分为 `init_db()`、`load_config()` 等，由顶层 `initialize()` 协调调用，使每个子模块功能单一。

## 过程内聚（Procedural Cohesion）

> [!definition] 过程内聚
> 模块内各成分按特定的过程顺序执行，前一成分的执行结果控制或影响后一成分的执行，但成分之间不一定有数据传递。

```text
模块: process_order()
  step1: 读取订单
  step2: 校验订单（依赖 step1 是否成功）
  step3: 计算金额
  step4: 保存订单
```

```python
# 过程内聚示例：按业务流程顺序执行
def process_order():
    order = read_order()          # 步骤1
    if not validate_order(order): # 步骤2 依赖步骤1结果
        return False
    amount = calculate_amount(order)  # 步骤3
    save_order(order, amount)     # 步骤4
    return True
```

> [!note] 过程内聚 vs 时间内聚
> 过程内聚的成分有**执行顺序上的依赖**（前一步控制后一步是否执行），而时间内聚的成分仅是“同时执行”无顺序依赖。过程内聚强于时间内聚，但成分未必有数据流动。

## 通信内聚（Communicational Cohesion）

> [!definition] 通信内聚
> 模块内各成分操作同一数据集（数据区），但成分之间无必然的执行顺序。

```text
模块: operate_buffer(buf)
  read_buffer(buf)
  write_buffer(buf, data)
  clear_buffer(buf)
  统计_buffer(buf)
```

```python
# 通信内聚示例：各成分都操作同一 buffer
def operate_buffer(buf):
    data = read_buffer(buf)
    write_buffer(buf, new_data)
    clear_buffer(buf)
    size = count_buffer(buf)
```

> [!note] 通信内聚 vs 过程内聚
> 通信内聚的各成分围绕**同一数据**，但无固定顺序；过程内聚的各成分围绕**固定顺序**，但未必操作同一数据。通信内聚通常强于过程内聚，因为成分共享数据上下文。

## 顺序内聚（Sequential Cohesion）

> [!definition] 顺序内聚
> 模块内各成分顺序执行，且前一成分的输出是后一成分的输入，形成数据流水线。

```text
模块: transform(data)
  step1: 读取原始数据 → 输出 raw
  step2: 清洗 raw → 输出 cleaned
  step3: 转换 cleaned → 输出 transformed
  step4: 输出 transformed
```

```python
# 顺序内聚示例：前一成分输出为后一成分输入
def transform(data):
    raw = read_raw(data)            # 输入 data → 输出 raw
    cleaned = clean(raw)            # 输入 raw → 输出 cleaned
    transformed = convert(cleaned)  # 输入 cleaned → 输出 transformed
    output(transformed)             # 输入 transformed
```

> [!note] 顺序内聚的优势
> 数据在模块内形成清晰流水线，成分之间有明确的数据依赖，模块功能较集中。顺序内聚是高内聚，仅次于功能内聚。若整个流水线只为一个明确目标服务，可进一步抽象为功能内聚。

## 功能内聚（Functional Cohesion）

> [!definition] 功能内聚
> 模块内所有成分共同为完成一个单一、明确的功能而协作，模块只做一件事。

```text
模块: compute_sin(x)
  泰勒展开计算
  精度控制
  返回 sin(x)
```

```python
# 功能内聚示例：所有成分共同完成单一功能
def compute_sin(x):
    # 泰勒展开: sin(x) = x - x^3/3! + x^5/5! - ...
    result = 0.0
    term = x
    n = 1
    while abs(term) > 1e-10:
        result += term
        n += 2
        term *= -x * x / ((n - 1) * n)
    return result
```

> [!tip] 功能内聚是最理想状态
> 功能内聚模块只做一件事，可独立理解、测试与复用，与其他模块耦合自然最低。设计时应尽量使每个模块达到功能内聚——这是“高内聚”的目标。

## 七种内聚对比

| 类型 | 强弱 | 成分关系 | 典型示例 | 设计建议 |
| --- | --- | --- | --- | --- |
| 偶然内聚 | 最弱 | 无关联 | 随意堆叠的 utils | 应避免，拆分 |
| 逻辑内聚 | 弱 | 逻辑相关，参数选择 | type 分支报表 | 应避免，拆分 |
| 时间内聚 | 较弱 | 同时间执行 | 初始化模块 | 可接受，可拆分 |
| 过程内聚 | 中 | 固定顺序 | 业务流程步骤 | 可接受 |
| 通信内聚 | 较强 | 操作同一数据 | 缓冲区操作 | 较好 |
| 顺序内聚 | 强 | 数据流水线 | 读→清→转→写 | 设计目标 |
| 功能内聚 | 最强 | 共同完成单一功能 | compute_sin(x) | 理想目标 |

## 小结

内聚按由弱到强分为七种：偶然（无关联）、逻辑（参数选择）、时间（同时间执行）、过程（固定顺序）、通信（操作同一数据）、顺序（数据流水线）、功能（单一功能）。前三种为低内聚应避免，中间两种为中内聚可接受，后两种为高内聚是设计目标，功能内聚最优。判定内聚类型时，依次检查成分是否共同服务单一功能、是否形成数据流水线、是否操作同一数据、是否固定顺序、是否同时间执行、是否由参数选择，最终落到“无关联”即偶然内聚。
