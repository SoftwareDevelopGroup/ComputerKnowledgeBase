### 简答题答案

<details>
<summary>点击展开简答题参考答案</summary>

**8.21 参考答案**
- 按抽象层次：机器语言、汇编语言、高级语言。
- 按范式：过程式（C/Pascal）、面向对象（Java/C++）、函数式（Lisp/Haskell）、逻辑式（Prolog）。
选择因素：应用领域、开发效率、运行效率、团队熟悉度、生态与库支持、可维护性、性能要求、部署环境。

**8.22 参考答案**
编码规范主要内容：
- 命名规范：见名知意，变量用名词、函数用动词，统一大小写风格（驼峰/下划线）。
- 格式规范：缩进、括号、空格、行长统一。
- 注释规范：关键逻辑与接口写注释，文档注释生成 API 文档。
作用：提高可读性、可维护性，降低沟通成本，减少缺陷，便于团队协作与代码审查。

**8.23 参考答案**
McCabe 圈复杂度衡量程序控制流的复杂程度，反映独立路径数。
- 计算方法：V(G) = E - N + 2（边数 - 节点数 + 2）；或 V(G) = 判定节点数 + 1。
- 阈值：≤10 可接受，>10 建议重构，>20 风险高。
- 圈复杂度过高意味着路径多、测试用例多、缺陷概率高、可维护性差，因此需重构以降低复杂度。

**8.24 参考答案**
Fagan 审查流程：①计划（确定审查范围与角色）；②概览（介绍代码背景）；③准备（审查者独立阅读）；④审查会议（集体发现缺陷）；⑤返工（作者修复）；⑥跟踪（验证修复）。
常见方式：结对编程、走查（Walkthrough）、审查（Inspection）、轮查、工具辅助自动审查（如 SonarQube）。

</details>

### 设计题答案

<details>
<summary>点击展开设计题参考答案</summary>

**8.25 参考答案**
- 边节点公式：V(G) = E - N + 2 = 9 - 8 + 2 = 3。
- 判定节点数 + 1：2 个 if + 1 个 while = 3 个判定节点，V(G) = 3 + 1 = 4。
说明：若两种方法结果不一致，通常因控制流图统计口径差异（如是否计入复合判定）。按题目给定 2 if + 1 while，判定节点法得 V(G) = 4。两种结果均 ≤10，不需要重构。
（注：若边节点公式按题目给定 9 边 8 节点得 V(G)=3，与判定法 4 的差异源于边数统计，应以控制流图实际为准。）

**8.26 参考答案**
坏味道与重构手法：
| 坏味道 | 重构手法 |
| --- | --- |
| 重复代码（遍历累加） | 提取方法（Extract Method）为 calcTotal() |
| switch/if-else 链 + 魔法数（0.9/0.85/0.8） | 以多态取代条件式 + 用命名常量/策略模式 |
| 过长函数（一个方法做计算、折扣、打印、存库） | 提取方法拆为 calcTotal/calcDiscount/print/save |
| 特性依恋（直接操作 o.items 内部） | 搬移方法到 Order 类，让 Order 提供 calcTotal() |
改进后：calcTotal、calcDiscount、printOrder、saveOrder 各司其职，折扣用策略模式消除 switch。

**8.27 参考答案**
坏味道：过大类（God Class），一个类承担地址、联系方式、订单、积分四类职责，违反单一职责。
重构方案：
- 用提取类（Extract Class）拆分为 Customer（核心信息）、Address（地址）、Contact（联系方式）、OrderHistory（订单）、PointAccount（积分）。
- 相关行为搬移到对应类（搬移方法）。
- Customer 通过关联持有这些类，职责单一。

**8.28 参考答案**
违反的规范：无缩进、参数间无空格、变量名 a/x/y/z 不见名知意、无注释、魔法数 100、一行多语句。
改进后：
```java
/** 计算两数之和，结果上限为 MAX_LIMIT */
int addWithLimit(int first, int second) {
    final int MAX_LIMIT = 100;
    int sum = first + second;
    if (sum > MAX_LIMIT) {
        sum = MAX_LIMIT;
    }
    return sum;
}
```

**8.29 参考答案**
1. 圈复杂度 18 超标。阈值：≤10 可接受，>10 建议重构，>20 风险高。18 已超 10，应重构。
2. 降低圈复杂度的重构手法：①提取方法（把分支逻辑拆为独立方法）；②以多态取代条件式（用策略/状态模式消除 switch）；③分解条件表达式（用卫语句提前返回）；④合并条件表达式（合并相同结果的条件）。
3. 以多态取代条件式：把每个 switch 分支对应一个策略子类（如 Type1Strategy、Type2Strategy…），定义公共接口，调用时由多态决定具体行为，消除 switch。
4. 保证行为不变：重构前先补充足够的单元测试覆盖现有行为，重构后运行测试，全部通过才确认行为不变；小步重构、持续运行测试。

**8.30 参考答案**
问题对质量的影响：
- 命名随意、无注释：可读性差，难以维护与交接。
- 单函数 300 行、圈复杂度 25：缺陷概率高、测试用例多、维护困难、风险高。
- 重复代码：修改需多处同步，易遗漏产生缺陷。
- 魔法数遍布：含义不明，修改易错。
改进方案：
1. 规范：制定并强制执行命名、格式、注释规范（工具如 Checkstyle 强制）。
2. 重构：对长函数用提取方法拆分；用提取类拆分过大类；用提取方法消除重复代码；魔法数提取为命名常量；条件式用多态取代。
3. 审查：引入代码审查（结对/Inspection）与工具辅助（SonarQube）持续检查。
4. 度量：设定圈复杂度 ≤10、函数行数 ≤50 等阈值门禁，超标禁止合入。
