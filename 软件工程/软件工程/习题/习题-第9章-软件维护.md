### 简答题答案

<details>
<summary>点击展开简答题参考答案</summary>

**9.21 参考答案**
四种维护类型：
- 改正性维护：修复运行中发现的缺陷。
- 适应性维护：适应外部环境变化（操作系统、硬件、接口、法规）。
- 完善性维护：新增功能、改进性能、优化体验。
- 预防性维护：主动提高可维护性与可靠性，预防未来问题（如重构）。
占比最大的是完善性维护（约 50%~66%）。

**9.22 参考答案**
维护流程：①提交维护申请（记录问题或需求）；②分类与影响评估（判定维护类型，评估影响范围、成本、风险）；③修改设计与代码；④测试（单元、集成、回归测试）；⑤复查与评审；⑥交付与文档更新记录。

**9.23 参考答案**
可维护性：软件被理解、改正、适应、完善以适应新环境的难易程度。
影响因素：可理解性、可测试性、可修改性、可移植性、可靠性。
提高措施：编写高质量文档、遵循编码规范、降低耦合提高内聚、控制复杂度、建立自动化测试、做预防性维护与重构。

**9.24 参考答案**
Lehman 八大定律：①持续变化；②复杂度增加；③自调节；④组织稳定性保持；⑤熟悉性保持；⑥持续增长；⑦质量下降；⑧反馈系统。
前三条解释：
1. 持续变化：系统必须持续变化，否则越来越不满足用户需求。
2. 复杂度增加：随演化复杂度持续增加，除非主动重构降低。
3. 自调节：软件演化是自调节的反馈过程，系统会趋向某种稳定速率。

</details>

### 设计题答案

**9.25 参考答案**

| (2) 适配新微信支付 API 版本 | 适应性维护 |
| (3) 增加批量导入功能 | 完善性维护 |
| (4) 重构 300 行长函数 | 预防性维护 |
| (5) JDK 8 迁移到 JDK 17 | 适应性维护 |
| (6) 修复闰年计算错误 | 改正性维护 |

**9.26 参考答案**
应采用再工程（包含逆向工程 + 正向工程），因为不仅需理解结构，还需改造为 Web 版。
步骤：
1. 逆向工程：分析源代码，恢复系统结构、设计与数据模型，重建文档。
2. 评估与规划：识别可复用部分与需重写部分，规划 Web 版架构。
3. 重构：对可复用代码重构以降低复杂度、提高可维护性。
4. 正向工程：基于恢复的设计与新技术重新实现 Web 版。
5. 测试与迁移：验证功能一致性，迁移数据，交付。

**9.27 参考答案**
改进方案：
1. 文档重建：补写需求、设计、接口文档（必要时逆向工程恢复）。
2. 规范化：制定并执行命名、格式、注释规范。
3. 解耦重构：降低耦合、提高内聚，拆分过大模块。
4. 自动化测试：建立单元测试与回归测试基线，保证后续修改安全。
5. 复杂度控制：监控圈复杂度，超标即重构。
6. 预防性维护：定期重构与文档同步。

**9.28 参考答案**
维护类型：完善性维护（新增自定义列排序功能）。
流程：①提交维护申请（描述自定义列排序需求）；②分类评估（判定为完善性，评估对报表模块的影响、工作量）；③修改设计与代码（设计排序逻辑，修改报表模块）；④测试（功能测试、回归测试确保不影响原有报表）；⑤复查评审；⑥交付与文档更新。

**9.29 参考答案**
1. 高并发偶发订单丢失：改正性维护（修复缺陷）。优先级高，工作量取决于并发逻辑复杂度。
2. 支持国产化数据库达梦：适应性维护（适应环境变化）。优先级中高，工作量较大（数据库适配、SQL 改写、测试）。
3. 增加数据大屏展示：完善性维护（新增功能）。优先级中，工作量取决于大屏复杂度。
4. 重构核心模块（圈复杂度 35）：预防性维护。优先级中，工作量较大，需先补测试再重构。
5. 修复验证码不刷新：改正性维护。优先级中，工作量小。
评估思路：按维护类型分类，按业务影响与风险排优先级，按影响范围与复杂度估工作量，改正性优先修复高影响缺陷，预防性需在测试覆盖充分后进行。

**9.30 参考答案**
1. 体现的定律：
   - 持续变化定律：8 年不断修补说明系统持续演化。
   - 复杂度增加定律：无数次修补使结构腐化、复杂度增加。
   - 质量下降定律：每次修改引入新缺陷，质量下降。
   - 熟悉性保持定律被破坏：文档缺失、新人难接手，熟悉性未保持。
2. "每次修改都引入新缺陷"的原因：文档缺失导致理解不全、复杂度高耦合强导致修改牵一发动全身、无测试无法验证行为、结构腐化使修改风险高（复杂度增加与质量下降定律的体现）。
3. 改善策略：
   - 逆向工程恢复设计与文档，重建可理解性。
   - 补充自动化测试建立安全网。
   - 预防性维护：逐步重构降低复杂度、解耦。
   - 必要时对核心模块再工程重写。
   - 建立维护流程与变更控制，避免随意修改。
