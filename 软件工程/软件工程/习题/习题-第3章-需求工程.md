## 答案与解析

### 单选题答案

<details>
<summary>点击展开单选题答案与解析</summary>

**3.1 答案：A**
解析：需求工程核心活动为：需求获取 → 需求分析 → 需求规格说明 → 需求验证 → 需求管理（贯穿全程）。

**3.2 答案：B**
解析："查询借阅记录"描述系统应提供的功能，属于功能性需求。

**3.3 答案：B**
解析："响应时间不超过 2 秒"是性能要求，属于非功能性需求。A、C、D 都是功能需求。

**3.4 答案：C**
解析：用户难以表达需求时，快速原型最有效——通过可见的原型帮助用户明确和确认需求。

**3.5 答案：A**
解析：SRS 的国际标准是 IEEE 830（软件需求规格说明指南）。IEEE 1016 是软件设计描述，ISO/IEC 12207 是生命周期过程。

**3.6 答案：D**
解析：代码走查是代码阶段的静态测试方法，不属于需求验证。需求验证方法包括需求评审、原型验证、测试用例验证、形式化分析。

**3.7 答案：B**
解析：需求变更管理核心是评估变更影响并控制变更，保持需求一致性、可追溯性，而非阻止所有变更。

**3.8 答案：A**
解析：CCB（Configuration/Change Control Board，变更控制委员会）负责审批变更请求，评估其对成本、进度、质量的影响。

**3.9 答案：C**
解析：DFD 中加工（处理）表示对数据进行变换处理。外部实体表示数据来源/去向，数据存储表示保存的数据，数据流表示数据移动。

**3.10 答案：A**
解析："必须使用 Java 11 开发"是对技术选型的限制，属于设计约束。B、D 是功能需求，C 是性能（非功能）需求。

### 简答题答案

<details>
<summary>点击展开简答题参考答案</summary>

**3.21 参考答案**
需求工程主要活动及顺序：
1. 需求获取：通过访谈、问卷、观察、原型等方法从用户收集需求。
2. 需求分析与协商：整理、建模、消除冲突、协商优先级。
3. 需求规格说明：编写 SRS，形成正式需求文档。
4. 需求验证：通过评审、原型、测试用例验证需求的正确性与可测试性。
5. 需求管理：贯穿全程，包括需求基线、变更控制、可追溯性维护。

**3.22 参考答案**
- 功能性需求：描述系统"应该做什么"，即系统应提供的功能与行为。例：用户登录、生成报表。
- 非功能性需求：描述系统"做得怎么样"，即对功能实现的性能、质量约束。例：响应时间 ≤ 2 秒、可用性 ≥ 99.9%。
区别：功能性需求定义行为，非功能性需求定义质量属性与约束。

**3.23 参考答案**
- 访谈：适合小范围、深度获取需求，适用于关键干系人与复杂业务。
- 问卷调查：适合大规模收集广度信息，适用于用户分散的偏好统计。
- 观察与现场跟踪：适合理解现有实际业务流程，适用于用户难以表达的隐式流程。
- 原型：适合需求模糊、用户难以一次性表达的场景，通过可见原型确认需求。

**3.24 参考答案**
需求变更管理流程：
1. 变更申请：提出变更请求并记录。
2. 影响分析：评估变更对成本、进度、质量、其他需求的影响。
3. CCB 审批：变更控制委员会评审并决定是否批准。
4. 文档更新：批准后更新 SRS 与需求基线，维护可追溯性。
5. 实施与回归验证：实施变更并进行回归测试。
CCB 作用：统一审批变更，权衡影响，防止随意变更导致需求混乱与范围蔓延。

</details>

- 层次：这属于 DFD 的顶层图（或 0 层图）——只展示系统与外部实体的交互边界，不展开内部加工细节。

### 综合题答案

**3.29 参考答案**
- ① 只访谈部门经理未访谈操作员：危害是遗漏一线实际操作需求，导致系统不符合实际使用场景。正确做法：识别全部干系人，访谈包括一线操作员在内的各类用户。
- ② 把"用 Redis 缓存"写进 SRS 功能需求：危害是把实现细节混入需求，限制设计自由且不属于功能。正确做法：SRS 只描述"做什么"（如响应时间要求），实现技术（Redis）应放入设计文档或设计约束，而非功能需求。
- ③ 未做需求评审直接进入设计：危害是需求错误流入设计阶段，修复成本指数级上升。正确做法：在 SRS 完成后、设计前进行需求评审与验证。
- ④ 变更由开发人员直接改代码：危害是需求与代码脱节、无追溯、范围蔓延失控。正确做法：走变更管理流程（申请、影响分析、CCB 审批、文档更新、回归验证）。

**3.30 参考答案**
需求变更管理流程：
1. 变更申请：客户提交"数据分析报表"功能的变更请求单，记录变更内容与理由。
2. 影响分析：分析对 3 个模块的影响，评估工作量、成本、进度、对现有功能与测试的影响，更新可追溯性矩阵。
3. CCB 审批：CCB 评审影响分析，决定批准、拒绝或延期，明确优先级与排期。
4. 文档更新：批准后更新 SRS、需求基线、设计文档，维护需求-设计-测试的可追溯性。
5. 实施与回归验证：开发实施变更，进行单元测试、集成测试与回归测试，验证不影响既有功能。
若不控制变更的后果：需求与实现脱节、范围蔓延、进度失控、回归缺陷频发、可追溯性丧失、维护成本激增。
