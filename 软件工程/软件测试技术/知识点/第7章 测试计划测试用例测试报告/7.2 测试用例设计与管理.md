# 7.2 测试用例设计与管理

测试用例是测试计划的落地，是可执行、可管理、可复用的测试资产。第4、5章解决了“如何设计用例的方法”，本节解决“如何把用例规范化、文档化、管理起来”。一份规范的测试用例应具备明确的要素、可重复执行、可验证结果，并能随项目演进持续维护。

## 测试用例要素

> [!definition] 测试用例
> 测试用例（Test Case）是为特定目标设计的一组测试输入、执行条件和预期结果，用于验证程序是否满足某项需求。它是测试执行的最小可管理单元。

### 核心要素

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| 用例编号 | 唯一标识，便于追溯 | TC-LOGIN-001 |
| 用例标题 | 简述测试目标 | 正确用户名密码登录成功 |
| 优先级 | 重要程度 | P0/P1/P2 |
| 前置条件 | 执行前系统状态与准备 | 用户已注册且账号有效 |
| 测试步骤 | 操作序列 | 1.打开登录页 2.输入用户名 3.输入密码 4.点击登录 |
| 测试数据 | 输入数据 | 用户名:alice 密码:Pass1234 |
| 预期结果 | 执行后应呈现的行为 | 跳转到首页，显示用户名 |
| 实际结果 | 执行时观察到的行为（执行时填写） | 跳转到首页（通过）/ 报错（失败） |

> [!warning] 预期结果的关键
> > 预期结果必须**明确、可观察、可验证**。模糊的预期（如“应该正常”）无法判定通过与否。应描述具体的行为：页面跳转、数据变化、提示信息、状态变更等。

## 测试用例设计规范

```mermaid
flowchart LR
    A[需求分析] --> B[等价类+边界值: 单字段]
    B --> C[决策表: 多字段组合]
    C --> D[场景法: 业务流程]
    D --> E[补充异常与边界]
    E --> F[评审与基线化]
```

### 设计原则

- **明确性**：步骤与预期清晰无歧义，任何人执行结果一致；
- **可重复性**：相同输入与前置条件产生相同结果；
- **独立性**：用例之间尽量独立，避免依赖导致连锁失败；
- **可追溯性**：每条用例关联需求项，便于覆盖率统计；
- **适度颗粒度**：一个用例验证一个测试点，避免过大或过碎。

> [!tip] 与第4、5章方法的衔接
> > 本节是“用例管理”层面，设计方法见 [[4.1 等价类划分法]]、[[4.2 边界值分析法]]、[[4.3 因果图法与决策表法]]（黑盒）与 [[5.1 语句覆盖与判定覆盖]]、[[5.3 条件组合覆盖与路径覆盖]]（白盒）。本节关注如何把设计结果文档化为可管理用例。

## 测试用例评审

用例评审确保设计质量：

| 评审维度 | 检查点 |
| --- | --- |
| 完整性 | 是否覆盖所有需求项？边界与异常是否覆盖？ |
| 正确性 | 预期结果是否符合需求？步骤是否准确？ |
| 冗余性 | 是否有重复或高度相似的用例？ |
| 可执行性 | 步骤是否清晰可操作？前置条件是否可实现？ |
| 可追溯性 | 是否关联需求编号？ |

> [!note] 评审形式
> > 用例评审可采用同行评审（测试人员互查）、走查（作者引导讲解）、审查（正式会议逐条检查）等形式。关键用例（P0）应经开发与产品共同确认。

## 测试用例管理工具

| 工具 | 类型 | 特点 | 适用场景 |
| --- | --- | --- | --- |
| TestRail | 商业 | 用例+计划+报告一体化 | 中大型团队 |
| Jira + 插件 | 商业 | 与缺陷管理集成 | 敏捷团队 |
| 禅道 | 开源/商业 | 国产，用例+缺陷+项目管理 | 国内团队 |
| TestLink | 开源 | 免费用例管理 | 中小团队 |
| Excel | 通用 | 灵活、零成本 | 小型项目早期 |

> [!tip] Excel 与专业工具的选择
> > 小型项目或课程练习用 Excel 足够；中大型项目建议用专业工具，便于版本管理、执行跟踪、覆盖率统计与团队协作。自动化用例应纳入代码仓库与 CI 管理。

## 测试用例模板示例

### 模板

| 字段 | 内容 |
| --- | --- |
| 用例编号 | TC-{模块}-{序号} |
| 用例标题 | 简述测试目标 |
| 优先级 | P0/P1/P2 |
| 关联需求 | REQ-{编号} |
| 前置条件 | 系统状态与准备 |
| 测试步骤 | 编号步骤 |
| 测试数据 | 输入数据 |
| 预期结果 | 可观察行为 |
| 实际结果 | （执行时填写） |
| 执行状态 | 通过/失败/阻塞/未执行 |

### 示例用例

| 字段 | 内容 |
| --- | --- |
| 用例编号 | TC-LOGIN-001 |
| 用例标题 | 正确用户名密码登录成功 |
| 优先级 | P0 |
| 关联需求 | REQ-LOGIN-01 |
| 前置条件 | 用户 alice 已注册且账号有效 |
| 测试步骤 | 1.打开登录页 /login<br>2.用户名输入框填入 alice<br>3.密码输入框填入 Pass1234<br>4.点击“登录”按钮 |
| 测试数据 | 用户名:alice 密码:Pass1234 |
| 预期结果 | 页面跳转到 /home，右上角显示用户名 alice，登录态有效 |
| 实际结果 | （执行时填写） |
| 执行状态 | （执行时填写） |

> [!example] 用例与等价类的关系
> > 上述用例对应 [[4.1 等价类划分法]] 中“有效等价类”的代表值。完整用例集还应包含无效等价类用例（如密码错误、用户名不存在）与边界值用例（如密码长度恰好为下限），由设计方法生成后再按本节模板文档化。

## 小结

测试用例是可执行、可管理的测试资产，核心要素包括编号、标题、优先级、前置条件、步骤、数据、预期与实际结果，其中预期结果须明确可验证。设计应遵循明确性、可重复性、独立性、可追溯性原则，把第4、5章方法的结果文档化。用例需经评审确保质量，并使用专业工具或 Excel 管理。用例是连接测试计划与测试报告的桥梁，需随项目持续维护。
