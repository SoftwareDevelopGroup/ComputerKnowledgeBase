### 单选题答案

<details>
<summary>点击展开单选题答案与解析</summary>

**9.1 答案：B**
解析：自动化测试替代的是"测试用例的执行与结果比对"环节，而非"测试设计与判断"环节。测试设计与探索性判断仍需人工完成。

**9.2 答案：B**
解析：需求频繁变更的 UI 不宜引入自动化，因为每次界面调整都需重写定位与脚本，脚本易碎且维护成本超过回归收益。

**9.3 答案：C**
解析：单元自动化投入小、稳定性高、回报快；接口自动化覆盖契约、回报高；UI 自动化投入大、易碎、回报慢。投入产出比由高到低为单元 > 接口 > UI。

**9.4 答案：C**
解析：数据驱动框架的核心是测试数据与脚本分离，数据存于外部文件（CSV/Excel），同一脚本可跑多组数据。A 是线性框架，B 是关键字驱动，D 是模块化。

**9.5 答案：A**
解析：Selenium WebDriver 通过 HTTP 协议（W3C WebDriver 协议）向浏览器驱动发送命令，驱动再操作浏览器。

**9.6 答案：B**
解析：GET 方法语义为查询资源，是幂等操作。POST 是新增，PUT 是整体更新，DELETE 是删除。

**9.7 答案：B**
解析：401 表示未认证（缺少或失效 token）；403 是权限不足；404 是资源不存在；500 是服务器内部错误。

**9.8 答案：B**
解析：负载测试逐步加压，找出满足性能指标的最大吞吐，回答"系统能支撑多少"。找崩溃点是压力测试，长期稳定是稳定性测试。

**9.9 答案：A**
解析：JMeter 线程组三个关键参数：Number of Threads（并发用户数）、Ramp-up Period（爬坡时间）、Loop Count（循环次数）。

**9.10 答案：C**
解析：Little 定律 $L = \lambda \times W$ 中，$L$ 为系统中平均请求数（并发），$\lambda$ 为到达率（吞吐量），$W$ 为平均响应时间。

**9.16 答案：错误**
解析：自动化测试不能完全替代手工测试。它擅长回归与重复，不擅长发现新缺陷；探索性测试与测试设计仍需人工。自动化与手工测试互补。

### 简答题答案

<details>
<summary>点击展开简答题参考答案</summary>

**9.21 参考答案**
适用场景：①频繁回归测试（脚本可重复执行）；②稳定接口测试（契约稳定，ROI 高）；③性能/负载测试（人工无法模拟高并发）；④数据驱动大量输入组合。
不适用场景：①需求频繁变更（脚本频繁失效）；②探索性测试（依赖人的即时判断）；③一次性项目（投入无法收回）；④UI 极不稳定（易碎，维护成本超过收益）。
需求频繁变更时 UI 自动化维护成本极高：每次界面调整都需重写定位与脚本，脚本易碎且频繁失败，维护成本超过回归收益，因此不宜大规模引入；应优先做接口自动化，UI 自动化只覆盖核心稳定路径。

**9.22 参考答案**
常用方法：GET（查询）、POST（新增）、PUT（整体更新）、PATCH（部分更新）、DELETE（删除）。
典型状态码：200 成功、201 创建成功、400 请求错误、401 未认证、403 禁止访问、404 资源不存在、500 服务器错误。
接口测试应断言：①状态码是否符合预期；②响应体结构与字段值是否正确；③响应时间是否在阈值内；④响应头是否符合契约（如 Content-Type）；⑤业务副作用（如 POST 后 GET 能查到新增数据、数据库状态变化）。

**9.23 参考答案**
- 负载测试：逐步增加负载，找出满足性能指标的最大吞吐，回答"系统能支撑多少"。
- 压力测试：施加超过容量的负载，找出崩溃点与恢复能力，回答"系统何时崩溃、能否恢复"。
- 稳定性测试：在正常负载下长时间运行，检查内存泄漏与稳定性，回答"系统能否长期稳定"。
TPS 反映吞吐能力，响应时间反映用户体验。随并发数增加，TPS 先线性上升，到达拐点后受资源限制趋于平缓或下降，同时响应时间急剧上升。性能评估需同时关注吞吐与响应，找到二者的平衡拐点。

**9.24 参考答案**
- 线性框架：脚本顺序执行、无抽象，简单但难维护，适合一次性验证。
- 数据驱动框架：测试数据与脚本分离，数据存于表格/文件，同一脚本可跑多组数据，适合大量输入组合的回归。
- 关键字驱动框架：把操作抽象为关键字（如 click、input），测试逻辑用关键字表格描述，非技术人员可参与，适合大型长期项目但实现复杂。
大型项目通常采用混合框架（数据驱动+关键字驱动）。

</details>

**9.27 参考答案**
JMeter 测试计划关键参数：
- 线程组：Number of Threads = 100（并发用户数），Ramp-up Period = 20 秒，Loop Count = 10；
- HTTP 取样器：POST /api/login，请求体 `{"username":"alice","password":"Pass1234"}`；
- 定时器：Constant Timer，延迟 1000ms（思考时间）；
- 断言：响应码为 200；
- 监听器：聚合报告。

Little 定律验证：
$$L = \lambda \times W$$
已知 $L = 100$（并发数），$W = 0.4$ 秒（平均响应时间），则：
$$\lambda = \frac{L}{W} = \frac{100}{0.4} = 250 \text{ req/s}$$
估算吞吐量 250 req/s > 100 req/s 目标，满足 TPS ≥ 100 的要求。

**9.28 参考答案**
```python
import pytest
import requests

BASE_URL = "https://demo.example.com/api"


class TestUserAPI:
    """用户接口测试"""

    def setup_class(self):
        # 登录获取 token, 供后续用例复用
        resp = requests.post(f"{BASE_URL}/login", json={
            "username": "alice",
            "password": "Pass1234"
        })
        assert resp.status_code == 200
        self.token = resp.json()["token"]

    def test_get_user_info(self):
        """正向: 查询用户信息"""
        headers = {"Authorization": f"Bearer {self.token}"}
        resp = requests.get(f"{BASE_URL}/user/alice", headers=headers)

        assert resp.status_code == 200
        data = resp.json()
        assert data["username"] == "alice"
        assert "email" in data

    def test_get_user_without_token(self):
        """反向: 未认证应返回 401"""
        resp = requests.get(f"{BASE_URL}/user/alice")
        assert resp.status_code == 401

    @pytest.mark.parametrize("username,password,expected_code", [
        ("alice", "Pass1234", 200),
        ("alice", "wrong", 401),
        ("", "Pass1234", 400),
    ])
    def test_login(self, username, password, expected_code):
        """数据驱动: 多组登录用例"""
        resp = requests.post(f"{BASE_URL}/login", json={
            "username": username,
            "password": password
        })
        assert resp.status_code == expected_code
```
说明：`setup_class` 登录获取 token 并复用，体现 token 共享；`test_get_user_without_token` 验证认证；`test_login` 用 `@pytest.mark.parametrize` 做数据驱动，体现同一脚本跑多组数据。

**9.29 参考答案**
1. 三层自动化测试比例与范围（测试金字塔）：
   - 单元自动化（最多，约 70%）：后端 Java 服务核心逻辑（价格计算、库存扣减、优惠券）用 JUnit 覆盖，目标覆盖率 > 80%；
   - 接口自动化（次之，约 20%）：商品、购物车、订单、支付接口用 Requests/Postman 自动化，覆盖正向/反向/权限；
   - UI 自动化（最少，约 10%）：核心业务路径（浏览→加购→下单→支付）用 Selenium/Cypress E2E 覆盖。
2. UI 自动化只覆盖核心路径的原因：①UI 测试执行慢，反馈周期长；②UI 易变，脚本维护成本高、易碎；③定位问题困难，失败难以归因；④投入产出比低于底层测试。大量 UI 测试会导致冰淇淋反模式。
3. 各层推荐工具：
   - 单元：JUnit（Java 后端）、Jest（React 前端组件）；
   - 接口：Postman（手工调试）、Requests+PyTest（自动化进 CI）；
   - UI：Selenium 或 Cypress（Web E2E）。
4. 需求每月迭代、UI 频繁调整时的策略调整：
   - 把自动化重心下沉到接口层（接口相对稳定，ROI 高）；
   - UI 自动化只保留最核心的冒烟路径（如登录、下单），减少易碎脚本；
   - 前端组件用 Jest 做 DOM 单元测试替代部分 E2E；
   - 接口与冒烟用例接入 CI，每次构建自动回归；
   - 评估每个 UI 用例的维护成本，淘汰维护成本高于回归收益的脚本。

**9.30 参考答案**
1. Little 定律验证：
   已知并发数 $L = 200$，平均响应时间 $W = 0.5$ 秒，则理论吞吐量：
   $$\lambda = \frac{L}{W} = \frac{200}{0.5} = 400 \text{ req/s}$$
   实测 TPS 峰值 380，略低于理论 400，说明系统接近稳定极限但存在少量损耗，关系基本自洽。
2. 未达标指标与瓶颈：
   - TPS 380 < 400 目标，未达标；
   - 数据库连接池使用率 95%，接近耗尽，是首要瓶颈；
   - CPU 85% 偏高，但未到极限；
   - 响应时间 0.5 秒 = 500ms，刚好达标但已到临界；
   - 错误率 0.05% < 0.1%，达标。
   主要瓶颈在数据库连接池，连接等待导致 TPS 无法继续提升。
3. 优化建议：
   - 扩大数据库连接池上限，减少连接等待；
   - 对热点接口增加缓存（如 Redis），减少数据库访问；
   - 优化慢 SQL，增加索引，减少单次查询耗时；
   - 对商品详情等读多写少接口做读写分离；
   - 考虑横向扩容应用服务器，分散负载。
4. "只看平均值"的误区：
   平均值会被大量快速请求稀释，掩盖少数慢请求（长尾）。例如平均 500ms 可能包含 95% 的 200ms 请求和 5% 的 5 秒请求。应关注 90 分位（P90）、95 分位（P95）、99 分位（P99）响应时间，反映长尾用户体验，确保大多数用户都能获得良好体验。
