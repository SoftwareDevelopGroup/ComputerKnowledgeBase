### 简答题答案

<details>
<summary>点击展开简答题参考答案</summary>

**6.21 参考答案**
- 桩模块（Stub）：位于被测模块的下层，模拟被调用的模块，接收参数并返回预设值。用于自顶向下集成。
- 驱动模块（Driver）：位于被测模块的上层，模拟调用模块，传递参数并接收返回值。用于自底向上集成。
记忆：桩在下（被调用），驱在上（调用者）。

**6.22 参考答案**

| 形式 | 环境 | 参与者 | 特点 |
| --- | --- | --- | --- |
| Alpha 测试 | 开发者环境 | 用户（开发者在场观察） | 受控、可即时反馈，早期内测 |
| Beta 测试 | 用户实际环境 | 最终用户（开发者不在场） | 不可控、贴近真实，发布前公测 |
| UAT | 模拟或生产环境 | 用户代表 | 按合同/验收标准逐项确认 |

时序：Alpha 先于 Beta，Beta 反馈稳定后进入 UAT 与发布。

**6.23 参考答案**
- 全量回归：执行全部已有用例，覆盖最全但成本高，适用于发布前关键节点。
- 选择性回归：选择部分用例执行，成本低但需准确选择，适用于日常迭代与缺陷修复。
选择性回归的依据：①基于风险（优先回归高风险模块）；②基于变更影响分析（分析修改影响范围选相关用例）；③基于用例优先级（高优先级必跑）。

**6.24 参考答案**

| 维度 | 冒烟测试 | 回归测试 |
| --- | --- | --- |
| 目标 | 确认系统可测（准入） | 确认不退化（保障） |
| 范围 | 核心功能主流程 | 已有用例（全量或选择） |
| 时机 | 详细测试前 | 修改后、发布前 |
| 失败处理 | 退回修复，不继续 | 记录缺陷，继续或停止 |

</details>

**6.25 参考答案**
```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.BeforeEach;
import static org.junit.jupiter.api.Assertions.*;

public class CalculatorTest {
    private Calculator calc;

    @BeforeEach
    public void setUp() {
        // 每个测试方法前执行，初始化测试夹具
        calc = new Calculator();
    }

    @Test
    public void testAdd() {
        // 输入: 2 和 3; 预期输出: 5
        assertEquals(5, calc.add(2, 3));
    }

    @Test
    public void testDivideByZero() {
        // 验证除零异常处理
        assertThrows(ArithmeticException.class, () -> calc.divide(10, 0));
    }
}
```

**6.26 参考答案**
- 自顶向下集成：从主控模块 A 开始，A 调用 B 和 C。步骤：①先测 A，用桩模块模拟 B 和 C（Stub_B、Stub_C）；②逐步用真实的 B、C 替换桩模块，每次替换后测试。需要的辅助模块：2 个桩模块。
- 自底向上集成：从底层 B、C 开始。步骤：①先测 B，用驱动模块 Driver_B 调用 B；②再测 C，用驱动模块 Driver_C 调用 C；③B、C 测试通过后，组装到 A 下，用驱动模块 Driver_A 调用 A（此时 A 未完成则用桩或驱动模拟）。需要的辅助模块：驱动模块。

**6.27 参考答案**

| 优先级 | 依据 | 回归策略 |
| --- | --- | --- |
| P0 高 | 核心功能、主流程、高频使用 | 每次必跑，优先自动化 |
| P1 中 | 重要功能、常见场景 | 每次迭代回归 |
| P2 低 | 边缘功能、低频场景 | 发布前或周期性回归 |

**6.28 参考答案**
顺序与对应 V 模型阶段：
1. 单元测试 ← 详细设计
2. 集成测试 ← 概要设计
3. 系统测试 ← 需求分析
4. Alpha 测试（开发环境内测）
5. Beta 测试（用户环境公测）
6. UAT 用户验收 ← 用户需求
7. 发布上线

### 综合题答案

<details>
<summary>点击展开综合题参考答案</summary>

**6.29 参考答案**
1. V 模型对应关系：用户需求→验收测试；需求分析→系统测试；概要设计→集成测试；详细设计→单元测试；编码→实现。

2. 各阶段依据、执行者与方法：

| 测试阶段 | 依据 | 执行者 | 方法 |
| --- | --- | --- | --- |
| 单元测试 | 详细设计 | 开发人员 | 白盒为主 |
| 集成测试 | 概要设计 | 开发/测试 | 灰盒为主 |
| 系统测试 | 需求规格 | 独立测试团队 | 黑盒为主 |
| 验收测试 | 用户需求 | 用户代表 | 黑盒为主 |

3. 若要求"尽早测试"，应引入 W 模型。理由：W 模型用双 V 结构强调开发与测试同步，每个开发阶段都伴随测试活动（需求评审、设计评审），把测试从"编码后"提前到"需求与设计阶段"，是"尽早测试"原则的过程化体现。

**6.30 参考答案**
1. 冒烟测试的作用是确认系统基本功能可用，是详细测试的准入门槛。若冒烟失败应直接退回修复，不继续详细测试，避免在不可测的系统上浪费时间。
2. 选择性回归基于：①风险（高风险模块优先）；②变更影响分析（分析修改影响范围选相关用例）；③用例优先级（高优先级必跑）。
3. 全量回归通常在发布前关键节点使用，覆盖最全但成本高。
4. 回归测试最受益于自动化，因为回归用例高频执行、需要重复运行，自动化后可集成到 CI/CD 每次构建自动执行，实现持续回归，大幅节省人力。

</details>
